## 框架对比

### 1. 🔥 三个框架分别适合什么场景

**简要总结：**

- FastAPI：现代 API 框架，异步友好，类型注解驱动，自动生成 OpenAPI 文档
- Django：大而全的 Web 框架，自带 ORM、Admin、认证、模板、迁移
- Flask：轻量微框架，核心简单，扩展自由，适合小服务或高度定制项目

**面试口语：**

FastAPI 更适合高性能接口服务和前后端分离项目；Django 适合后台系统、CMS、管理平台这类需要完整工程能力的项目；Flask 更轻量，适合小型服务、脚本型接口或需要自己组合技术栈的项目。

**底层原理 / 背后逻辑：**

三者差异本质是“框架帮你管多少事情”。Django 内置多，约定强，开发效率高但灵活度相对低；Flask 只提供路由、请求响应等核心能力，其他靠扩展；FastAPI 站在 ASGI、类型注解和 Pydantic 之上，把参数校验、文档生成、异步处理都标准化了。

### 2. 🔥 WSGI 和 ASGI

**简要总结：**

- WSGI 是传统 Python Web 同步网关协议
- ASGI 支持异步、WebSocket、长连接
- Flask、Django 早期主要基于 WSGI
- FastAPI 基于 ASGI
- Django 现在也支持 ASGI

**面试口语：**

WSGI 更像同步请求响应模型，一个请求进来，应用处理完再返回。ASGI 支持异步事件模型，不只支持 HTTP，还能支持 WebSocket、SSE 这类长连接场景。

**底层原理 / 背后逻辑：**

Web 服务器和 Python 应用之间需要一套调用协议。WSGI 规定服务器把请求环境和回调传给应用，应用返回响应 iterable；它模型简单但不适合原生异步。ASGI 把连接抽象成 `scope`、`receive`、`send` 三部分，应用可以异步接收事件、发送事件，因此适合异步 IO 和实时通信。

```python
# ASGI 应用的简化形态
async def app(scope, receive, send):
    await send({
        "type": "http.response.start",
        "status": 200,
        "headers": [(b"content-type", b"text/plain")]
    })
    await send({
        "type": "http.response.body",
        "body": b"hello"
    })
```

📌 重点记忆：WSGI 是同步 Web 协议，ASGI 是异步事件协议。

## FastAPI

### 1. 🔥 FastAPI 核心特点

**简要总结：**

- 基于 Starlette 和 Pydantic
- 使用类型注解做参数解析和校验
- 自动生成 Swagger / OpenAPI 文档
- 原生支持 async / await
- 依赖注入系统强

**面试口语：**

FastAPI 的核心优势是类型注解驱动开发。请求参数、请求体、响应模型都可以通过类型声明表达，框架会自动完成校验、转换和文档生成。

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UserCreate(BaseModel):
    name: str
    age: int

@app.post("/users")
async def create_user(user: UserCreate):
    return {"name": user.name, "age": user.age}
```

**底层原理 / 背后逻辑：**

FastAPI 自身负责路由注册、依赖解析和文档集成；底层请求响应能力来自 Starlette；数据校验和序列化主要来自 Pydantic。函数参数上的类型注解会被 FastAPI 读取，用来判断参数来自 path、query、header、cookie 还是 body，并自动生成 OpenAPI schema。

### 2. 🔥 FastAPI 依赖注入

**简要总结：**

- 使用 `Depends`
- 可复用数据库连接、登录用户、权限校验
- 支持依赖嵌套
- 方便测试时替换依赖

**面试口语：**

FastAPI 的依赖注入可以把通用逻辑从接口函数里抽出去，比如获取数据库会话、解析当前用户、校验权限。这样接口函数更关注业务本身。

```python
from fastapi import Depends, HTTPException

def get_current_user(token: str):
    if token != "valid":
        raise HTTPException(status_code=401, detail="未登录")
    return {"id": 1, "name": "Tom"}

@app.get("/profile")
def profile(user=Depends(get_current_user)):
    return user
```

**底层原理 / 背后逻辑：**

FastAPI 在处理请求前会构建依赖图，按依赖关系依次执行。每个依赖的返回值会注入到接口函数参数中。依赖可以继续依赖别的函数，因此能形成树状解析过程。测试时可以通过 `app.dependency_overrides` 替换依赖，减少对真实数据库或认证服务的依赖。

### 3. ⭐ FastAPI 同步和异步接口

**简要总结：**

- `async def` 适合调用异步数据库、异步 HTTP 客户端
- 普通 `def` 适合同步逻辑
- 异步接口中不要调用阻塞函数
- CPU 密集型任务不适合直接放在事件循环里执行

**面试口语：**

FastAPI 支持同步和异步接口。异步接口不是写了 `async` 就一定更快，关键是内部调用的 IO 库也要是异步的。如果在 async 接口里调用阻塞数据库驱动，反而会卡住事件循环。

## Django

### 1. 🔥 Django 核心特点

**简要总结：**

- MTV 架构：Model、Template、View
- 自带 ORM、Admin、认证、Session、中间件、迁移
- 工程约定强，适合快速搭建完整 Web 系统
- 生态成熟

**面试口语：**

Django 是 batteries included 的框架，很多 Web 项目常用能力都内置了。它适合后台管理系统、内容管理系统、企业内部平台这类需要快速交付和长期维护的项目。

**底层原理 / 背后逻辑：**

Django 的核心链路是 URLConf 匹配路由，View 处理请求，Model 通过 ORM 访问数据库，Template 渲染 HTML。中间件包在请求前后，可以处理认证、Session、CSRF、日志等横切逻辑。

```python
# urls.py
path("users/<int:user_id>/", views.user_detail)

# views.py
def user_detail(request, user_id):
    user = User.objects.get(id=user_id)
    return JsonResponse({"id": user.id, "name": user.name})
```

### 2. 🔥 Django ORM

**简要总结：**

- 用 Python 类映射数据库表
- QuerySet 是惰性执行的
- 支持迁移、关联查询、事务
- 注意 N+1 查询问题

**面试口语：**

Django ORM 把表映射成模型类，把查询封装成 QuerySet。QuerySet 通常是惰性的，只有真正遍历、取值或序列化时才执行 SQL。

```python
users = User.objects.filter(is_active=True)

for user in users:
    print(user.name)
```

**底层原理 / 背后逻辑：**

ORM 的本质是把对象操作翻译成 SQL。惰性 QuerySet 让查询可以继续链式拼接，直到需要结果时再统一生成 SQL。性能面试常追问 `select_related` 和 `prefetch_related`：前者适合外键一对一或多对一，用 SQL join；后者适合多对多或反向关系，用额外查询后在 Python 层组装。

## Flask

### 1. 🔥 Flask 核心特点

**简要总结：**

- 微框架，核心轻量
- 路由和请求响应简单
- 扩展生态丰富
- 技术选型自由

**面试口语：**

Flask 的核心很小，适合小服务和灵活定制。它不会强制你用某个 ORM、模板或认证方案，团队可以按项目需要选择扩展。

```python
from flask import Flask, jsonify

app = Flask(__name__)

@app.get("/health")
def health():
    return jsonify({"status": "ok"})
```

**底层原理 / 背后逻辑：**

Flask 基于 Werkzeug 处理 WSGI 请求和路由匹配，基于 Jinja2 做模板渲染。请求进来后，Flask 根据 URL rule 找到 view function，执行后把返回值转换成 Response。因为核心轻，复杂项目需要自己补齐配置管理、认证、ORM、迁移和项目分层规范。
