## REST 基础

### 1. 🔥 RESTful 是什么

**简要总结：**

- REST 是一种面向资源的接口设计风格
- URL 表示资源
- HTTP 方法表示动作
- 状态码表示结果
- 请求和响应通常使用 JSON

**面试口语：**

RESTful 的核心是资源。比如用户资源用 `/users` 表示，获取用户用 GET，创建用户用 POST，更新用 PUT 或 PATCH，删除用 DELETE。接口设计要让 URL 表达资源，而不是把动作都写进 URL。

**底层原理 / 背后逻辑：**

HTTP 本身已经提供了方法、状态码、Header、缓存等语义。RESTful 是利用 HTTP 语义组织接口，让客户端和服务端的约定更清晰。好的 REST API 不只是路径好看，而是资源边界清楚、方法语义正确、状态码准确、错误格式统一。

```txt
GET    /users          查询用户列表
POST   /users          创建用户
GET    /users/1        查询用户详情
PATCH  /users/1        局部更新用户
DELETE /users/1        删除用户
```

### 2. 🔥 HTTP 方法语义

**简要总结：**

- GET：查询资源
- POST：创建资源或提交动作
- PUT：整体替换资源
- PATCH：局部更新资源
- DELETE：删除资源
- GET 应该是安全且幂等的
- PUT / DELETE 通常是幂等的

**面试口语：**

GET 不应该修改服务端数据；PUT 是整体替换，PATCH 是局部修改。幂等的意思是同一个请求执行一次和执行多次，最终结果应该一样，比如重复 DELETE 同一个资源，资源最终都是不存在。

**底层原理 / 背后逻辑：**

方法语义会影响缓存、重试和网关行为。GET 可以被缓存和预取，如果 GET 做删除操作，浏览器、爬虫或代理一次访问就可能造成数据变更。幂等接口更适合失败重试，因为重复执行不会造成额外副作用。

### 3. 🔥 状态码设计

**简要总结：**

- 200：成功
- 201：创建成功
- 204：成功但无响应体
- 400：参数错误
- 401：未认证
- 403：无权限
- 404：资源不存在
- 409：资源冲突
- 422：语义校验失败
- 500：服务端错误

**面试口语：**

状态码要表达请求结果。没登录是 401，没有权限是 403，资源不存在是 404，参数格式错误是 400，业务唯一键冲突可以用 409。不要所有错误都返回 200 再靠业务 code 判断。

```python
from fastapi import HTTPException

def get_user(user_id: int):
    user = find_user(user_id)
    if user is None:
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
```

### 4. ⭐ 统一响应格式

**简要总结：**

- 成功响应统一结构
- 错误响应统一结构
- 便于前端拦截和日志排查
- 不要让 HTTP 状态码失去语义

**面试口语：**

项目里通常会统一响应格式，比如 `code`、`message`、`data`。但我不会把所有请求都返回 HTTP 200，HTTP 状态码仍然要表达协议层结果，业务 code 表达业务细节。

```json
{
  "code": "USER_NOT_FOUND",
  "message": "用户不存在",
  "data": null
}
```

### 5. 🔥 分页、过滤和排序

**简要总结：**

- 分页常用 `page/page_size` 或 `limit/offset`
- 大数据量可用游标分页 cursor
- 过滤条件放 query 参数
- 排序用 `sort` 或 `order_by`

**面试口语：**

列表接口要考虑分页、筛选和排序。普通后台管理系统可以用 page/page_size；数据量很大或实时变化明显时，cursor 分页更稳定。

```txt
GET /users?page=1&page_size=20&status=active&sort=-created_at
```

**底层原理 / 背后逻辑：**

offset 分页在页数很深时性能会变差，因为数据库要跳过大量记录；并且数据插入删除时可能出现重复或漏数据。cursor 分页用某个稳定排序字段作为游标，比如 `created_at` 或 `id`，更适合信息流和大数据量滚动加载。

### 6. ⭐ API 版本管理

**简要总结：**

- URL 版本：`/api/v1/users`
- Header 版本：`Accept: application/vnd.xxx.v1+json`
- 大多数项目使用 URL 版本更直观
- 版本升级要考虑兼容和废弃周期

**面试口语：**

API 一旦对外使用，就不能随便改字段语义。常见做法是加版本号，比如 `/api/v1`，大版本不兼容时新增 `/api/v2`，给客户端迁移时间。

### 7. 🔥 RESTful 常见问题

**常见追问：**

- REST 和 RPC 区别是什么？
- PUT 和 PATCH 区别是什么？
- 为什么不能所有接口都 POST？
- HTTP 状态码和业务 code 怎么分工？
- 如何设计批量操作接口？

**面试口语：**

REST 偏资源建模，RPC 偏动作调用。不是所有接口都必须 REST，比如登录、导出、批量审批这些动作型接口，用 POST 表达操作也合理。关键是语义清楚、幂等性和错误处理明确。
