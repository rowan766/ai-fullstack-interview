# 后端性能优化

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 性能优化基础

### 1. 🔥 后端性能优化思路

**简要总结：**

- 先度量，再优化
- 判断瓶颈在 CPU、IO、数据库、网络还是锁竞争
- 常用指标：QPS、RT、P95/P99、错误率、CPU、内存、数据库慢查询
- 优化后要对比数据

**面试口语：**

后端优化不能一上来就加缓存。应该先看监控和日志，判断慢在数据库、接口调用、CPU 计算还是网络 IO。定位瓶颈后再选择索引、缓存、异步、并发、批处理等手段。

**底层原理 / 背后逻辑：**

性能问题本质是资源竞争和等待。CPU 忙说明计算或序列化重；数据库慢可能是索引、锁、SQL 或连接池问题；IO 慢可能是下游服务或网络等待；内存涨可能是缓存、对象引用或批量数据加载。优化要针对瓶颈，否则可能只是把压力转移到别处。

### 2. 🔥 数据库优化

**简要总结：**

- 建立合适索引
- 避免 N+1 查询
- 只查询需要字段
- 分页避免深 offset
- 使用连接池
- 分析慢 SQL

**面试口语：**

数据库通常是后端性能瓶颈。优化时先看慢查询和执行计划，确认有没有走索引，再看是否有 N+1 查询、返回字段过多、深分页等问题。

```sql
EXPLAIN SELECT id, name FROM users WHERE email = 'a@example.com';
```

**底层原理 / 背后逻辑：**

索引本质是额外的数据结构，常见 B+Tree 索引能减少扫描行数。没有索引时可能全表扫描，数据量大后会很慢。但索引不是越多越好，写入时也要维护索引，会增加写成本。

### 3. 🔥 缓存

**简要总结：**

- 本地缓存：速度快，但多实例不共享
- Redis：集中缓存，适合分布式服务
- 缓存 key 要设计清楚
- 要考虑过期、失效、穿透、击穿、雪崩

**面试口语：**

缓存适合读多写少、计算成本高、实时性要求没那么强的数据。使用缓存要重点考虑一致性和异常场景，比如缓存穿透、击穿、雪崩。

```python
def get_user(user_id: int):
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)

    user = query_user(user_id)
    redis.setex(key, 300, json.dumps(user))
    return user
```

**底层原理 / 背后逻辑：**

缓存是用空间换时间，把慢查询或重复计算结果放到更快的存储里。缓存一致性通常采用 Cache Aside：先读缓存，未命中查数据库再写缓存；更新时先改数据库，再删除缓存。删除缓存比更新缓存更常见，因为可以避免复杂对象部分字段不一致。

### 4. 🔥 缓存穿透、击穿、雪崩

**简要总结：**

- 穿透：查询不存在数据，缓存一直不命中
- 击穿：热点 key 过期，大量请求打到数据库
- 雪崩：大量 key 同时过期或缓存服务故障
- 防护：空值缓存、布隆过滤器、互斥锁、随机过期时间、降级

**面试口语：**

缓存穿透是查不存在的数据，可以缓存空值或用布隆过滤器；缓存击穿是热点 key 失效，可以用互斥锁或逻辑过期；缓存雪崩是大量 key 同时失效，要给过期时间加随机值并做好降级。

### 5. ⭐ 接口优化

**简要总结：**

- 减少不必要字段
- 合并请求或批量查询
- 下游调用设置超时
- 并发请求下游
- 异步处理非关键任务

**面试口语：**

接口优化要看关键路径。能少查就少查，能批量就不要循环单查，下游请求一定要设置超时，非关键任务比如发通知可以异步化。

```python
async def get_dashboard():
    user_task = asyncio.create_task(fetch_user())
    order_task = asyncio.create_task(fetch_orders())
    return {
        "user": await user_task,
        "orders": await order_task,
    }
```

### 6. ⭐ 序列化和大数据返回

**简要总结：**

- 大响应会增加网络和序列化成本
- 避免一次返回过多数据
- 使用分页、字段裁剪、压缩
- 大文件使用流式响应

**面试口语：**

接口慢不一定都慢在数据库，也可能慢在 JSON 序列化和网络传输。列表接口要分页，大文件要流式返回，避免一次性把所有数据放进内存。

### 7. ⭐ 连接池

**简要总结：**

- 数据库、Redis、HTTP 客户端都常用连接池
- 复用连接减少建立连接成本
- 连接数过小会排队，过大会压垮下游
- 要设置超时和最大连接数

**面试口语：**

连接池是为了复用连接，避免每次请求都创建 TCP 连接或数据库连接。但连接池不是越大越好，下游承载有限，过大反而会增加数据库压力。
