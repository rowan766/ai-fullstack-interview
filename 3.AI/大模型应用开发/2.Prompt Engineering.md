## Prompt 基础

### 1. 🔥 Prompt Engineering 是什么

**简要总结：**

- Prompt Engineering 是设计输入，让模型更稳定完成任务的方法
- 目标是明确任务、约束边界、提供上下文和输出格式
- 常见手段：角色设定、任务拆解、示例、格式约束、反问澄清
- 本质是管理模型当前上下文，而不是修改模型参数

**面试口语：**

Prompt Engineering 不是写一段漂亮的话，而是把任务目标、背景信息、约束条件和输出格式清楚地放进上下文里，让模型减少猜测空间，输出更稳定。

**底层原理 / 背后逻辑：**

LLM 是根据上下文预测后续 Token。Prompt 的作用就是改变上下文分布，让模型更倾向于生成符合任务的答案。指令越模糊，模型越依赖训练中的一般模式；约束越清晰，模型越容易在当前上下文内对齐任务目标。

### 2. 🔥 一个好 Prompt 包含什么

**简要总结：**

- 角色：模型扮演什么能力
- 任务：要完成什么
- 上下文：可用信息和业务背景
- 约束：不能做什么、优先级是什么
- 输出格式：JSON、表格、步骤、字段
- 示例：Few-shot 示例能稳定格式和判断标准

**面试口语：**

我一般会把 Prompt 拆成角色、任务、上下文、约束、输出格式和示例。尤其是业务系统里，输出格式一定要明确，否则后续程序很难稳定解析。

```text
你是一个客服工单分类助手。
任务：根据用户描述判断工单类型。
类型只能是：退款、物流、账号、其他。
输出 JSON：{"category": "...", "reason": "..."}。

用户描述：我买的东西三天没发货。
```

### 3. 🔥 System / User / Assistant 消息

**简要总结：**

- System：定义模型行为、边界和全局规则
- User：用户真实请求
- Assistant：历史回复，用于多轮上下文
- 多轮对话本质是把历史消息重新传入模型

**面试口语：**

System Prompt 更像应用给模型的全局规则，User Message 是用户当前输入。多轮对话不是模型天然记住历史，而是应用把历史消息或摘要重新放进请求上下文。

**底层原理 / 背后逻辑：**

模型每次调用只看到当前请求中的上下文。不同角色消息会通过模型的聊天模板转成特定 Token 序列，让模型理解谁在说话、哪些是规则、哪些是用户输入。系统提示不是绝对安全边界，但能影响模型行为优先级。

### 4. ⭐ Zero-shot / Few-shot

**简要总结：**

- Zero-shot：不给示例，直接描述任务
- Few-shot：给少量输入输出示例
- 示例能稳定输出格式和判断标准
- 示例要覆盖关键边界场景

**面试口语：**

Few-shot 的价值是让模型从上下文示例里学习任务模式。比如分类、抽取、格式转换，如果只写规则不稳定，可以给 2 到 3 个典型示例。

```text
示例 1：
输入：我忘记密码了
输出：{"category":"账号"}

示例 2：
输入：什么时候发货
输出：{"category":"物流"}
```

### 5. 🔥 结构化输出

**简要总结：**

- 明确字段名、类型、枚举值
- 尽量让输出可被程序解析
- 复杂任务可用 JSON Schema 或工具调用约束
- 要处理模型输出不合法的兜底

**面试口语：**

AI 应用落地时，结构化输出很重要。自然语言答案适合给人看，但系统集成通常需要 JSON 字段。Prompt 可以约束格式，但强约束场景更推荐使用结构化输出或 Tool Calling。

```json
{
  "intent": "refund",
  "confidence": 0.86,
  "need_human": false
}
```

### 6. 🔥 Prompt 常见问题

**常见问题：**

- 指令模糊，模型自由发挥
- 上下文太长，关键信息被淹没
- 输出格式没有约束，后处理困难
- 示例和规则冲突
- 把安全边界完全寄托在 Prompt 上

**面试口语：**

Prompt 优化不是越长越好，而是要减少歧义。关键信息要靠前、规则不能互相冲突、输出格式要明确。涉及权限和安全的判断不能只靠 Prompt，必须在代码层做校验。
