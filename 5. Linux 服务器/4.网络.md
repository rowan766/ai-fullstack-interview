## 网络排查基础

### 1. 🔥 端口和监听

**简要总结：**

- 服务对外提供能力通常需要监听端口
- `ss -lntp` 查看 TCP 监听
- `netstat` 老系统常见
- 端口被占用会导致服务启动失败
- 监听 `127.0.0.1` 和 `0.0.0.0` 暴露范围不同

**面试口语：**

服务访问不了时，我会先看进程有没有监听端口。比如只监听 `127.0.0.1`，本机能访问，外部机器访问不了；监听 `0.0.0.0` 才表示所有网卡都监听。

**底层原理 / 背后逻辑：**

端口是操作系统给网络应用分配的通信入口。客户端连接时，本质是连接到目标 IP 加端口。服务没有监听、监听地址不对、防火墙拦截，都会表现为访问失败。

### 2. 🔥 常用网络命令

**简要总结：**

- `ping`：测试网络连通性
- `curl`：测试 HTTP 接口
- `telnet` / `nc`：测试端口连通性
- `ss`：查看连接和监听
- `traceroute`：查看路由路径
- `dig` / `nslookup`：查 DNS

**面试口语：**

排查网络问题时，我会分层确认：域名能不能解析、IP 能不能通、端口能不能连、HTTP 返回是否正常。这样能区分 DNS、网络、端口、防火墙和应用问题。

**底层原理 / 背后逻辑：**

一次请求要经过 DNS 解析、建立 TCP 连接、TLS 握手、发送 HTTP 请求、应用处理、返回响应。网络排查就是沿着这条链路逐段确认，而不是只说“接口不通”。

## 连接状态

### 1. 🔥 TCP 连接状态

**简要总结：**

- LISTEN：服务正在监听
- ESTABLISHED：连接已建立
- TIME_WAIT：主动关闭方等待旧包消失
- CLOSE_WAIT：对端关闭，本端还没关闭
- SYN_SENT / SYN_RECV：连接建立过程中

**面试口语：**

如果服务器出现大量 CLOSE_WAIT，通常说明应用没有正确关闭连接；大量 TIME_WAIT 不一定是问题，但如果数量异常，要结合短连接和端口耗尽分析。

**底层原理 / 背后逻辑：**

TCP 是可靠连接协议，需要通过状态机管理连接生命周期。连接关闭后保留 TIME_WAIT，是为了确保旧连接的数据包不会污染新连接，也让最后的 ACK 有机会重传。

### 2. ⭐ 访问不了服务怎么排查

**简要总结：**

- 查域名解析
- 查目标 IP 是否可达
- 查端口是否监听
- 查防火墙和安全组
- 查反向代理配置
- 查应用日志

**面试口语：**

我会按链路排查：先 `dig` 看域名解析，再 `ping` 或 `traceroute` 看网络，再 `nc` 测端口，再看服务器 `ss -lntp`，最后看 Nginx 和应用日志。

**底层原理 / 背后逻辑：**

访问失败可能发生在任何一层。DNS 错了请求到不了正确机器，端口没监听连接建不起来，防火墙拦截包到不了进程，应用异常则可能返回 500。分层排查能快速缩小范围。
