## 日志查看

### 1. 🔥 常用日志命令

**简要总结：**

- `tail -f`：实时查看新增日志
- `less`：分页查看大文件
- `grep`：搜索关键字
- `journalctl`：查看 systemd 服务日志
- `awk` / `sed`：按列或规则处理文本

**面试口语：**

线上排查问题时，我通常先看错误日志和最近请求日志。实时问题用 `tail -f`，历史问题用 `less` 或 `grep` 按时间、trace_id、用户 id 搜索。

**底层原理 / 背后逻辑：**

日志是系统运行过程留下的证据。接口报错、请求超时、权限失败、数据库异常，最终都应该能在日志里找到线索。好的日志能把一次请求从入口追到数据库和外部服务。

### 2. 🔥 grep 排查

**简要总结：**

- 按错误关键字查：ERROR、Exception、Traceback
- 按请求 id 查：trace_id、request_id
- 按时间范围查
- 可结合 `grep -C` 查看上下文

**面试口语：**

如果用户反馈某次请求失败，我会优先拿请求时间、用户 id 或 trace_id 去日志里定位。只看最后几行日志容易漏掉真正的异常上下文。

**底层原理 / 背后逻辑：**

线上请求并发很多，单靠肉眼翻日志效率很低。关键字段能把海量日志缩小到一次请求链路，trace_id 的价值就在于把分散在多个服务里的日志串起来。

## 日志设计

### 1. 🔥 好日志应该包含什么

**简要总结：**

- 时间
- 日志级别
- 服务名和模块
- trace_id / request_id
- 用户或业务 id
- 关键参数和错误堆栈

**面试口语：**

好日志不是打印越多越好，而是要能定位问题。至少要有时间、级别、请求 id、业务 id、错误信息和堆栈。敏感信息不能直接打印。

**底层原理 / 背后逻辑：**

日志的目标是降低排查成本。缺少上下文的日志只会告诉你“出错了”，但不能告诉你哪个用户、哪个接口、哪个参数、哪个下游导致出错。日志字段设计直接影响故障恢复速度。

### 2. ⭐ 日志级别

**简要总结：**

- DEBUG：调试信息
- INFO：关键业务流程
- WARN：异常但可恢复
- ERROR：请求失败或需要关注
- FATAL：严重故障

**面试口语：**

日志级别要区分清楚。正常业务流程用 INFO，异常但能兜底用 WARN，请求失败或需要处理用 ERROR。生产环境通常不会开大量 DEBUG。

**底层原理 / 背后逻辑：**

日志本身也会消耗磁盘和 IO。级别控制可以在不同环境输出不同详细程度，既保证排查能力，也避免生产日志过多拖慢服务或泄露信息。

## 日志系统

### 1. ⭐ 集中式日志

**简要总结：**

- 单机日志不适合多服务排查
- 常见方案：ELK、EFK、Loki
- 日志采集、存储、检索、告警
- trace_id 串联调用链

**面试口语：**

服务多了以后，不能一台台机器 SSH 查日志。需要集中式日志系统，把所有服务日志采集起来，按 trace_id、时间、服务名检索。

**底层原理 / 背后逻辑：**

分布式系统里一次请求可能经过网关、后端、任务队列、模型服务和数据库。日志分散在不同机器上，集中式日志把它们汇总索引，才能快速还原链路。
