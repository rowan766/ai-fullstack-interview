# 性能排查

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 排查方法

### 1. 🔥 服务器变慢怎么排查

**简要总结：**

- 先看整体负载：`uptime`
- 看 CPU 和进程：`top`
- 看内存：`free -h`
- 看磁盘：`df -h`、`iostat`
- 看网络和端口：`ss`
- 看日志和应用错误

**面试口语：**

服务器变慢我会先判断是整体资源问题还是单个应用问题。先看 load、CPU、内存、磁盘、网络，再看具体进程和应用日志，最后结合业务链路定位。

**底层原理 / 背后逻辑：**

服务变慢通常不是单一原因。CPU 打满会排队，内存不足会触发 swap，磁盘 IO 高会让进程等待，网络连接耗尽会让请求进不来。排查要先从系统资源全局视角缩小范围。

### 2. 🔥 load average

**简要总结：**

- load 表示等待 CPU 或不可中断 IO 的任务数量
- 要结合 CPU 核数看
- load 高不一定是 CPU 高
- IO 等待也会让 load 升高

**面试口语：**

load 要结合 CPU 核数看。4 核机器 load 长期 8，就说明任务排队明显。load 高但 CPU 不高时，我会怀疑 IO wait 或不可中断等待。

**底层原理 / 背后逻辑：**

load 不是 CPU 使用率，而是系统中正在运行和等待运行的任务数量。任务可能在等 CPU，也可能在等磁盘 IO。只看 load 不看 CPU、IO，容易误判。

## CPU / 内存 / IO

### 1. 🔥 CPU 高

**简要总结：**

- 用 `top` 找高 CPU 进程
- 区分用户态和系统态
- 可能原因：死循环、复杂计算、频繁 GC、压缩加密、慢 SQL 后应用忙等
- 需要结合应用日志和性能分析

**面试口语：**

CPU 高我会先找哪个进程占用高，再看是不是业务流量上来了、代码死循环、复杂计算或日志异常。后端服务还要结合接口耗时和错误日志判断。

**底层原理 / 背后逻辑：**

CPU 是执行指令的资源。计算密集、序列化、加密压缩、正则回溯、频繁异常处理都会消耗 CPU。CPU 饱和后，请求只能排队等待调度。

### 2. 🔥 内存高

**简要总结：**

- `free -h` 查看内存
- Linux 会把空闲内存用于缓存
- 关注 available 而不是只看 free
- swap 使用高通常会拖慢服务
- 可能原因：内存泄漏、大查询、大对象缓存

**面试口语：**

Linux 里 free 低不一定有问题，因为系统会用内存做缓存。我更关注 available 和 swap。如果 swap 很高，说明内存压力大，服务可能明显变慢。

**底层原理 / 背后逻辑：**

内存比磁盘快得多。Linux 用空闲内存做 page cache 是正常优化。真正危险的是可用内存不足，进程频繁换页到 swap，访问速度从内存级别退化到磁盘级别。

### 3. ⭐ IO wait 高

**简要总结：**

- CPU 等待磁盘 IO
- 数据库慢查询、大日志、大文件读写常见
- `iostat` 看磁盘繁忙
- `iotop` 看哪个进程在读写

**面试口语：**

IO wait 高说明 CPU 很多时间在等磁盘。应用看起来没占满 CPU，但请求还是慢，这时要重点看数据库、日志和文件读写。

**底层原理 / 背后逻辑：**

进程需要的数据不在内存时，就要等磁盘返回。磁盘慢会让大量进程进入等待状态，系统吞吐下降。缓存、索引、批量写入和日志策略都能影响 IO。

## 面试优先级

### 第一优先级

- 🔥 服务器变慢排查顺序
- 🔥 load average
- 🔥 CPU 高排查
- 🔥 内存和 swap
- 🔥 IO wait

### 第二优先级

- ⭐ top / free / df / iostat
- ⭐ 进程级资源定位
- ⭐ 日志结合排查

### 第三优先级

- 💡 perf
- 💡 火焰图
