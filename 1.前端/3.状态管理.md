# 状态管理

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 状态管理基础

### 1. 🔥 为什么需要状态管理

**简要总结：**

- 组件之间需要共享数据
- 多层 props 传递会变复杂
- 业务状态需要统一维护、调试和复用
- 状态变化需要可预测，方便定位问题

**面试口语：**

状态管理主要解决组件之间共享状态和状态变化可维护的问题。简单页面可以用组件内部状态，复杂业务里如果多个组件都依赖同一份数据，就需要把状态抽到统一的 store 中管理。

**底层原理 / 背后逻辑：**

状态管理真正解决的是“数据源”和“更新路径”的问题。组件内部 state 只适合局部交互，一旦多个组件读写同一份数据，如果每个组件都维护副本，就会出现数据不同步、更新链路分散、问题难追踪。全局 store 的价值是把共享状态集中成一个可订阅的数据源：组件读取状态并订阅变化，事件触发 action 修改状态，状态变化后通知依赖它的视图更新。

面试可以这样讲：状态管理不是为了替代组件 state，而是为了让共享状态有单一来源、明确更新入口和可追踪的订阅通知机制。

📌 重点记忆：状态管理不是越早引入越好，而是当状态共享、更新链路、调试成本变高时再引入。

### 2. 🔥 前端状态分类

**简要总结：**

- 本地状态：只影响当前组件，比如弹窗开关、输入框内容
- 共享状态：多个组件都需要，比如用户信息、主题、权限
- 服务端状态：来自接口的数据，比如列表、详情、分页
- URL 状态：路由参数、查询条件、分页参数
- 缓存状态：接口缓存、表单草稿、页面缓存

**面试口语：**

我会先区分状态类型。组件自己的交互状态放组件内部；多个组件共享的状态放 store；接口数据属于服务端状态，通常要考虑缓存、刷新、过期和错误处理；筛选条件这类状态适合放 URL，方便刷新和分享。

⚠️ 注意：不要把所有状态都塞进全局 store，会让状态来源变混乱。

### 3. ⭐ 单向数据流

**简要总结：**

- 状态从统一来源流向视图
- 视图触发事件，再提交状态修改
- 数据变化后视图重新渲染
- 更新路径清晰，便于调试

**面试口语：**

单向数据流就是状态向下流动，事件向上触发。这样数据从哪里来、在哪里改都更清楚，排查问题时能沿着固定链路找。

**底层原理 / 背后逻辑：**

单向数据流的核心是限制“谁能改状态”。如果视图可以随意改多个地方的数据，状态变化会变成网状结构，很难定位来源。单向数据流把链路固定成：视图只负责展示和触发事件，状态修改集中在 action、mutation 或 reducer 中，状态更新后再驱动视图渲染。这样每一次变化都能沿着固定路径回溯。

```txt
state -> view -> action -> update state -> view
```

## Vue 状态管理

### 1. 🔥 Pinia

**简要总结：**

- Vue 官方推荐的新一代状态管理库
- 核心概念：`state`、`getters`、`actions`
- 没有 Vuex 的 `mutation`
- 支持组合式 API
- TypeScript 支持更好

**面试口语：**

Pinia 可以理解成 Vue3 更轻量的全局状态管理方案。它通过 store 管理状态、计算属性和动作，不再强制 mutation，写法更简单，也更适合 TypeScript。

```ts
export const useUserStore = defineStore('user', {
  state: () => ({ name: '', token: '' }),
  getters: {
    isLogin: (state) => Boolean(state.token)
  },
  actions: {
    setToken(token: string) {
      this.token = token
    }
  }
})
```

### 2. 🔥 Pinia 的核心原理

**简要总结：**

- 每个 store 本质是一个响应式对象
- `state` 基于 Vue 响应式系统
- `getters` 类似 `computed`
- `actions` 用来封装同步或异步业务逻辑
- 组件使用 store 后会自动追踪依赖并更新

**面试口语：**

Pinia 底层依赖 Vue3 的响应式系统。store 里的 state 是响应式的，组件读取 state 后会建立依赖，state 改变时组件自动更新。getter 类似 computed，action 用来集中写业务逻辑。

**底层原理 / 背后逻辑：**

Pinia store 本质上是包了一层 Vue 响应式能力的对象。组件在渲染过程中读取 store 的 state，Vue 的依赖收集会把当前组件更新函数记录到这个 state 对应的依赖集合里。之后 action 修改 state 时，响应式系统触发依赖更新，使用这个 state 的组件才会重新渲染。getter 可以理解成绑定在 store 上的 computed，依赖不变时会复用缓存结果。

```vue
<script setup lang="ts">
const userStore = useUserStore()

function login() {
  userStore.setToken('token-value')
}
</script>

<template>
  <button @click="login">{{ userStore.isLogin ? '已登录' : '登录' }}</button>
</template>
```

### 3. ⭐ Pinia 使用场景

**适合放进 Pinia：**

- 登录用户信息
- 权限菜单
- 全局配置
- 多页面共享筛选条件
- 跨组件共享的业务数据

**不适合放进 Pinia：**

- 单个组件内部的 UI 状态
- 临时表单输入
- 和 URL 强相关但没有同步的状态
- 可以从接口随时重新获取的数据副本

📌 重点记忆：全局 store 适合保存“多个地方都关心且生命周期较长”的状态。

### 4. 🔥 Pinia 和 Vuex 区别

**简要总结：**

- Vuex 有 `state`、`getter`、`mutation`、`action`
- Pinia 只有 `state`、`getter`、`action`
- Pinia 没有命名空间概念，每个 store 天然独立
- Pinia 对 TS 更友好
- Pinia 写法更轻量

**面试口语：**

Vuex 更强调严格数据流，mutation 必须同步，方便调试追踪。Pinia 去掉 mutation，允许直接在 action 或组件里修改 state，写法更简单。Vue3 项目一般优先选择 Pinia。

```ts
// Vuex: commit mutation
store.commit('setToken', token)

// Pinia: 直接调用 action
userStore.setToken(token)
```

### 5. ⚠️ Pinia 持久化注意点

**简要总结：**

- 持久化通常存到 `localStorage` 或 `sessionStorage`
- 不要存敏感信息，比如明文 token、密码、权限细节
- 要考虑版本升级后的数据兼容
- 要考虑退出登录时清理状态

**面试口语：**

Pinia 持久化适合保存主题、用户偏好等非敏感数据。登录态可以保存 token，但要结合安全策略，不要把敏感业务数据都放在本地存储里。

```ts
watch(
  () => settingStore.theme,
  (theme) => localStorage.setItem('theme', theme)
)
```

## React 状态管理

### 1. 🔥 React 内置状态方案

**简要总结：**

- `useState`：组件本地状态
- `useReducer`：复杂状态逻辑
- `useContext`：跨层级传值
- `useRef`：保存不触发渲染的可变数据

**面试口语：**

React 不一定一上来就用 Redux。简单状态用 `useState`，复杂状态逻辑用 `useReducer`，跨层级传递用 Context。只有状态共享复杂、更新链路多时才引入外部状态库。

```jsx
const [visible, setVisible] = useState(false)

const [state, dispatch] = useReducer(reducer, { count: 0 })
```

### 2. 🔥 Redux 核心原理

**简要总结：**

- 单一 store 保存状态
- `action` 描述发生了什么
- `reducer` 根据旧状态和 action 返回新状态
- `dispatch` 触发状态更新
- `subscribe` 订阅 store 变化

**面试口语：**

Redux 的核心是单向数据流：组件 dispatch action，reducer 根据 action 计算新 state，store 更新后通知视图重新渲染。reducer 必须是纯函数，不能直接修改原 state。

**底层原理 / 背后逻辑：**

Redux 的 store 内部最关键的是三个东西：当前 state、订阅函数列表、dispatch。`dispatch(action)` 时，Redux 会把旧 state 和 action 交给 reducer，得到新 state，然后遍历 listeners 通知订阅者。React 组件通常通过 React-Redux 订阅 store，并用 selector 取自己关心的数据；当 selector 结果变化时，组件才需要更新。

源码级别可以抓住一句话：Redux 本身不认识 React，它只是一个“可订阅的状态容器”；React-Redux 才负责把 store 变化接到 React 渲染上。

```js
function reducer(state = { count: 0 }, action) {
  if (action.type === 'increment') {
    return { ...state, count: state.count + 1 }
  }

  return state
}
```

📌 重点记忆：Redux = store + action + reducer + dispatch。

### 3. 🔥 Redux 为什么要求 reducer 是纯函数

**简要总结：**

- 相同输入必须得到相同输出
- 不能直接修改原 state
- 不能在 reducer 里写异步请求或副作用
- 方便调试、回放、测试和时间旅行

**面试口语：**

reducer 是根据旧状态和 action 计算新状态的地方。如果它有副作用或直接改原对象，状态变化就不可预测，也不利于调试和性能优化。

```js
// 正确：返回新对象
return { ...state, keyword: action.payload }

// 错误：直接修改原对象
state.keyword = action.payload
return state
```

### 4. ⭐ Redux Toolkit

**简要总结：**

- Redux 官方推荐写法
- 简化 store、reducer、action 创建
- 内置 Immer，可以写“看起来可变”的更新
- 推荐使用 `createSlice`

**面试口语：**

Redux Toolkit 是现在 Redux 的推荐用法，它减少了大量样板代码。通过 `createSlice` 可以同时定义 state、reducer 和 action，内部借助 Immer 保持不可变更新。

```ts
const counterSlice = createSlice({
  name: 'counter',
  initialState: { count: 0 },
  reducers: {
    increment(state) {
      state.count++
    }
  }
})
```

### 5. ⭐ Redux 中间件

**简要总结：**

- 中间件增强 `dispatch`
- 可以在 action 到 reducer 之间插入逻辑
- 常用于异步请求、日志、错误上报
- 常见方案：redux-thunk、redux-saga

**面试口语：**

Redux 中间件本质是对 dispatch 的增强。它可以拦截 action，在 action 到达 reducer 之前做异步请求、日志记录或其他副作用处理。

**底层原理 / 背后逻辑：**

Redux middleware 不是改 reducer，而是用函数组合把原始 `dispatch` 包起来。每个中间件接收 `store`，返回 `next => action => result`，`next(action)` 表示把 action 交给下一个中间件，最后才到真正的 dispatch。redux-thunk 能处理函数 action，就是因为它在中间件层判断 action 如果是函数，就先执行函数，而不是直接交给 reducer。

```js
const logger = (store) => (next) => (action) => {
  console.log('dispatch', action)
  return next(action)
}
```

### 6. ⭐ Zustand

**简要总结：**

- 轻量级 React 状态管理库
- 样板代码少
- 支持 selector 精准订阅状态片段
- 不强制 Redux 的 action / reducer 模式

**面试口语：**

Zustand 比 Redux 更轻量，适合中小型项目或状态逻辑不想写得太重的场景。组件可以通过 selector 只订阅需要的状态，从而减少不必要渲染。

**底层原理 / 背后逻辑：**

Zustand 的 store 可以理解成一个外部状态容器，内部保存 state 和 listeners。组件调用 hook 时传入 selector，Zustand 会订阅 store，并在状态变化后重新执行 selector；如果 selector 返回值没有变化，就不用让组件更新。它不像 Redux 那样强制 action/reducer 流程，所以写法更轻，但大型团队项目要自己约束更新规范。

```ts
const useUserStore = create((set) => ({
  name: '',
  setName: (name: string) => set({ name })
}))

const name = useUserStore((state) => state.name)
```

### 7. ⭐ Jotai

**简要总结：**

- 原子化状态管理库
- 状态由一个个 `atom` 组成
- 组件只订阅自己使用的 atom
- 适合中小型 React 项目和局部共享状态
- 写法接近 `useState`，上手成本低

**面试口语：**

Jotai 的核心是 atom，每个 atom 都是一份独立状态。组件通过 `useAtom` 读取和修改 atom，只有依赖这个 atom 的组件才会更新，所以它比较适合拆得比较细的共享状态。

**底层原理 / 背后逻辑：**

Jotai 的思路是把状态拆成原子。每个 atom 可以是基础值，也可以依赖其他 atom 计算得到。组件读取 atom 时建立订阅关系，更新某个 atom 时，只通知依赖这个 atom 的组件或派生 atom。它和 Redux 最大区别是：Redux 更像一个中心化状态树，Jotai 更像一张 atom 依赖图，更新粒度通常更细。

```tsx
const countAtom = atom(0)

function Counter() {
  const [count, setCount] = useAtom(countAtom)

  return <button onClick={() => setCount(count + 1)}>{count}</button>
}
```

📌 重点记忆：Jotai 是原子化状态管理，关注“把状态拆小”，Redux 更关注“统一数据流和可预测更新”。

## 服务端状态管理

### 1. 🔥 服务端状态和客户端状态区别

**简要总结：**

- 服务端状态来源于接口
- 客户端状态来源于页面交互
- 服务端状态要考虑缓存、过期、重新请求、错误和加载中状态
- 客户端状态更关注 UI 交互和同步逻辑

**面试口语：**

服务端状态不是简单的全局变量，它涉及缓存、重新验证、并发请求、错误处理和 loading。像用户列表、详情页数据这类，更适合用请求缓存库管理，而不是手写全局 store。

```ts
type ServerState = {
  data: User[]
  loading: boolean
  error: Error | null
  updatedAt: number
}
```

### 2. ⭐ TanStack Query / SWR 思路

**简要总结：**

- 按 query key 缓存接口数据
- 自动处理 loading、error、data
- 支持请求去重、缓存过期、后台刷新
- 支持乐观更新和失效刷新

**面试口语：**

TanStack Query 这类库主要解决服务端状态管理问题。它不是替代 Redux 或 Pinia，而是专门管理接口数据的缓存、刷新和同步。

**底层原理 / 背后逻辑：**

TanStack Query 的核心不是全局 store，而是 query cache。每个请求用 `queryKey` 标识，缓存里保存 data、error、loading、更新时间、失效状态和订阅者。多个组件使用同一个 queryKey 时，会共享同一份请求和缓存；缓存过期或被主动 invalidate 后，再触发重新请求。它解决的是“远端数据在前端的缓存一致性”，不是按钮开关、弹窗状态这类本地交互状态。

```tsx
const { data, isLoading, error } = useQuery({
  queryKey: ['users', page],
  queryFn: () => fetchUsers(page)
})
```

📌 重点记忆：客户端状态用 store，服务端状态优先考虑 query cache。

## 状态设计与性能

### 1. 🔥 状态应该放在哪里

**判断原则：**

- 只被一个组件用：放组件内部
- 被父子组件共享：提升到共同父组件
- 跨多个页面共享：放全局 store
- 和 URL 强相关：放路由参数
- 来自接口：考虑请求缓存

**面试口语：**

状态放哪里取决于谁需要它、生命周期多长、是否需要持久化。状态越靠近使用它的地方越好，只有确实共享时才上升到更高层级。

```txt
SearchInput 内部输入中 -> 组件 state
URL 上的 ?keyword=vue -> 路由状态
登录用户信息 -> 全局 store
用户列表接口数据 -> query cache
```

### 2. ⭐ 不可变更新

**简要总结：**

- React 更依赖不可变数据更新
- Vue 依赖响应式代理，但也要避免复杂引用误改
- 不可变更新方便浅比较
- 可以减少难以追踪的副作用

**面试口语：**

不可变更新的价值是让变化更可追踪。尤其在 React 中，浅比较主要看引用是否变化，如果直接修改原对象，可能导致组件不更新或 memo 失效。

**底层原理 / 背后逻辑：**

React 的很多优化建立在浅比较上，浅比较不会递归检查对象内部每个字段，而是看引用有没有变化。如果直接修改原对象，引用仍然相同，`React.memo`、selector 比较或依赖数组都可能认为“没有变化”。不可变更新通过创建新对象表达变化，让框架和工具能用低成本的引用比较发现更新。

```js
setUser({
  ...user,
  profile: {
    ...user.profile,
    city: 'Shanghai'
  }
})
```

### 3. ⭐ 状态管理常见问题

**常见问题：**

- 全局 store 过大
- 接口数据和本地副本不同步
- 状态来源不唯一
- 持久化数据没有版本管理
- Context value 频繁变化导致大范围渲染
- selector 写得太粗导致重复渲染

**面试口语：**

状态管理最怕状态来源混乱。一个数据如果既在接口缓存里，又在全局 store 里，还在组件内部维护一份，就很容易出现不一致。设计时要尽量保证单一数据源。
