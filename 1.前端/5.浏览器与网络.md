# 浏览器与网络

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 浏览器架构与渲染

### 1. 🔥 浏览器主要进程

**简要总结：**

- 浏览器进程：负责地址栏、书签、进程管理等
- 渲染进程：负责页面解析、渲染、JS 执行
- 网络进程：负责网络请求
- GPU 进程：负责图形绘制和合成
- 插件进程：负责插件运行

**面试口语：**

现代浏览器通常是多进程架构。页面渲染主要发生在渲染进程里，网络请求由网络进程处理，GPU 进程负责合成和绘制相关工作。多进程能提升稳定性和安全性。

### 2. 🔥 从输入 URL 到页面展示

**简要流程：**

- 浏览器解析 URL
- DNS 解析域名得到 IP
- 建立 TCP 连接
- HTTPS 还要进行 TLS 握手
- 发送 HTTP 请求
- 服务器返回响应
- 浏览器解析 HTML、CSS、JS
- 构建 DOM、CSSOM、渲染树
- 布局、绘制、合成，最终展示页面

**面试口语：**

输入 URL 后，浏览器先做 DNS 解析，然后建立连接，HTTPS 还要 TLS 握手。拿到 HTML 后开始解析，构建 DOM 和 CSSOM，再生成渲染树，经过布局、绘制和合成显示到页面上。

**底层原理 / 背后逻辑：**

这个题要分成网络链路和渲染链路。网络链路解决“资源怎么拿到”：DNS 找 IP，TCP 建可靠连接，TLS 建加密通道，HTTP 发送请求并接收响应。渲染链路解决“资源怎么变成页面”：HTML 解析成 DOM，CSS 解析成 CSSOM，二者合成渲染树，再布局、绘制、合成。JS 可能阻塞 HTML 解析，CSS 可能阻塞渲染，所以真实优化会关注关键 CSS、脚本加载方式和首屏接口。

📌 重点记忆：网络链路和渲染链路都要说到，别只说 HTTP 请求。

### 3. 🔥 浏览器渲染流程

**简要总结：**

- HTML 解析生成 DOM
- CSS 解析生成 CSSOM
- DOM 和 CSSOM 合成 Render Tree
- Layout 计算位置和大小
- Paint 绘制像素
- Composite 合成图层

**面试口语：**

浏览器渲染页面时，会先解析 HTML 和 CSS，生成 DOM 和 CSSOM，然后合成渲染树，计算布局位置，再绘制并合成到屏幕上。

**底层原理 / 背后逻辑：**

DOM 只描述节点结构，CSSOM 只描述样式规则，浏览器必须把它们结合起来才知道哪些节点可见、每个节点用什么样式。Layout 阶段计算盒模型的位置和尺寸，Paint 阶段生成绘制指令，Composite 阶段把不同图层合成到屏幕。`transform`、`opacity` 动画更容易走合成层，通常比频繁修改宽高位置更流畅。

```html
<p class="title">Hello</p>

<style>
  .title {
    color: red;
  }
</style>
```

上面 HTML 会参与生成 DOM，CSS 会参与生成 CSSOM，二者结合后才知道这个 `p` 应该以红色文字渲染。

### 4. 🔥 重绘和回流

**简要总结：**

- 回流：布局变化，需要重新计算元素位置和大小
- 重绘：外观变化，不影响布局
- 回流一定会触发重绘
- 重绘不一定触发回流

**面试口语：**

回流是元素几何信息变了，比如宽高、位置变化；重绘是颜色、背景这类视觉变化。回流成本通常更高，所以要避免频繁读写布局。

```js
box.style.width = '200px' // 可能触发回流
box.style.color = 'red' // 通常只触发重绘
```

⚠️ 注意：性能优化文件会展开优化手段，这里重点记概念和浏览器流程。

## HTTP 基础

### 1. 🔥 HTTP 和 HTTPS

**简要总结：**

- HTTP 是应用层协议，明文传输
- HTTPS = HTTP + TLS
- HTTPS 提供加密、身份认证、完整性校验
- HTTPS 需要证书

**面试口语：**

HTTP 本身是明文传输，容易被窃听或篡改。HTTPS 在 HTTP 之上加了 TLS，通过加密、证书和完整性校验提升安全性。

```txt
HTTP:  浏览器 -> 明文请求 -> 服务器
HTTPS: 浏览器 -> TLS 加密通道 -> 服务器
```

### 2. 🔥 HTTP 请求和响应

**请求包含：**

- 请求行：方法、路径、协议版本
- 请求头：请求元信息
- 请求体：POST、PUT 等提交的数据

**响应包含：**

- 状态行：协议版本、状态码
- 响应头：响应元信息
- 响应体：返回数据

**面试口语：**

HTTP 请求主要由请求行、请求头和请求体组成；响应由状态行、响应头和响应体组成。前端最常关注方法、状态码、缓存头、Cookie 和响应数据。

```http
GET /api/users?page=1 HTTP/1.1
Host: example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"list":[],"total":0}
```

### 3. 🔥 常见 HTTP 方法

**简要总结：**

- `GET`：获取资源
- `POST`：提交资源
- `PUT`：整体更新资源
- `PATCH`：局部更新资源
- `DELETE`：删除资源
- `OPTIONS`：预检请求或查询支持的方法

**面试口语：**

RESTful 风格里，GET 获取数据，POST 创建数据，PUT 整体更新，PATCH 局部更新，DELETE 删除。跨域复杂请求前，浏览器可能会先发 OPTIONS 预检。

```js
await fetch('/api/users/1', { method: 'PATCH', body: JSON.stringify({ name: 'Tom' }) })
```

### 4. 🔥 常见状态码

**简要总结：**

- `200`：请求成功
- `201`：创建成功
- `204`：成功但无响应体
- `301`：永久重定向
- `302`：临时重定向
- `304`：协商缓存命中
- `400`：请求参数错误
- `401`：未认证
- `403`：无权限
- `404`：资源不存在
- `500`：服务端错误
- `502`：网关错误
- `504`：网关超时

**面试口语：**

状态码可以按类别记：2xx 成功，3xx 重定向，4xx 客户端问题，5xx 服务端问题。前端排查问题时，401 看登录态，403 看权限，304 看缓存，502/504 看网关或后端服务。

```js
if (response.status === 401) {
  redirectToLogin()
}
```

### 5. ⭐ HTTP 1.1 / HTTP 2 / HTTP 3

**简要总结：**

- HTTP 1.1 支持持久连接，但存在队头阻塞
- HTTP 2 基于二进制分帧，支持多路复用、头部压缩
- HTTP 3 基于 QUIC，底层使用 UDP，减少 TCP 层队头阻塞

**面试口语：**

HTTP 2 最大特点是多路复用，一个连接上可以并发多个请求。HTTP 3 基于 QUIC，建立连接更快，也能减少 TCP 队头阻塞带来的影响。

**底层原理 / 背后逻辑：**

HTTP/1.1 虽然支持 keep-alive，但一个连接上响应仍然容易按顺序受阻，所以浏览器通常会开多个 TCP 连接并发请求。HTTP/2 把数据拆成二进制帧，不同请求属于不同 stream，多个 stream 可以复用同一个 TCP 连接传输，减少连接成本和应用层队头阻塞。但 HTTP/2 仍跑在 TCP 上，如果 TCP 层丢包，整个连接的数据都可能等待重传。HTTP/3 基于 QUIC/UDP，把多路复用放到 QUIC 层，能减少 TCP 层队头阻塞影响。

```txt
HTTP/1.1: 请求 A 完成后，同连接里的请求 B 才更容易继续
HTTP/2:   请求 A、B、C 可以在同一个连接上并发传输
```

## DNS、TCP 和 TLS

### 1. ⭐ DNS

**简要总结：**

- DNS 把域名解析成 IP
- 浏览器、系统、路由器、运营商 DNS 都可能有缓存
- DNS 解析耗时会影响首屏
- 可通过 DNS 预解析优化关键域名

**面试口语：**

DNS 的作用是把域名转换成 IP。浏览器请求资源前通常要先解析域名，DNS 慢会影响请求开始时间，所以关键第三方域名可以做 DNS 预解析。

**底层原理 / 背后逻辑：**

DNS 解析不是每次都直接访问权威 DNS，它有多级缓存：浏览器缓存、系统缓存、路由器或本地 DNS 缓存、运营商递归 DNS 缓存。命中缓存时很快，未命中才会递归或迭代查询。DNS 预解析的价值是提前把关键域名解析好，让真正请求资源时少等一段解析时间。

```html
<link rel="dns-prefetch" href="//cdn.example.com" />
```

### 2. 🔥 TCP 三次握手

**简要总结：**

- 第一次：客户端发送 SYN
- 第二次：服务端返回 SYN + ACK
- 第三次：客户端返回 ACK
- 目的是确认双方收发能力正常

**面试口语：**

TCP 三次握手是为了建立可靠连接，确认客户端和服务端双方的发送和接收能力都正常。连接建立后才能传输 HTTP 数据。

```txt
客户端 -> SYN        -> 服务端
客户端 <- SYN + ACK  <- 服务端
客户端 -> ACK        -> 服务端
```

### 3. ⭐ TCP 四次挥手

**简要总结：**

- 主动关闭方发送 FIN
- 被动关闭方返回 ACK
- 被动关闭方发送 FIN
- 主动关闭方返回 ACK
- TCP 是全双工连接，所以关闭需要双方各自确认

**面试口语：**

四次挥手是因为 TCP 两端都能独立发送数据。一方说我不发了，另一方确认；另一方也准备关闭后再发 FIN，最后对方确认。

```txt
A -> FIN -> B
A <- ACK <- B
A <- FIN <- B
A -> ACK -> B
```

### 4. 🔥 TLS 握手

**简要总结：**

- 协商加密算法
- 服务端发送证书
- 客户端校验证书
- 协商会话密钥
- 后续使用对称加密传输数据

**面试口语：**

HTTPS 的 TLS 握手主要是为了验证服务端身份，并协商后续通信使用的密钥。真正传输业务数据时通常使用对称加密，因为性能更好。

```txt
客户端发送支持的 TLS 版本和加密套件
服务端返回证书并协商加密参数
双方生成会话密钥，后续用对称加密通信
```

## 缓存

### 1. 🔥 强缓存

**简要总结：**

- 命中强缓存时不请求服务器
- 相关响应头：`Cache-Control`、`Expires`
- `Cache-Control` 优先级高于 `Expires`
- 常见指令：`max-age`、`no-cache`、`no-store`

**面试口语：**

强缓存命中时，浏览器直接用本地缓存，不会向服务器发请求。现代项目主要看 `Cache-Control`，比如 `max-age` 表示缓存有效时间。

**底层原理 / 背后逻辑：**

强缓存判断发生在浏览器本地。浏览器先看缓存记录是否过期，如果 `Cache-Control: max-age` 还在有效期内，就直接从内存缓存或磁盘缓存读取资源，不会发网络请求。`no-cache` 不是不缓存，而是每次使用前要向服务器验证；`no-store` 才是不存储缓存。

```http
Cache-Control: public, max-age=31536000, immutable
```

### 2. 🔥 协商缓存

**简要总结：**

- 强缓存失效后向服务器确认资源是否变化
- 命中协商缓存返回 `304`
- 相关响应头：`ETag`、`Last-Modified`
- `ETag` 通常优先级更高

**面试口语：**

协商缓存会向服务器发请求，但服务器如果判断资源没变，就返回 304，让浏览器继续使用本地缓存。这样省掉响应体传输。

**底层原理 / 背后逻辑：**

协商缓存的核心是“带条件的请求”。浏览器把上次响应里的 `ETag` 或 `Last-Modified` 带回服务器，服务器对比资源当前版本。如果没变，返回 `304` 和很小的响应头，不返回响应体；如果变了，返回 `200` 和新资源。`ETag` 通常比 `Last-Modified` 更精确，因为它可以基于内容 hash 或版本生成，不受秒级时间精度影响。

```http
If-None-Match: "app.abc123.js"

HTTP/1.1 304 Not Modified
ETag: "app.abc123.js"
```

📌 重点记忆：强缓存不发请求，协商缓存会发请求。

### 3. ⭐ 前端静态资源缓存策略

**简要总结：**

- HTML 不建议长时间强缓存
- JS / CSS 文件名带 hash，可以设置长缓存
- 图片、字体等静态资源可长缓存
- 发布时通过 hash 变更让用户拿到新资源

**面试口语：**

前端通常让 HTML 保持较短缓存或协商缓存，确保能拿到最新资源入口。带 hash 的 JS 和 CSS 可以长缓存，因为内容变化后文件名会变。

```txt
index.html          -> no-cache
assets/app.a1b2.js  -> max-age=31536000
```

## 跨域与认证

### 1. 🔥 同源策略

**简要总结：**

- 同源要求协议、域名、端口都相同
- 浏览器出于安全原因限制跨源访问
- 跨域是浏览器限制，不是服务端一定收不到请求
- 主要限制 JS 读取跨域响应

**面试口语：**

同源策略是浏览器安全机制，协议、域名、端口有一个不同就算跨域。跨域时请求可能已经到服务端了，但浏览器不允许前端读取响应。

**底层原理 / 背后逻辑：**

同源策略限制的是浏览器里的脚本读取跨源响应，不是限制网络请求一定发不出去。比如表单提交、图片加载可以跨域，但 JS 不能随便读取另一个源的接口数据。CORS 是浏览器和服务器约定的一套放行机制：服务器通过响应头声明允许哪些源读取响应，浏览器检查通过后才把数据交给前端代码。

```txt
https://a.com:443 和 https://a.com:443   同源
https://a.com:443 和 http://a.com:80     不同源
https://a.com:443 和 https://api.a.com   不同源
```

### 2. 🔥 CORS

**简要总结：**

- CORS 是服务端通过响应头允许跨域
- 常见头：`Access-Control-Allow-Origin`
- 携带 Cookie 时需要 `Access-Control-Allow-Credentials`
- 复杂请求会先发送 OPTIONS 预检

**面试口语：**

CORS 的核心是服务端明确告诉浏览器哪些源可以访问。前端不能单方面解决 CORS，必须后端或网关返回正确响应头。

**底层原理 / 背后逻辑：**

简单请求会直接发出，浏览器收到响应后检查 `Access-Control-Allow-Origin`。复杂请求会先发 `OPTIONS` 预检，询问服务器是否允许这个方法、请求头和来源；预检通过后才发送真实请求。携带 Cookie 时，前端要设置 `credentials: 'include'`，服务端也要返回 `Access-Control-Allow-Credentials: true`，并且 `Allow-Origin` 不能是 `*`。

```http
Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Credentials: true
```

⚠️ 注意：`credentials: 'include'` 时，`Access-Control-Allow-Origin` 不能是 `*`。

### 3. ⭐ Cookie / Session / Token

**简要总结：**

- Cookie 是浏览器存储并自动随请求携带的数据
- Session 通常保存在服务端，客户端只存 session id
- Token 通常由客户端保存，手动放到请求头
- JWT 是常见 Token 格式

**面试口语：**

Cookie 更适合浏览器自动携带，Session 把登录状态存在服务端，Token 更适合前后端分离和多端场景。选择时要考虑安全、跨域、过期和刷新机制。

```js
await fetch('/api/profile', {
  headers: { Authorization: `Bearer ${token}` }
})
```

### 4. ⭐ Cookie 属性

**简要总结：**

- `HttpOnly`：禁止 JS 读取，降低 XSS 窃取风险
- `Secure`：只在 HTTPS 下发送
- `SameSite`：限制跨站携带，降低 CSRF 风险
- `Max-Age` / `Expires`：控制过期时间
- `Domain` / `Path`：控制作用范围

**面试口语：**

Cookie 安全重点是 `HttpOnly`、`Secure` 和 `SameSite`。登录态 Cookie 通常要开启 HttpOnly 和 Secure，并根据跨站需求设置 SameSite。

**底层原理 / 背后逻辑：**

Cookie 会被浏览器按 Domain、Path、Secure、SameSite 等规则自动携带。`HttpOnly` 让 JS 读不到 Cookie，主要降低 XSS 窃取风险；`SameSite` 控制跨站请求是否携带 Cookie，主要降低 CSRF 风险；`Secure` 要求只在 HTTPS 下发送，避免明文链路泄露。它们解决的问题不同，不能互相替代。

```http
Set-Cookie: sid=abc; HttpOnly; Secure; SameSite=Lax; Path=/
```

## 实时通信

### 1. ⭐ WebSocket

**简要总结：**

- WebSocket 是全双工长连接协议
- 建立连接时先通过 HTTP Upgrade 升级
- 适合聊天、实时通知、实时大屏、协同编辑
- 需要处理心跳、断线重连、消息顺序和鉴权

**面试口语：**

WebSocket 建立后，客户端和服务端都可以主动发送消息，适合实时性要求高的场景。实际项目里要考虑心跳保活、断线重连和服务端连接管理。

**底层原理 / 背后逻辑：**

WebSocket 不是普通 HTTP 轮询，它先通过 HTTP 请求发起 `Upgrade: websocket`，服务端同意后协议升级为长连接。连接建立后，双方可以在同一条 TCP 连接上互相推送消息，减少反复建立请求的开销。生产中必须做心跳检测，因为中间代理、网络切换或服务重启都可能让连接悄悄断开。

```js
const socket = new WebSocket('wss://example.com/chat')

socket.onmessage = (event) => {
  console.log(JSON.parse(event.data))
}

socket.send(JSON.stringify({ text: 'hello' }))
```

### 2. 💡 SSE 和轮询

**简要总结：**

- 轮询：客户端定时请求服务端
- 长轮询：服务端有数据或超时才返回
- SSE：服务端向浏览器单向推送文本事件
- WebSocket：双向通信

**面试口语：**

如果只是服务端单向推送，可以考虑 SSE；如果需要双向实时通信，用 WebSocket 更合适。简单低频场景用轮询也可以。

```js
const source = new EventSource('/api/notice-stream')

source.onmessage = (event) => {
  console.log(event.data)
}
```
