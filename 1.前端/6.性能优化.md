# 性能优化

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 性能优化基础

### 1. 🔥 前端性能优化目标

**简要总结：**

- 加载更快：减少白屏和首屏时间
- 交互更快：减少卡顿和长任务
- 渲染更稳：减少布局抖动
- 资源更小：减少 JS、CSS、图片体积
- 体验更好：让用户更快看到可用内容

**面试口语：**

前端性能优化不只是让资源变小，还包括首屏速度、交互响应、渲染流畅度和线上稳定性。优化前要先确定指标，再定位瓶颈。

**底层原理 / 背后逻辑：**

性能优化的核心不是套招，而是减少关键路径上的等待和主线程工作。加载慢通常来自网络传输、资源体积、连接建立、接口耗时；交互卡通常来自主线程长任务、频繁渲染、同步布局；页面乱跳通常来自资源尺寸不稳定。先用指标判断问题类型，再找对应链路，优化才有方向。

📌 重点记忆：先度量，再优化。

### 2. 🔥 常见性能指标

**简要总结：**

- FCP：首次内容绘制
- LCP：最大内容绘制，衡量主要内容加载速度
- CLS：累计布局偏移，衡量视觉稳定性
- INP：交互到下一次绘制，衡量交互响应
- TTFB：首字节时间
- TTI：页面可交互时间

**面试口语：**

性能指标里比较重要的是 Web Vitals。LCP 看主要内容什么时候出现，CLS 看页面是否乱跳，INP 看用户交互后页面响应快不快。

**底层原理 / 背后逻辑：**

LCP 受资源加载、接口返回、图片解码、渲染阻塞影响；CLS 受图片无尺寸、广告插入、字体切换、异步内容撑开布局影响；INP 关注交互发生后到下一帧绘制之间的耗时，主线程如果被大 JS、复杂渲染或同步布局占满，INP 就会变差。面试讲指标时，要把指标和底层瓶颈对应起来。

```js
new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    console.log(entry.name, entry.startTime)
  })
}).observe({ type: 'largest-contentful-paint', buffered: true })
```

### 3. ⭐ 性能优化流程

**简要总结：**

- 明确目标：首屏慢、交互卡、包体大还是接口慢
- 使用工具定位瓶颈
- 针对瓶颈优化
- 对比优化前后数据
- 接入监控持续观察

**面试口语：**

我不会一上来就盲目优化，而是先用 Lighthouse、Performance、Network、监控数据看瓶颈在哪里，再针对资源、接口、渲染或 JS 执行做优化。

## 加载性能优化

### 1. 🔥 减少资源体积

**简要总结：**

- JS / CSS 压缩
- 移除无用代码
- Tree Shaking
- 组件库按需引入
- 图片压缩和格式优化
- 避免引入过大的第三方库

**面试口语：**

资源体积越大，下载、解析和执行成本越高。常见做法是压缩代码、移除无用依赖、开启 Tree Shaking、组件库按需加载，并对图片做压缩和格式转换。

**底层原理 / 背后逻辑：**

JS 的成本不只是下载，还有解析、编译和执行。一个大 bundle 即使被 gzip 压小，浏览器解压后仍要在主线程解析执行，所以首屏 JS 过大会同时影响加载和交互。减少资源体积的本质是减少网络字节数和主线程工作量。

```js
// 按需导入，避免把整个工具库都打进首屏包
import debounce from 'lodash-es/debounce'
```

### 2. 🔥 代码分割和懒加载

**简要总结：**

- 路由懒加载
- 组件懒加载
- 第三方库拆包
- 首屏只加载必要资源
- 非关键资源延后加载

**面试口语：**

代码分割的核心是不要让用户一进来就下载整个应用。可以按路由拆包，访问到对应页面时再加载对应代码，从而降低首屏 JS 体积。

```js
const routes = [
  { path: '/order', component: () => import('./pages/OrderPage.vue') }
]
```

### 3. ⭐ CDN 和缓存

**简要总结：**

- CDN 就近分发静态资源
- hash 文件可以设置长期缓存
- HTML 缓存时间不宜太长
- 合理缓存能减少重复下载

**面试口语：**

CDN 可以让用户从更近的节点加载资源，缓存可以避免重复下载。前端通常让带 hash 的静态资源长缓存，HTML 保持较短缓存或协商缓存。

```http
Cache-Control: public, max-age=31536000, immutable
```

### 4. ⭐ 资源加载优先级

**简要总结：**

- 关键 CSS 优先加载
- 非关键 JS 使用 `defer` 或 `async`
- 图片懒加载
- 关键资源可用 preload
- 第三方资源尽量不要阻塞主流程

**面试口语：**

加载优化要区分关键资源和非关键资源。首屏必需的 CSS 和核心 JS 优先加载，非首屏图片和不影响首屏的脚本可以延后。

**底层原理 / 背后逻辑：**

浏览器解析 HTML 时会发现 CSS、JS、图片、字体等资源，但它们对首屏的重要性不同。关键 CSS 会影响首屏渲染，应该尽早加载；普通脚本如果阻塞 HTML 解析，会推迟 DOM 构建；非首屏图片提前加载会抢占带宽。`preload` 是提前告诉浏览器“这个资源马上要用”，`defer` 是让脚本等 HTML 解析完再执行。

```html
<link rel="preload" href="/assets/main.css" as="style" />
<script src="/analytics.js" defer></script>
```

### 5. ⭐ 图片优化

**简要总结：**

- 使用合适尺寸，避免大图缩小显示
- 使用 WebP、AVIF 等现代格式
- 图片懒加载
- 响应式图片适配不同屏幕
- 图标优先使用 SVG 或 icon font

**面试口语：**

图片通常是页面体积大头。优化图片要控制尺寸、压缩体积、选择合适格式，并对非首屏图片做懒加载。

```html
<img
  src="/banner-800.webp"
  srcset="/banner-400.webp 400w, /banner-800.webp 800w"
  sizes="(max-width: 600px) 400px, 800px"
  loading="lazy"
  alt="活动封面"
/>
```

## 渲染性能优化

### 1. 🔥 减少重绘和回流

**简要总结：**

- 避免频繁修改布局属性
- 批量修改 DOM
- 使用 class 统一切换样式
- 动画优先使用 `transform` 和 `opacity`
- 避免强制同步布局

**面试口语：**

回流成本比重绘高。实际优化时，要减少频繁读写布局，比如不要在循环里反复读取 `offsetWidth` 后又修改样式。动画优先用 `transform` 和 `opacity`。

**底层原理 / 背后逻辑：**

浏览器为了性能会延迟批量计算样式和布局。但如果 JS 先修改布局属性，又立刻读取 `offsetWidth`、`getBoundingClientRect()` 这类布局信息，浏览器必须提前把队列里的样式和布局计算做完，这叫强制同步布局。频繁读写交错会让布局反复刷新，造成卡顿。

```js
// 先读后写，避免在循环里反复触发布局计算
const width = box.offsetWidth
box.classList.add(width > 300 ? 'wide' : 'narrow')
```

### 2. 🔥 长列表优化

**简要总结：**

- 虚拟列表只渲染可视区域
- 分页或无限滚动减少一次性 DOM 数量
- 列表项组件尽量轻量
- 保持稳定 key

**面试口语：**

长列表最大问题是 DOM 节点太多，渲染和更新都很慢。虚拟列表只渲染可视区域附近的元素，可以显著降低 DOM 数量。

**底层原理 / 背后逻辑：**

虚拟列表不是让数据变少，而是让真实 DOM 变少。它根据滚动距离、容器高度、单项高度计算当前可见范围，只渲染这一段数据；同时用一个占位高度撑开滚动条，让用户感觉列表完整存在。这样把上万 DOM 节点降到几十个，布局、绘制和框架 Diff 成本都会下降。

```js
const start = Math.floor(scrollTop / itemHeight)
const end = start + visibleCount
const visibleList = list.slice(start, end)
```

### 3. ⭐ 动画优化

**简要总结：**

- 使用 `requestAnimationFrame`
- 使用 `transform`、`opacity`
- 避免同时做大量布局变化
- 控制动画元素数量
- 必要时使用 CSS 动画替代 JS 动画

**面试口语：**

动画优化核心是让浏览器更容易合成。`transform` 和 `opacity` 通常可以走合成线程，比频繁修改 `top`、`left` 更稳定。

```css
.panel {
  transition: transform 0.2s;
}

.panel.open {
  transform: translateX(0);
}
```

### 4. ⭐ 防抖和节流

**简要总结：**

- 防抖：连续触发后只执行最后一次
- 节流：固定时间内最多执行一次
- 适合输入搜索、滚动、resize、拖拽等高频事件

**面试口语：**

防抖适合等用户停止操作后再执行，比如搜索框输入；节流适合控制执行频率，比如滚动监听。它们都能减少高频事件造成的性能压力。

```js
const onSearch = debounce((keyword) => {
  fetch(`/api/search?q=${keyword}`)
}, 300)
```

## JS 执行性能优化

### 1. 🔥 减少主线程阻塞

**简要总结：**

- 避免长任务阻塞 UI
- 大任务拆分成小任务
- 非关键逻辑延后执行
- 大计算可放到 Web Worker
- 减少不必要的同步计算

**面试口语：**

浏览器主线程既要执行 JS，也要处理渲染和用户交互。如果 JS 长时间占用主线程，页面就会卡顿。可以拆分任务、延后执行或用 Web Worker 处理大计算。

**底层原理 / 背后逻辑：**

页面响应依赖主线程及时让出执行权。一个超过 50ms 的长任务会阻塞输入事件处理、样式计算、布局和绘制。拆分任务的本质是把一次长时间同步执行拆成多段，让浏览器有机会在中间处理用户输入和渲染帧。Web Worker 则是把纯计算搬到后台线程，但 DOM 操作仍必须回到主线程。

```js
function runChunk(tasks) {
  requestIdleCallback(() => {
    tasks.splice(0, 20).forEach((task) => task())
    if (tasks.length) runChunk(tasks)
  })
}
```

### 2. ⭐ Web Worker

**简要总结：**

- 适合大计算、文件解析、数据处理
- 不阻塞主线程
- 通过消息通信
- 不能直接操作 DOM

**面试口语：**

Web Worker 适合把耗时计算放到后台线程，避免阻塞 UI。但它不能直接访问 DOM，所以需要通过 `postMessage` 和主线程通信。

```js
// main.js
const worker = new Worker('/worker.js')
worker.postMessage(100000)
worker.onmessage = (event) => console.log(event.data)

// worker.js
self.onmessage = (event) => {
  self.postMessage(expensiveCount(event.data))
}
```

### 3. ⭐ 内存优化

**简要总结：**

- 及时清理定时器
- 取消事件监听
- 避免全局变量长期持有大对象
- 避免闭包持有无用引用
- 组件卸载时清理副作用

**面试口语：**

前端内存泄漏常见原因是定时器没清、事件没解绑、全局缓存持有对象、组件卸载后异步回调还在引用旧数据。框架项目里要特别注意组件卸载清理。

```js
useEffect(() => {
  window.addEventListener('resize', onResize)

  return () => {
    window.removeEventListener('resize', onResize)
  }
}, [])
```

## 框架性能优化

### 1. 🔥 Vue 性能优化

**简要总结：**

- 合理使用 `computed`
- 避免不必要的深层响应式
- 使用 `v-once`、`v-memo`
- 路由懒加载
- 大列表虚拟滚动
- 合理拆分组件

**面试口语：**

Vue 优化重点是减少不必要响应式追踪和组件更新。比如稳定数据可以不用做深层响应式，派生数据用 computed 缓存，大列表用虚拟列表。

**底层原理 / 背后逻辑：**

Vue 的更新来自响应式依赖触发，所以优化重点是减少依赖数量和更新范围。大对象如果不需要深层响应式，可以用 `shallowRef`、`markRaw` 降低代理和追踪成本；稳定内容用 `v-once` 跳过后续更新；部分列表项用 `v-memo` 在依赖不变时跳过 patch。核心思路是让响应式系统少追踪、让 Diff 少比较。

```vue
<template>
  <p v-once>{{ appName }}</p>
  <ItemRow v-for="item in list" :key="item.id" v-memo="[item.id, item.status]" />
</template>
```

### 2. 🔥 React 性能优化

**简要总结：**

- 合理拆分组件
- 降低 state 层级
- 使用 `React.memo`
- 使用 `useMemo`、`useCallback`
- 避免 Context 过大
- 大列表虚拟滚动

**面试口语：**

React 性能优化重点是控制渲染范围。父组件更新时子组件可能跟着执行，所以要拆组件、稳定 props 引用、合理使用 memo，并避免把频繁变化的状态放得太高。

**底层原理 / 背后逻辑：**

React 的更新模型是 state 变化后重新执行组件函数，默认子组件也会跟着进入渲染计算。真实 DOM 不一定更新，但函数执行、虚拟 DOM 创建和 Diff 也有成本。`React.memo` 通过浅比较 props 跳过子组件渲染，`useMemo/useCallback` 用来稳定传给子组件的值和函数引用。优化关键不是到处加 memo，而是让变化影响尽量小。

```jsx
const UserRow = React.memo(function UserRow({ user, onSelect }) {
  return <button onClick={() => onSelect(user.id)}>{user.name}</button>
})
```

⚠️ 注意：框架优化不要无脑加 memo，先确认是否真的存在重复渲染问题。

## 接口与网络性能

### 1. 🔥 接口请求优化

**简要总结：**

- 合并请求或减少无效请求
- 请求缓存
- 请求去重
- 分页加载
- 并发控制
- 超时和重试

**面试口语：**

接口优化要减少没必要的请求，同时提升请求稳定性。比如相同请求可以去重，列表数据分页加载，批量任务做并发控制，失败请求设置合理重试。

**底层原理 / 背后逻辑：**

接口性能不仅看单个请求快不快，还看请求数量、并发压力和重复请求。请求去重是用相同 key 复用同一个 pending Promise；缓存是用 key 保存已完成响应并设置过期策略；并发控制是限制同时进行的请求数量，避免浏览器连接、网关或后端被瞬时打满。重试要加次数和退避时间，否则失败时可能放大流量。

```js
const pending = new Map()

function requestOnce(url) {
  if (!pending.has(url)) {
    pending.set(url, fetch(url).finally(() => pending.delete(url)))
  }

  return pending.get(url)
}
```

### 2. ⭐ 首屏接口优化

**简要总结：**

- 首屏关键接口优先
- 非关键接口延后
- 使用骨架屏改善感知体验
- SSR / SSG 可提前生成内容
- BFF 可以减少前端聚合成本

**面试口语：**

首屏优化要优先保证关键数据回来。非关键接口可以延后，页面可以用骨架屏减少白屏感。如果接口聚合太重，可以通过 BFF 在服务端聚合。

```js
const mainData = await fetch('/api/home-main')

requestIdleCallback(() => {
  fetch('/api/home-recommend')
})
```

## 监控与排查

### 1. 🔥 性能分析工具

**常用工具：**

- Chrome DevTools Performance
- Chrome DevTools Network
- Lighthouse
- Web Vitals
- Coverage
- Bundle Analyzer

**面试口语：**

性能排查时，Network 看资源加载和接口耗时，Performance 看主线程和渲染，Lighthouse 给整体建议，Bundle Analyzer 用来看包体积构成。

### 2. ⭐ 线上性能监控

**简要总结：**

- 采集 Web Vitals
- 采集接口耗时和错误率
- 采集 JS 错误和资源加载失败
- 采集白屏、卡顿、长任务
- 按页面、浏览器、地区、版本聚合分析

**面试口语：**

本地优化只能解决部分问题，线上还要靠监控。通过采集 Web Vitals、接口耗时、错误率和长任务，才能知道真实用户的性能体验。

**底层原理 / 背后逻辑：**

线上监控的价值是拿到真实用户环境的数据。本地 Lighthouse 只能代表当前机器和网络，线上用户的设备、地区、浏览器、缓存状态都不同。监控通常会采样上报指标，并带上页面、版本、设备、网络、地区等维度，后续才能判断是某个版本退化、某类设备卡顿，还是某个地区接口慢。

```js
window.addEventListener('error', (event) => {
  report({ type: 'js_error', message: event.message })
})
```

### 3. ⭐ 性能优化面试回答模板

**回答思路：**

- 先说发现问题的指标
- 再说定位工具和瓶颈
- 然后说采取的优化手段
- 最后说优化后的数据变化

**面试口语：**

讲性能优化项目时，不要只说“做了懒加载、压缩资源”。更好的说法是：哪个指标不好，用什么工具定位到什么问题，做了什么优化，最后指标提升了多少。
