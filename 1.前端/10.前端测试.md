# 前端测试

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 测试基础

### 1. 🔥 为什么需要前端测试

**简要总结：**

- 提前发现回归问题
- 保证核心业务流程稳定
- 支撑重构和多人协作
- 降低只靠人工测试的成本
- 在 CI 中形成质量门禁

**面试口语：**

前端测试的价值不是追求 100% 覆盖率，而是保证关键逻辑和核心流程不被改坏。尤其是组件复用多、业务链路长、多人协作时，测试可以让重构更有底气。

**底层原理 / 背后逻辑：**

测试本质是把“预期行为”固化成可重复执行的检查。人工测试容易漏场景，而且每次回归成本高；自动化测试把输入、操作和断言写成代码，改动后可以快速验证旧行为是否还成立。面试要强调：测试不是替代人工，而是把高频、稳定、核心的验证自动化。

### 2. 🔥 测试金字塔

**简要总结：**

- 单元测试：数量最多，验证函数或小模块
- 组件测试：验证组件渲染和交互
- 集成测试：验证多个模块协作
- E2E 测试：验证真实用户流程
- 越靠上越接近用户，成本也越高

**面试口语：**

测试金字塔的意思是底层单元测试多一些，因为快、稳定、成本低；上层 E2E 少一些，因为它更接近真实用户，但速度慢、维护成本高。核心链路可以用 E2E 保底，复杂逻辑用单元测试覆盖。

**底层原理 / 背后逻辑：**

不同测试层级的取舍是速度、稳定性和真实性的平衡。单元测试隔离依赖，定位问题快；E2E 测试启动浏览器，覆盖链路长，但失败原因可能来自网络、环境、数据、UI 变化。健康的测试体系通常不是只选一种，而是按风险分层。

```txt
E2E 测试        少量，覆盖核心链路
集成 / 组件测试  适量，覆盖模块协作和交互
单元测试        较多，覆盖工具函数和复杂逻辑
```

### 3. 🔥 单元测试

**简要总结：**

- 测试一个函数、类或模块的独立行为
- 常用工具：Vitest、Jest
- 适合工具函数、数据转换、权限判断、复杂计算
- 要关注输入、输出和边界条件

**面试口语：**

单元测试适合测纯函数和复杂逻辑，比如金额计算、表单校验、权限判断。因为它不依赖真实浏览器和接口，所以执行快、定位问题也快。

```ts
// sum.ts
export function sum(a: number, b: number) {
  return a + b
}
```

```ts
// sum.test.ts
import { expect, test } from 'vitest'
import { sum } from './sum'

test('adds two numbers', () => {
  expect(sum(1, 2)).toBe(3)
})
```

**底层原理 / 背后逻辑：**

单元测试的核心是 AAA：Arrange 准备数据，Act 执行被测逻辑，Assert 断言结果。好的单元测试应该稳定、快速、输入输出清晰。越纯的函数越容易测，因为它不依赖外部时间、网络、DOM 或全局状态。

### 4. ⭐ 组件测试

**简要总结：**

- 测试组件是否正确渲染
- 测试用户交互后 UI 是否变化
- 常用工具：Testing Library、Vue Test Utils
- 更关注用户能看到和操作的行为

**面试口语：**

组件测试不是测组件内部变量名，而是测用户行为。比如按钮能不能点击，输入后列表是否过滤，接口 loading 是否展示。Testing Library 的理念就是尽量像用户一样查找元素和触发事件。

```tsx
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'

test('increments count', async () => {
  render(<Counter />)

  await userEvent.click(screen.getByRole('button', { name: '0' }))

  expect(screen.getByRole('button', { name: '1' })).toBeInTheDocument()
})
```

**底层原理 / 背后逻辑：**

组件测试通常运行在 jsdom 或真实浏览器环境里。jsdom 模拟 DOM API，但不做真实布局和绘制，所以适合测结构和交互，不适合测像素级布局。断言时优先从用户视角查找元素，可以减少测试和组件内部实现的耦合。

### 5. ⭐ Storybook

**简要总结：**

- Storybook 是组件隔离开发和文档工具
- 可以为组件编写不同状态的 `stories`
- 方便设计、前端、测试一起查看组件状态
- 可结合交互测试、可访问性测试、视觉回归测试
- 适合组件库、中后台通用组件、设计系统

**面试口语：**

Storybook 不是单纯的单元测试工具，它更像一个组件工作台。我们可以把按钮、弹窗、表格这些组件在不同 props、不同状态下单独展示出来，方便开发调试、评审 UI，也能配合测试工具做交互和视觉回归。

```tsx
// Button.stories.tsx
import type { Meta, StoryObj } from '@storybook/react'
import { Button } from './Button'

const meta: Meta<typeof Button> = {
  title: 'Components/Button',
  component: Button
}

export default meta

export const Primary: StoryObj<typeof Button> = {
  args: {
    type: 'primary',
    children: '提交'
  }
}

export const Disabled: StoryObj<typeof Button> = {
  args: {
    disabled: true,
    children: '不可点击'
  }
}
```

**底层原理 / 背后逻辑：**

Storybook 的核心是把组件从业务页面里隔离出来运行。每个 story 本质上都是组件的一种输入状态，比如不同 props、不同插槽、不同 loading/error 状态。这样可以在不启动完整业务流程的情况下验证组件展示是否正确。它和组件测试的区别是：组件测试更强调自动断言，Storybook 更强调组件状态沉淀、可视化调试和跨角色协作。

**常见追问：Storybook 和测试是什么关系？**

Storybook 本身更偏组件开发和文档，但它可以成为测试资产。组件的 stories 可以复用到交互测试和视觉回归测试里：交互测试检查点击、输入后的行为；视觉回归测试截图对比 UI 是否意外变化。面试里可以说：Storybook 负责把组件状态枚举清楚，自动化测试负责验证这些状态是否符合预期。

📌 重点记忆：Storybook 解决的是“组件状态可视化和可复用”，不是替代 Jest、Vitest 或 Playwright。

### 6. 🔥 Mock

**简要总结：**

- Mock 用来替代真实依赖
- 可以 Mock 接口、时间、路由、浏览器 API
- 让测试更稳定、更快
- 不要过度 Mock，否则测试失去真实性

**面试口语：**

Mock 的作用是隔离不可控依赖。比如接口不稳定、时间会变化、浏览器 API 在测试环境没有，就可以用 Mock 固定输入，让测试只关注当前模块行为。

```ts
import { vi, test, expect } from 'vitest'

test('loads users', async () => {
  globalThis.fetch = vi.fn().mockResolvedValue({
    json: () => Promise.resolve([{ id: 1, name: 'Tom' }])
  })

  const users = await loadUsers()

  expect(users[0].name).toBe('Tom')
})
```

**底层原理 / 背后逻辑：**

Mock 本质是替换依赖的实现。测试时我们不关心真实接口怎么返回，只关心“当接口返回某个数据时，业务代码是否正确处理”。但如果所有东西都 Mock，测试就只能证明代码适配了 Mock，不一定能证明真实系统可用，所以关键链路还需要集成或 E2E 测试补充。

### 7. 🔥 E2E 测试

**简要总结：**

- 从用户视角测试完整流程
- 常用工具：Playwright、Cypress
- 覆盖登录、下单、支付、权限跳转等核心路径
- 成本高，不适合覆盖所有细节

**面试口语：**

E2E 测试就是启动真实浏览器，模拟用户点击、输入、跳转，验证完整业务流程。它最适合覆盖核心链路，比如登录后进入工作台、提交表单成功、权限不足跳转。

```ts
import { test, expect } from '@playwright/test'

test('login flow', async ({ page }) => {
  await page.goto('/login')
  await page.getByLabel('用户名').fill('admin')
  await page.getByLabel('密码').fill('123456')
  await page.getByRole('button', { name: '登录' }).click()

  await expect(page).toHaveURL('/dashboard')
})
```

**底层原理 / 背后逻辑：**

E2E 测试通过浏览器自动化协议控制真实浏览器，所以更接近用户环境。它能发现路由、接口、浏览器兼容、构建产物、样式交互等集成问题。但它慢且容易受环境影响，所以应该少而精，优先覆盖高价值路径。

### 8. ⭐ 快照测试

**简要总结：**

- 记录组件输出结构
- 下次测试对比是否变化
- 适合稳定 UI 结构
- 不适合频繁变化或复杂页面滥用

**面试口语：**

快照测试适合防止结构意外变化，但不能证明交互正确。快照太大时，开发者容易无脑更新快照，反而失去测试价值。

**底层原理 / 背后逻辑：**

快照测试本质是把某次渲染结果序列化保存，下次运行时做文本 diff。它擅长发现“输出变了”，但不擅长判断“变化是否符合业务预期”。所以面试里可以说：快照要谨慎用，更推荐对关键行为写明确断言。

### 9. ⭐ 覆盖率

**简要总结：**

- 行覆盖率：代码行是否执行
- 分支覆盖率：if/else 等分支是否覆盖
- 函数覆盖率：函数是否被调用
- 覆盖率高不等于质量一定高

**面试口语：**

覆盖率是参考指标，不是最终目标。高覆盖率只能说明代码被执行过，不代表断言有效。项目里更应该关注核心业务和复杂逻辑是否有测试，而不是为了数字写没有意义的测试。

```txt
80% 覆盖率 + 关键链路有断言 > 95% 覆盖率 + 大量无效快照
```

**底层原理 / 背后逻辑：**

覆盖率工具会在代码中插桩，记录运行时哪些语句、函数和分支被执行。它能发现明显没测到的区域，但不能判断断言是否充分。比如一段代码执行了，但测试没有断言结果，也可能覆盖率很高但质量很差。

### 10. 🔥 CI 中的测试和质量门禁

**简要总结：**

- 提交或合并前执行 lint、typecheck、test
- 核心分支可加 E2E 测试
- 覆盖率和 SonarQube 可作为 Quality Gate
- 不通过时阻止合并或发布

**面试口语：**

测试最好接入 CI，而不是只靠开发者本地自觉执行。常见流程是提交后跑 ESLint、TypeScript、单元测试，主分支或发布前跑 E2E，再结合覆盖率或 SonarQube 质量门禁控制风险。

```yaml
steps:
  - run: pnpm lint
  - run: pnpm typecheck
  - run: pnpm test
  - run: pnpm test:e2e
```

**底层原理 / 背后逻辑：**

CI 的价值是把质量检查放到统一环境里自动执行，避免“我本地没问题”。Quality Gate 是把质量标准数字化，比如不能有 blocker 级漏洞、新增代码覆盖率不能低于阈值、重复率不能超标。它解决的是团队协作中的质量下限问题。

### 11. ⭐ 测试怎么选

**判断原则：**

- 纯函数和复杂逻辑：单元测试
- 组件渲染和交互：组件测试
- 多模块协作：集成测试
- 登录、下单、权限等核心流程：E2E 测试
- 样式视觉稳定性要求高：视觉回归测试

**面试口语：**

我会先看风险和成本。核心业务链路用 E2E 保底，复杂计算用单元测试，组件交互用组件测试。不是所有代码都要测，而是优先测容易出错、影响大、长期维护的地方。

## 面试优先级

### 第一优先级

- 🔥 测试金字塔
- 🔥 单元测试
- 🔥 组件测试
- ⭐ Storybook
- 🔥 Mock
- 🔥 E2E 测试
- 🔥 CI 质量门禁

### 第二优先级

- ⭐ 覆盖率
- ⭐ 快照测试
- ⭐ Testing Library 理念
- ⭐ Playwright / Cypress

### 第三优先级

- 💡 视觉回归测试
- 💡 契约测试
- 💡 测试数据管理
