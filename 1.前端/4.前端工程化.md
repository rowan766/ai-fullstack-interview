# 前端工程化

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 工程化基础

### 1. 🔥 什么是前端工程化

**简要总结：**

- 用工程手段提升前端开发效率、质量和可维护性
- 覆盖脚手架、构建、模块化、规范、测试、部署、监控等环节
- 目标是让项目可开发、可维护、可构建、可发布、可回滚

**面试口语：**

前端工程化不是单指 Webpack 或 Vite，而是从项目创建、代码开发、质量检查、构建打包到部署上线的一整套流程和规范。

📌 重点记忆：工程化解决的是团队协作和项目长期维护问题。

### 2. ⭐ 项目目录设计

**简要总结：**

- `src`：源码目录
- `components`：通用组件
- `views` / `pages`：页面组件
- `router`：路由配置
- `store`：状态管理
- `api`：接口请求
- `utils`：通用工具
- `assets`：静态资源
- `types`：类型定义

**面试口语：**

目录设计要让职责清晰。页面放 pages，通用组件放 components，接口统一放 api，状态放 store。团队越大，越需要统一目录和命名规范。

## 模块化与包管理

### 1. 🔥 前端模块化

**简要总结：**

- CommonJS：Node.js 常见模块规范
- ES Module：浏览器和现代前端标准模块规范
- AMD / CMD：早期浏览器模块方案
- 现代前端项目主要使用 ES Module

**面试口语：**

模块化是为了解决代码拆分、复用和依赖管理问题。现在前端主流使用 ES Module，通过 `import` 和 `export` 管理模块依赖。

```js
// utils/format.js
export function formatPrice(value) {
  return `￥${value.toFixed(2)}`
}

// main.js
import { formatPrice } from './utils/format.js'
```

### 2. 🔥 npm / yarn / pnpm

**简要总结：**

- npm：Node 官方包管理器
- yarn：更早关注速度和锁文件稳定性
- pnpm：通过内容寻址和软硬链接节省磁盘空间
- 锁文件用于保证依赖版本一致

**面试口语：**

包管理器负责安装和管理依赖。pnpm 的特点是依赖不会在每个项目里重复复制，而是通过全局内容寻址仓库复用，所以安装快、占用空间小，也能减少幽灵依赖问题。

**底层原理 / 背后逻辑：**

Node 查找依赖时，会从当前文件所在目录开始找 `node_modules`，找不到就一层层向父目录查找。npm 和 Yarn Classic 为了减少重复安装，会把很多依赖提升到项目根目录的 `node_modules`，这会让项目代码“意外地”可以引入自己没有声明过的包。

幽灵依赖就是：项目代码使用了某个包，但这个包没有写在当前项目的 `package.json` 里，只是因为它被其他依赖间接安装并提升到了根目录，所以暂时能用。一旦间接依赖版本变化、包管理器变化或部署环境更严格，代码就可能突然报 `Cannot find module`。

pnpm 主要通过“内容寻址仓库 + 硬链接 + 符号链接”的方式解决这个问题。项目根目录下只暴露自己显式声明的直接依赖，间接依赖放在 `.pnpm` 的隔离结构里，普通业务代码不能随便引用未声明依赖，因此能更早暴露依赖声明不完整的问题。

```txt
npm / Yarn Classic:
node_modules/
  axios
  follow-redirects   <- axios 的依赖也可能被提升，业务代码可能误用

pnpm:
node_modules/
  axios -> .pnpm/axios@x/node_modules/axios
  .pnpm/
    axios@x/node_modules/follow-redirects
```

📌 重点记忆：幽灵依赖不是“包不存在”，而是“你没声明却刚好能访问”。pnpm 对它的约束更强，npm 和 Yarn Classic 更容易因为扁平提升产生这个问题。

⚠️ 注意：团队项目要统一包管理器，不要混用 `package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`。

### 3. ⭐ dependencies 和 devDependencies

**简要总结：**

- `dependencies`：运行时依赖
- `devDependencies`：开发和构建阶段依赖
- 组件库、请求库通常是运行依赖
- TypeScript、ESLint、构建工具通常是开发依赖

**面试口语：**

dependencies 是项目运行需要的包，devDependencies 是开发或构建需要的包。比如 Vue、React、axios 是运行依赖，Vite、TypeScript、ESLint 是开发依赖。

```json
{
  "dependencies": {
    "vue": "^3.0.0",
    "axios": "^1.0.0"
  },
  "devDependencies": {
    "vite": "^5.0.0",
    "typescript": "^5.0.0"
  }
}
```

## 构建工具

### 1. 🔥 Webpack

**简要总结：**

- Webpack 是模块打包工具
- 从入口文件分析依赖图
- loader 处理不同类型文件
- plugin 扩展构建流程
- 支持代码分割、资源处理、Tree Shaking 等

**面试口语：**

Webpack 会从入口文件开始递归分析依赖，把 JS、CSS、图片等资源都当作模块处理，最后输出浏览器可运行的静态资源。loader 负责转换文件，plugin 负责扩展构建流程。

**底层原理 / 背后逻辑：**

Webpack 的核心是“从入口构建依赖图”。它读取入口文件后，会解析 `import`、`require` 等依赖关系，递归把每个模块加入图中。遇到非 JS 文件时，先交给 loader 转成 Webpack 能理解的模块；构建过程中再通过 plugin 监听不同生命周期，插入额外逻辑。最后 Webpack 把模块图切成一个或多个 chunk，再生成 bundle。

面试被追问时，可以按这条链路回答：`entry -> 解析依赖 -> loader 转换 -> plugin 扩展生命周期 -> chunk -> bundle`。

**完整项目示例：**

一个最小 Webpack 项目通常包含入口文件、HTML 模板、样式文件、Webpack 配置和 npm scripts。这个例子能说明 Webpack 的核心流程：从 `src/main.js` 入口开始，遇到 CSS 交给 loader 处理，再用 plugin 生成 HTML，最后输出到 `dist`。

```txt
webpack-demo/
  package.json
  webpack.config.js
  public/
    index.html
  src/
    main.js
    message.js
    style.css
```

```json
{
  "scripts": {
    "dev": "webpack serve --mode development",
    "build": "webpack --mode production"
  },
  "devDependencies": {
    "webpack": "^5.0.0",
    "webpack-cli": "^5.0.0",
    "webpack-dev-server": "^5.0.0",
    "html-webpack-plugin": "^5.0.0",
    "css-loader": "^6.0.0",
    "style-loader": "^3.0.0"
  }
}
```

```html
<!-- public/index.html -->
<div id="app"></div>
```

```js
// src/message.js
export function getMessage() {
  return 'Hello Webpack'
}
```

```css
/* src/style.css */
#app {
  color: #1677ff;
}
```

```js
// src/main.js
import './style.css'
import { getMessage } from './message.js'

document.querySelector('#app').textContent = getMessage()
```

```js
// webpack.config.js
const path = require('path')
const HtmlWebpackPlugin = require('html-webpack-plugin')

module.exports = {
  entry: './src/main.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'assets/[name].[contenthash].js',
    clean: true
  },
  module: {
    rules: [{ test: /\.css$/, use: ['style-loader', 'css-loader'] }]
  },
  plugins: [new HtmlWebpackPlugin({ template: './public/index.html' })],
  devServer: {
    port: 8080,
    hot: true
  }
}
```

📌 重点记忆：loader 转换文件，plugin 参与构建生命周期。

### 2. 🔥 Vite

**简要总结：**

- 开发环境基于浏览器原生 ES Module
- 依赖预构建通常使用 esbuild
- 生产构建通常使用 Rollup
- 冷启动快，HMR 快

**面试口语：**

Vite 开发环境不需要一开始把整个项目打包，而是利用浏览器原生 ES Module 按需加载源码，所以启动很快。生产环境仍然会打包优化。

**底层原理 / 背后逻辑：**

Vite 快的关键不只是“用了 esbuild”，而是开发阶段改变了工作模式。Webpack dev server 通常要先构建一份可运行的模块图；Vite 启动时主要做依赖预构建，然后把源码作为 ESM 交给浏览器按需请求。浏览器请求到哪个模块，Vite 才转换哪个模块，所以冷启动更轻。依赖预构建用 esbuild 把 CommonJS 或多模块依赖提前转成浏览器友好的 ESM，减少请求数量。

HMR 时，Vite 能根据模块依赖关系只让变更模块和相关边界失效，不需要重新打完整包，所以热更新也快。

```js
// vite.config.js
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  server: { port: 5173 }
})
```

### 3. ⭐ Webpack 和 Vite 区别

**简要总结：**

- Webpack 开发时通常先打包再启动
- Vite 开发时按需加载源码模块
- Vite 冷启动和热更新通常更快
- Webpack 生态成熟、配置能力强
- 大型复杂老项目仍可能使用 Webpack

**面试口语：**

Webpack 更像先把项目整体构建成 bundle 再给浏览器用；Vite 开发阶段更多利用浏览器原生 ESM，按需请求模块，所以启动和热更新更快。

**面试追问：为什么 Vite 更快？**

这个问题要明确说“开发环境更快”，不要泛泛说 Vite 永远比 Webpack 快。Vite 快主要有三层原因：

- 启动方式不同：Webpack dev server 启动时通常要从入口递归分析依赖，先构建出一份 bundle 或内存中的模块图；Vite 启动时不需要先打完整应用包，而是启动一个开发服务器，把源码模块交给浏览器按需请求。
- 源码处理范围不同：Webpack 更偏“先整体编译，再提供给浏览器”；Vite 是浏览器访问到哪个 ESM 模块，开发服务器才转换哪个模块，所以冷启动时处理的源码更少。
- 依赖处理工具不同：Vite 对第三方依赖会做预构建，通常用 esbuild 把 CommonJS 或零散 ESM 依赖转成更适合浏览器加载的 ESM。esbuild 用 Go 编写，转换速度通常比传统 JS 工具链更快。

HMR 也更快，是因为 Vite 基于 ESM 模块边界做更新。某个文件变化后，只需要让这个模块及其相关边界失效，浏览器重新请求变更模块即可；Webpack 的 HMR 也能局部更新，但它维护的是打包后的模块系统，项目越大，更新链路和重新编译成本通常越高。

```txt
Webpack dev:
启动 -> 分析入口 -> 构建依赖图 -> 打包 bundle -> 浏览器加载

Vite dev:
启动开发服务器 -> 浏览器请求页面 -> 按需请求 ESM -> 按需转换源码
```

📌 重点记忆：Vite 快的核心不是单点优化，而是“开发阶段不先全量打包 + 浏览器原生 ESM 按需加载 + esbuild 预构建依赖”。

**面试追问：为什么 Vite 生产环境还要打包？**

开发环境追求启动快和按需编译，但生产环境更关注资源体积、缓存、兼容性和请求数量。如果完全保留大量 ESM 文件，浏览器会产生很多网络请求，也不利于压缩、Tree Shaking 和长期缓存。因此 Vite 生产构建会使用 Rollup 打包，把资源合并、拆分、压缩并生成 hash 文件。

### 4. 🔥 Loader 和 Plugin

**简要总结：**

- Loader 处理具体文件转换
- Plugin 处理构建流程扩展
- Loader 是文件级别
- Plugin 是构建生命周期级别

**面试口语：**

Loader 主要回答“这个文件怎么处理”，比如把 Sass 转 CSS、把 TS 转 JS。Plugin 主要回答“构建过程中要额外做什么”，比如生成 HTML、抽离 CSS、定义环境变量。

**底层原理 / 背后逻辑：**

Loader 本质是一个转换函数，输入文件内容，输出新的代码内容，所以它是“模块级别”的处理。多个 loader 会按配置顺序组成管道，例如 Sass 先转 CSS，CSS 再转 JS 模块。Plugin 本质是订阅构建生命周期的对象，它可以在编译开始、模块解析、资源生成、产物输出等阶段执行逻辑，所以它是“流程级别”的扩展。

```js
module.exports = {
  module: {
    rules: [{ test: /\.ts$/, use: 'ts-loader' }]
  },
  plugins: [new HtmlWebpackPlugin({ template: './index.html' })]
}
```

### 5. ⭐ Babel / SWC / esbuild

**简要总结：**

- Babel：JS 转译工具，生态成熟
- SWC：Rust 编写，速度快
- esbuild：Go 编写，速度快，常用于预构建
- 它们都可以处理语法转换，但插件生态和能力不同

**面试口语：**

Babel 主要负责把新语法转换成目标环境能运行的代码。SWC 和 esbuild 更强调速度，很多现代构建工具会用它们提升开发和构建性能。

### 6. 🔥 Tree Shaking

**简要总结：**

- Tree Shaking 用于删除未使用代码
- 依赖 ES Module 的静态结构
- 生产构建中更常见
- 代码要避免不必要副作用

**面试口语：**

Tree Shaking 就是把没有用到的代码从最终产物里移除。它依赖 ES Module 静态分析，所以库如果想支持 Tree Shaking，要尽量使用 ESM 并正确声明副作用。

**底层原理 / 背后逻辑：**

ES Module 的 `import` / `export` 是静态结构，构建工具在不运行代码的情况下就能知道“导出了什么、导入了什么”。Tree Shaking 会先做依赖标记，判断哪些导出被使用；再在压缩阶段配合 Terser、esbuild 等删除没有被引用的代码。CommonJS 的 `require` 可以写在条件、函数和变量里，依赖关系更动态，所以天然不如 ESM 容易做静态分析。

副作用会影响删除判断。例如一个文件虽然导出的函数没人用，但顶层代码可能修改全局变量或引入 CSS，构建工具不能随便删。`package.json` 里的 `sideEffects` 就是告诉构建工具哪些文件可以安全移除。

```js
// math.js
export const add = (a, b) => a + b
export const minus = (a, b) => a - b

// 只导入 add，生产构建时 minus 有机会被移除
import { add } from './math.js'
```

## 环境与配置

### 1. ⭐ 环境变量

**简要总结：**

- 常见环境：开发、测试、预发、生产
- 环境变量用于区分接口地址、开关配置、构建参数
- 前端环境变量会被打进产物，不应放敏感信息
- Vite 常用 `VITE_` 前缀暴露变量

**面试口语：**

前端环境变量主要用于区分不同环境的配置，比如 API 地址。要注意前端变量最终会出现在浏览器代码里，所以不能放密钥、密码这类敏感信息。

```js
const baseURL = import.meta.env.VITE_API_BASE_URL
```

### 2. ⭐ Source Map

**简要总结：**

- Source Map 用来映射压缩后的代码和源码
- 方便线上错误定位
- 生产环境是否开放要看安全策略
- 可以上传到监控平台后不公开给用户

**面试口语：**

线上代码通常被压缩混淆，Source Map 可以把错误堆栈还原到源码位置。实际项目里一般会上传到监控平台，不一定直接公开。

**底层原理 / 背后逻辑：**

Source Map 本质是一份映射表，记录“压缩后代码的行列位置”对应“源码文件的行列位置”。浏览器或监控平台拿到压缩代码报错位置后，通过 map 文件反查源码位置。生产环境常见做法是构建时生成 sourcemap，但不公开访问，只上传到错误监控平台，既能定位问题，又减少源码泄露风险。

```js
// vite.config.js
export default defineConfig({
  build: {
    sourcemap: true
  }
})
```

**简要总结：**

- ESLint 负责代码质量和规则检查
- Prettier 负责代码格式化
- 两者配合可以减少风格争议

### 2. ⭐ TypeScript 工程化

**简要总结：**

- 开启 `strict` 提升类型安全
- 使用路径别名提升导入可读性
- 公共类型集中管理
- API 入参和响应要定义类型
- 避免滥用 `any`

**面试口语：**

TypeScript 工程化重点是把类型用在关键边界，比如接口、组件 props、状态管理和工具函数。类型不是写得越复杂越好，而是要提升维护效率。

```ts
interface UserDTO {

  name: string
}

async function getUser(): Promise<UserDTO> {
  return request('/api/user')
}
```

### 3. ⭐ Git Hooks

**简要总结：**

- 常用工具：husky、lint-staged、commitlint
- 提交前执行 lint、format、类型检查
- commit message 统一规范
- 避免问题代码进入仓库

**面试口语：**

Git Hooks 可以在提交前自动做检查，比如格式化、ESLint、提交信息校验。这样能把问题尽量拦在本地，而不是等到 CI 或线上才发现。

```json
{
  "lint-staged": {

  }
}
```

## 构建优化

### 1. 🔥 代码分割

**简要总结：**

- 按路由拆分
- 按组件懒加载
- 第三方库单独拆包
- 减少首屏加载体积

**面试口语：**

代码分割是把一个大包拆成多个小包，用户访问到对应页面时再加载需要的代码。最常见的是路由懒加载，可以明显降低首屏资源体积。

**底层原理 / 背后逻辑：**

代码分割依赖动态导入 `import()`。静态 `import` 会进入初始依赖图，通常被放进首屏包；动态 `import()` 会形成异步 chunk，运行到这行代码时才发请求加载。路由懒加载就是把页面组件写成动态导入，让“访问页面”变成加载对应 chunk 的触发条件。

```js
const UserPage = () => import('./pages/UserPage.vue')

export const routes = [{ path: '/user', component: UserPage }]
```

### 2. ⭐ 依赖优化

**简要总结：**

- 移除未使用依赖
- 使用支持按需引入的库
- 避免引入过大的工具库
- 分析 bundle 体积
- 使用 CDN 或 external 要结合缓存和部署策略

**面试口语：**

依赖优化要先分析包体积，找出大依赖和重复依赖。比如工具函数只用一个方法，就不要引入整个库；组件库要开启按需引入。

```js
// 更推荐：只导入需要的方法
import debounce from 'lodash-es/debounce'
```

### 3. ⭐ 构建缓存

**简要总结：**

- 构建缓存可以减少重复编译
- CI 中可以缓存依赖和构建中间产物
- 文件 hash 变化影响缓存命中
- 合理缓存能提升构建速度

**面试口语：**

构建缓存的目标是避免每次从零开始编译。比如 CI 可以缓存包管理器依赖，构建工具也可以缓存转换结果，从而缩短构建时间。

**底层原理 / 背后逻辑：**

缓存是否命中，本质取决于输入是否变化。依赖缓存通常看锁文件 hash，锁文件没变就复用包缓存；构建缓存通常看源码、配置、环境变量和依赖版本的 hash，输入一致就复用上次产物。Monorepo 工具里的任务缓存也是这个思路：同一个任务在同一组输入下，结果应该可复用。

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.pnpm-store
    key: pnpm-${{ hashFiles('pnpm-lock.yaml') }}
```

## CI/CD 与部署

### 1. 🔥 前端 CI/CD 流程

**常见流程：**

- 安装依赖
- 代码规范检查
- 类型检查
- 单元测试
- 构建产物
- 上传静态资源
- 部署到目标环境
- 通知或生成发布记录

**面试口语：**

前端 CI/CD 就是把本地构建发布流程自动化。代码提交后自动安装依赖、检查代码、构建产物，再部署到测试或生产环境，减少人工操作风险。

```yaml
steps:
  - run: pnpm install --frozen-lockfile
  - run: pnpm lint
  - run: pnpm test
  - run: pnpm build
```

### 2. ⭐ 静态资源部署

**简要总结：**

- 前端项目最终通常是 HTML、JS、CSS、图片等静态资源
- JS / CSS 文件名通常带 hash，便于长期缓存
- HTML 不适合强缓存太久
- 静态资源可部署到 Nginx、对象存储、CDN

**面试口语：**

前端部署本质是部署静态资源。带 hash 的 JS 和 CSS 可以设置长缓存，HTML 要保证能及时更新，因为它负责引用最新的静态资源。

```nginx
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}

location = /index.html {
  add_header Cache-Control "no-cache";
}
```

### 3. ⭐ 灰度发布和回滚

**简要总结：**

- 灰度发布：先让部分用户使用新版本
- 回滚：出现问题快速恢复旧版本
- 前端回滚通常依赖版本化静态资源
- 发布记录和产物归档很重要

**面试口语：**

灰度发布能降低新版本风险，先给少量用户验证。前端要能快速回滚，需要保留历史构建产物，并且 HTML 和静态资源版本要对应。

```js
const version = localStorage.getItem('app_version')
const entry = version === 'gray' ? '/gray/index.html' : '/stable/index.html'
```

## Monorepo

### 1. 💡 Monorepo 是什么

**简要总结：**

- 多个项目或包放在同一个仓库
- 方便共享组件、工具、类型和规范
- 常见工具：pnpm workspace、Nx、Turborepo
- 需要解决依赖关系、构建顺序和缓存问题

**面试口语：**

Monorepo 适合多个前端项目或公共包需要协同开发的场景。它能统一依赖和规范，但也需要配套构建缓存、任务编排和版本管理。

**底层原理 / 背后逻辑：**

Monorepo 不是简单地“把很多项目放进一个仓库”。它真正解决的是多项目之间共享代码、统一规范和联动发布的问题。比如 `admin`、`mobile`、`docs` 三个应用都依赖同一个 `ui` 组件库和 `utils` 工具库，如果分散在多个仓库，改一次公共组件要跨仓库发包、升级版本、同步联调。Monorepo 把这些包放在同一个仓库里，通过 workspace 建立本地依赖关系，改公共包后可以立刻被应用引用。

```yaml
# pnpm-workspace.yaml
packages:
  - apps/*
  - packages/*
```

```txt
repo/
  apps/
    admin/
    mobile/
  packages/
    ui/
    utils/
    eslint-config/
```

**常见追问 1：Monorepo 怎么引用内部包？**

内部包会在自己的 `package.json` 声明包名，应用通过 workspace 协议依赖它。包管理器会把依赖链接到本地包，而不是从 npm 仓库下载。

```json
{
  "dependencies": {
    "@repo/ui": "workspace:*",
    "@repo/utils": "workspace:*"
  }
}
```

**常见追问 2：Monorepo 怎么保证构建顺序？**

核心是依赖拓扑排序。比如 `apps/admin` 依赖 `packages/ui`，`packages/ui` 又依赖 `packages/utils`，那构建顺序应该是 `utils -> ui -> admin`。Nx、Turborepo 这类工具会分析 package 之间的依赖图，只执行受影响的任务，并按依赖关系排序。

```txt
packages/utils -> packages/ui -> apps/admin
```

**常见追问 3：Monorepo 的缓存为什么有效？**

任务缓存的底层逻辑是：同一个任务在输入不变时，输出应该一致。工具会把源码、配置、依赖版本、环境变量等作为输入计算 hash。如果 hash 没变，就直接复用上次的构建或测试结果；如果只改了 `apps/admin`，就不需要重新构建完全无关的 `apps/mobile`。

**常见追问 4：Monorepo 有什么问题？**

- 仓库变大后，安装、检索、CI 都可能变慢
- 公共包修改影响面更大，需要明确依赖边界
- 权限管理比多仓库更粗
- 工具链复杂度更高，需要任务编排、缓存和规范约束

**常见追问 5：什么时候适合用 Monorepo？**

多个项目共享组件、工具函数、类型定义、工程规范，并且经常需要联动开发时适合 Monorepo。如果只有一个应用，或者项目之间几乎不共享代码，强行上 Monorepo 反而会增加维护成本。

📌 重点记忆：Monorepo 的核心不是“一个仓库放多个项目”，而是“workspace 管内部依赖、任务图管执行顺序、缓存减少重复任务、规范统一团队协作”。
