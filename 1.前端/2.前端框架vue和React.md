# 前端框架 Vue 和 React

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## Vue 面试题

### 1. 🔥 Vue2 和 Vue3 响应式原理

**简要总结：**

- Vue2 使用 `Object.defineProperty` 劫持对象属性的 `get` 和 `set`
- Vue3 使用 `Proxy` 代理整个对象
- Vue2 对新增属性、删除属性、数组索引修改监听不完整
- Vue3 可以监听属性新增、删除、数组变化、`Map`、`Set` 等

**面试口语：**

Vue2 响应式是通过 `Object.defineProperty` 对每个属性做 getter 和 setter 劫持。Vue3 改成 `Proxy`，代理的是整个对象，所以能更自然地监听新增属性、删除属性和数组变化，性能和类型支持也更好。

**底层原理 / 背后逻辑：**

Vue 响应式的核心不是“监听数据变化”这么简单，而是建立“数据 -> 组件更新函数”的依赖关系。组件渲染时会读取响应式数据，读取触发 `get`，框架就能把当前渲染 effect 收集到这个属性对应的依赖集合里；数据修改时触发 `set`，框架再找到依赖这个属性的 effect 重新执行。

Vue2 的 `Object.defineProperty` 只能劫持已经存在的属性，所以新增属性、删除属性、数组索引变化需要额外处理。Vue3 的 `Proxy` 代理整个对象，可以拦截 `get`、`set`、`deleteProperty`、`has` 等操作，能力更完整。

```js
const state = reactive({ count: 0 })

effect(() => {
  console.log(state.count)
})

state.count++
```

📌 重点记忆：Vue2 是“劫持属性”，Vue3 是“代理对象”。

### 2. 🔥 Object.defineProperty 和 Proxy 区别

**简要总结：**

- `Object.defineProperty` 只能劫持已有属性
- `Proxy` 可以代理整个对象
- `Proxy` 能拦截 `get`、`set`、`deleteProperty`、`has` 等更多操作
- `Proxy` 对数组和集合类型支持更好

**面试口语：**

`defineProperty` 更像是给对象已有属性加拦截器，所以 Vue2 初始化时要递归遍历对象。`Proxy` 是直接代理对象本身，访问、修改、删除都能被拦截，所以 Vue3 响应式能力更完整。

```js
const user = { name: 'Tom' }

const proxy = new Proxy(user, {
  set(target, key, value) {
    target[key] = value
    console.log('更新了', key)
    return true
  }
})

proxy.age = 18
```

⚠️ 注意：`Proxy` 不能兼容 IE，这也是 Vue3 不支持 IE 的原因之一。

### 3. 🔥 ref 和 reactive

**简要总结：**

- `ref` 可以包装基本类型和引用类型
- `reactive` 只能包装对象类型
- `ref` 在 JS 中访问需要 `.value`
- `reactive` 返回的是代理对象
- 模板中使用 `ref` 会自动解包

**面试口语：**

`ref` 适合定义基本类型，也可以包对象；`reactive` 适合定义对象或数组。`ref` 本质上是一个带 `.value` 的响应式对象，所以在 JS 里要通过 `.value` 访问，模板里会自动解包。

```vue
<script setup>
const count = ref(0)
const user = reactive({ name: 'Tom' })

count.value++
user.name = 'Jerry'
</script>
```

📌 重点记忆：基本类型用 `ref`，对象结构复杂时可以用 `reactive`。

### 4. 🔥 computed 和 watch

**简要总结：**

- `computed` 用来基于已有状态计算新值
- `computed` 有缓存，依赖不变不会重新计算
- `watch` 用来监听数据变化并执行副作用
- `watch` 默认是惰性的，数据变化后才执行

**面试口语：**

`computed` 更适合做派生状态，比如根据列表计算总价；`watch` 更适合做副作用，比如数据变化后请求接口、操作缓存。`computed` 有缓存，依赖没变时会直接返回上次结果。

**底层原理 / 背后逻辑：**

`computed` 本质是一个带缓存的响应式 effect。第一次读取时执行 getter，并记录依赖；依赖没变时再次读取直接返回缓存。依赖变化后，computed 不一定马上重新计算，而是先标记为 dirty，等下次读取时再计算。`watch` 更像是显式订阅某个数据源，数据变化后执行回调，因此适合请求接口、写缓存、操作 DOM 这类副作用。

```js
const total = computed(() => cart.value.reduce((sum, item) => sum + item.price, 0))

watch(keyword, (value) => {
  fetchList(value)
})
```

⚠️ 注意：能用 `computed` 表达的数据派生，不建议用 `watch` 手动同步。

### 5. ⭐ watch 和 watchEffect

**简要总结：**

- `watch` 需要明确指定监听源
- `watchEffect` 会自动收集回调中用到的响应式依赖
- `watch` 可以拿到新值和旧值
- `watchEffect` 初始化会立即执行

**面试口语：**

`watch` 是明确监听某个数据，适合需要新旧值对比的场景。`watchEffect` 会自动收集依赖，代码里用到了什么响应式数据，它就监听什么，更适合依赖比较多但不关心旧值的场景。

```js
watch(count, (newValue, oldValue) => {
  console.log(newValue, oldValue)
})

watchEffect(() => {
  console.log(count.value, keyword.value)
})
```

### 6. 🔥 Vue 依赖收集和派发更新

**简要总结：**

- 组件渲染会创建响应式副作用 `effect`
- 读取响应式数据时触发 `track` 收集依赖
- 修改响应式数据时触发 `trigger` 派发更新
- 依赖通常按 `target -> key -> effect` 的结构保存

**面试口语：**

Vue 的响应式核心可以概括成读取时收集依赖，修改时触发更新。组件渲染时会创建一个 effect，渲染过程中读到响应式数据，就把这个 effect 收集起来。之后数据变化，就通知对应 effect 重新执行。

📌 重点记忆：`track` 收集依赖，`trigger` 触发更新。

### 7. 🔥 Vue 异步更新和 nextTick

**简要总结：**

- Vue 数据变化后不会立刻同步更新 DOM
- 多次数据修改会被合并到一次更新中
- 更新任务会放入队列异步执行
- `nextTick` 可以在 DOM 更新后执行回调
- 底层通常优先使用微任务

**面试口语：**

Vue 修改数据后不会马上更新 DOM，而是把组件更新任务放进队列，等当前同步代码执行完后统一刷新。这样可以合并多次更新，提高性能。想在 DOM 更新后拿到最新结果，可以用 `nextTick`。

**底层原理 / 背后逻辑：**

Vue 的更新是异步批处理。一次同步代码里多次修改响应式数据，如果每次都立刻重新渲染，会造成大量重复 DOM 更新。Vue 会把组件更新任务放入队列，并通过微任务统一 flush。`nextTick` 等待的就是这次更新队列刷新完成后的时机，所以它能拿到更新后的 DOM。

```js
count.value++

await nextTick()
console.log(document.querySelector('#count').textContent)
```

### 8. 🔥 虚拟 DOM 和 Diff

**简要总结：**

- 虚拟 DOM 是用 JS 对象描述真实 DOM
- 数据变化后生成新的虚拟 DOM
- Diff 对比新旧虚拟 DOM，找出最小更新范围
- 最后把变化 patch 到真实 DOM

**面试口语：**

虚拟 DOM 本质是用 JS 对象描述页面结构。数据变化后，Vue 会生成新的虚拟 DOM，然后和旧的虚拟 DOM 做 Diff，找出需要变化的部分，再更新真实 DOM。

💡 提示：虚拟 DOM 不是一定比直接操作 DOM 快，它的价值是跨平台、声明式开发和可维护的更新模型。

### 9. 🔥 Vue2 和 Vue3 Diff 区别

**简要总结：**

- Vue2 使用双端 Diff
- Vue3 在双端比较基础上增加了最长递增子序列优化
- Vue3 结合编译时的 Patch Flag，能跳过很多不需要比较的节点
- Vue3 静态节点会被提升，减少重复创建

**面试口语：**

Vue2 的 Diff 主要是双端比较。Vue3 除了双端比较，还结合 Patch Flag、静态提升和最长递增子序列，能更快定位动态节点，并尽量减少 DOM 移动。

**底层原理 / 背后逻辑：**

列表 Diff 的难点是判断节点复用和移动。Vue3 对有 key 的子节点会先从头尾同步比较，快速跳过相同前缀和后缀；剩余乱序部分再建立 key 到新索引的映射，判断旧节点是复用、删除还是新增。最长递增子序列用于找出“已经相对有序、不需要移动”的节点，剩下节点才移动，因此能减少真实 DOM 操作。

📌 重点记忆：最长递增子序列主要用来减少列表节点移动次数。

### 10. 🔥 key 的作用

**简要总结：**

- `key` 用来标识节点身份
- 帮助 Diff 判断节点是否可以复用
- 合理的 `key` 可以减少错误复用和不必要更新
- 不建议用数组下标作为 `key`

**面试口语：**

`key` 的作用是告诉框架每个节点的唯一身份。列表更新时，Diff 会根据 `key` 判断节点是移动、复用、删除还是新增。如果用下标做 key，插入或删除元素时容易导致状态错乱。

```vue
<UserItem v-for="user in users" :key="user.id" :user="user" />
```

⚠️ 注意：列表项有输入框、动画、组件状态时，更不能用数组下标作为 `key`。

### 11. ⭐ 生命周期

**Vue2 常见生命周期：**

- `beforeCreate`
- `created`
- `beforeMount`
- `mounted`
- `beforeUpdate`
- `updated`
- `beforeDestroy`
- `destroyed`

**Vue3 常见生命周期：**

- `setup`
- `onBeforeMount`
- `onMounted`
- `onBeforeUpdate`
- `onUpdated`
- `onBeforeUnmount`
- `onUnmounted`

**面试口语：**

生命周期就是组件从创建、挂载、更新到卸载的过程。Vue3 组合式 API 中，一般在 `setup` 里组织逻辑，再通过 `onMounted`、`onUnmounted` 等函数注册生命周期。

### 12. ⭐ 父子组件生命周期顺序

**挂载阶段：**

- 父 `beforeCreate`
- 父 `created`
- 父 `beforeMount`
- 子 `beforeCreate`
- 子 `created`
- 子 `beforeMount`
- 子 `mounted`
- 父 `mounted`

**更新阶段：**

- 父 `beforeUpdate`
- 子 `beforeUpdate`
- 子 `updated`
- 父 `updated`

**面试口语：**

父子组件挂载时，父组件先开始创建，但要等子组件挂载完成后，父组件才算 mounted。更新时也是父组件先进入更新流程，子组件更新完成后父组件 updated。

### 13. 🔥 组件通信

**简要总结：**

- 父传子：`props`
- 子传父：`emit`
- 跨层级：`provide / inject`
- 兄弟组件：事件总线、状态管理、共同父组件
- 全局状态：Pinia / Vuex
- 双向绑定：`v-model`

**面试口语：**

Vue 组件通信要看组件关系。父子之间用 `props` 和 `emit`，跨层级可以用 `provide/inject`，复杂全局状态用 Pinia 或 Vuex。`v-model` 本质也是 props 加 emit 的语法糖。

### 14. 🔥 props / emit / v-model

**简要总结：**

- `props` 是父组件传给子组件的数据
- 子组件不应该直接修改 props
- `emit` 用于子组件通知父组件
- Vue3 默认 `v-model` 对应 `modelValue` 和 `update:modelValue`
- Vue3 支持多个 `v-model`

**面试口语：**

Vue 是单向数据流，父组件通过 props 把数据传给子组件，子组件通过 emit 通知父组件修改。`v-model` 本质就是一个 prop 加一个 update 事件。

```vue
<Child v-model:title="title" />
```

```vue
<!-- Child.vue -->
<script setup>
defineProps({ title: String })
const emit = defineEmits(['update:title'])
</script>

<template>
  <input :value="title" @input="emit('update:title', $event.target.value)" />
</template>
```

### 15. 🔥 v-if 和 v-show

**简要总结：**

- `v-if` 控制元素是否真正创建和销毁
- `v-show` 控制 `display` 样式
- `v-if` 切换成本高，初始渲染成本低
- `v-show` 初始渲染成本高，切换成本低

**面试口语：**

`v-if` 是条件渲染，不满足条件时元素不会存在；`v-show` 是显示隐藏，元素始终存在，只是切换 `display`。频繁切换用 `v-show`，条件很少变化用 `v-if`。

```vue
<Modal v-if="needCreate" />
<div v-show="visible">频繁显示隐藏的内容</div>
```

### 16. 🔥 v-if 和 v-for 为什么不建议一起用

**简要总结：**

- 可读性差
- 会让条件判断和列表渲染耦合
- Vue2 中 `v-for` 优先级高于 `v-if`
- Vue3 中 `v-if` 优先级高于 `v-for`
- 推荐先用 `computed` 过滤列表

**面试口语：**

`v-if` 和 `v-for` 写在同一个元素上会让逻辑不清晰，也容易产生优先级问题。更推荐先用 `computed` 得到过滤后的列表，再用 `v-for` 渲染。

```js
const activeUsers = computed(() => users.value.filter((user) => user.active))
```

```vue
<UserItem v-for="user in activeUsers" :key="user.id" :user="user" />
```

### 17. ⭐ 模板编译

**简要总结：**

- 模板会被编译成 `render` 函数
- 主要阶段：parse、transform、generate
- parse：模板转 AST
- transform：优化和转换 AST
- generate：生成渲染函数代码

**面试口语：**

Vue 模板最终不是直接运行的，而是会编译成 render 函数。编译过程大致是先解析成 AST，再做转换和优化，最后生成可执行的渲染函数。

**底层原理 / 背后逻辑：**

模板编译的本质是把字符串模板变成 JS 函数。`parse` 阶段把模板解析成 AST，`transform` 阶段标记静态节点、动态属性、事件等信息，`generate` 阶段生成 render 函数代码。运行时状态变化后，组件重新执行 render 得到新的 vnode，再进入 Diff。Vue3 很多性能优化其实发生在编译期，因为编译器知道哪些节点永远不变、哪些字段是动态的。

### 18. ⭐ Vue3 编译时优化

**简要总结：**

- 静态提升：静态节点只创建一次
- Patch Flag：标记动态内容类型
- Block Tree：把动态节点收集到 block 中
- 缓存事件处理函数

**面试口语：**

Vue3 的编译器会尽量区分静态内容和动态内容。静态内容提升后不用每次重新创建，动态节点用 Patch Flag 标记，更新时可以更精准地比较。

**底层原理 / 背后逻辑：**

静态提升是把不会变化的 vnode 提到 render 函数外面，避免每次渲染都重新创建。Patch Flag 是编译器给动态节点打的标记，例如只有文本动态、只有 class 动态、只有 props 动态。运行时 Diff 看到 Patch Flag 后，就不用全量比较节点属性，只检查标记指出的动态部分。Block Tree 则把动态子节点收集起来，让更新时更快跳到真正可能变化的地方。

### 19. ⭐ 插槽和作用域插槽

**简要总结：**

- 插槽用于让父组件向子组件传入模板内容
- 默认插槽、具名插槽、作用域插槽
- 作用域插槽允许子组件把数据传给父组件的插槽模板

**面试口语：**

插槽解决的是组件内容分发问题。普通插槽是父组件传内容给子组件，作用域插槽是子组件把自己的数据暴露给父组件，让父组件决定怎么渲染。

```vue
<UserList v-slot="{ user }">
  <span>{{ user.name }}</span>
</UserList>
```

### 20. ⭐ KeepAlive

**简要总结：**

- 缓存组件实例
- 组件切换时不销毁
- 命中缓存时复用之前的组件状态
- 常配合动态组件、路由组件使用
- 有 `activated` 和 `deactivated` 生命周期

**面试口语：**

`KeepAlive` 用来缓存组件实例，切换组件时不会销毁实例，下次回来还能保留之前的状态。常用于 tab 页、表单页、路由页面缓存。

```vue
<KeepAlive>
  <component :is="currentTab" />
</KeepAlive>
```

### 21. 💡 Teleport 和 Suspense

**Teleport：**

- 把组件内容渲染到指定 DOM 节点
- 常用于弹窗、通知、全局浮层

**Suspense：**

- 用于处理异步组件或异步依赖
- 可以显示 fallback 内容
- 等异步完成后再显示真实内容

**面试口语：**

`Teleport` 解决的是组件逻辑位置和 DOM 渲染位置分离的问题。`Suspense` 主要用于异步组件加载时展示兜底内容。

```vue
<Teleport to="body">
  <Dialog />
</Teleport>
```

### 22. 🔥 Vue Router

**简要总结：**

- hash 模式基于 URL 中的 `#` 和 `hashchange`
- history 模式基于 HTML5 History API
- hash 不需要服务端特殊配置
- history 刷新页面时需要服务端兜底到入口 HTML
- 路由变化后匹配组件并渲染到 `router-view`

**面试口语：**

Vue Router 本质是监听 URL 变化，根据当前路径匹配对应路由记录，然后渲染对应组件。hash 模式兼容性好，history 模式 URL 更干净，但需要服务端配置兜底。

```ts
const router = createRouter({
  history: createWebHistory(),
  routes: [{ path: '/user/:id', component: UserDetail }]
})
```

### 23. ⭐ 路由守卫执行流程

**常见顺序：**

- 失活组件 `beforeRouteLeave`
- 全局 `beforeEach`
- 复用组件 `beforeRouteUpdate`
- 路由配置 `beforeEnter`
- 进入组件 `beforeRouteEnter`
- 全局 `beforeResolve`
- 导航确认
- 全局 `afterEach`

**面试口语：**

路由守卫就是在导航切换过程中插入一些钩子，用来做登录校验、权限判断、数据预加载等。常用的是全局 `beforeEach` 和路由级 `beforeEnter`。

```ts
router.beforeEach((to) => {
  if (to.meta.requiresAuth && !userStore.isLogin) {
    return '/login'
  }
})
```

### 24. 🔥 Pinia 和 Vuex

**简要总结：**

- Vuex 核心是 `state`、`getter`、`mutation`、`action`
- Vuex 要求 mutation 同步执行，方便追踪状态变化
- Pinia 去掉 mutation，直接通过 action 或 store 修改状态
- Pinia 更轻量，TS 支持更好，模块化更自然

**面试口语：**

Vuex 更强调严格的数据流，mutation 必须同步，方便调试和追踪。Pinia 设计更简单，没有 mutation，组合式 API 和 TypeScript 支持更好，现在 Vue3 项目一般优先用 Pinia。

```ts
const useUserStore = defineStore('user', {
  state: () => ({ token: '' }),
  actions: {
    setToken(token: string) {
      this.token = token
    }
  }
})
```

### 25. ⭐ Vue 性能优化

**简要总结：**

- 合理使用 `key`
- 避免 `v-if` 和 `v-for` 同元素使用
- 使用 `computed` 缓存派生数据
- 大组件拆分、路由懒加载、组件懒加载
- `v-memo`、`v-once` 减少不必要更新
- 长列表使用虚拟列表
- 静态资源走缓存和 CDN

**面试口语：**

Vue 性能优化一般从减少不必要渲染、降低组件复杂度、优化列表和资源加载入手。比如使用 computed 缓存计算结果，路由和组件懒加载，大列表用虚拟列表。

### 26. ⭐ Vue SSR 和 Hydration

**简要总结：**

- SSR 是服务端先把组件渲染成 HTML 返回给浏览器
- 浏览器拿到 HTML 后可以更快看到首屏
- Hydration 是客户端接管服务端生成的 HTML
- 如果服务端和客户端渲染结果不一致，可能 hydration 失败

**面试口语：**

SSR 可以提升首屏速度和 SEO。服务端先输出 HTML，客户端加载 JS 后再进行 hydration，把静态 HTML 变成可交互页面。如果两端渲染内容不一致，就可能导致 hydration mismatch。

### 27. 🔥 Composition API

**简要总结：**

- 按逻辑组织代码，而不是按选项分散代码
- 更适合复用复杂逻辑
- 更适合 TypeScript 类型推导
- 解决大型组件中逻辑分散的问题

**面试口语：**

Composition API 主要解决 Options API 在复杂组件里逻辑分散的问题。它可以把同一块业务逻辑组织在一起，也更方便抽成组合函数复用，并且对 TypeScript 更友好。

```ts
function useCounter() {
  const count = ref(0)
  const increment = () => count.value++

  return { count, increment }
}
```

## React 面试题

### 1. 🔥 React 核心设计思想

**简要总结：**

- 声明式 UI
- 组件化
- 单向数据流
- 状态驱动视图
- 通过虚拟 DOM 和 Diff 更新真实 DOM

**面试口语：**

React 的核心思想是用组件描述 UI，用状态驱动视图。开发者只关心状态变成什么样，React 负责根据状态变化重新渲染组件，并把变化更新到页面上。

📌 重点记忆：React = 组件化 + 声明式 + 状态驱动。

### 2. 🔥 state 更新为什么触发重新渲染

**简要总结：**

- 组件状态变化后，React 会调度一次更新
- 重新执行组件函数，生成新的虚拟 DOM
- Diff 新旧虚拟 DOM
- commit 阶段更新真实 DOM

**面试口语：**

React 中 UI 是 state 的映射。调用 `setState` 或 `setXxx` 后，React 会认为组件状态变了，于是重新执行组件函数得到新的 UI 描述，再通过 Diff 找出真实 DOM 需要更新的地方。

```jsx
function Counter() {
  const [count, setCount] = useState(0)

  return <button onClick={() => setCount(count + 1)}>{count}</button>
}
```

### 3. 🔥 React 渲染流程

**简要总结：**

- 触发更新：state、props、context 变化
- render 阶段：构建 Fiber 树，计算变化
- commit 阶段：把变化提交到真实 DOM
- commit 后执行副作用

**面试口语：**

React 更新大致分为 render 和 commit 两个阶段。render 阶段负责计算要改什么，可以被中断；commit 阶段负责真正改 DOM 和执行生命周期，不能被中断。

### 4. 🔥 虚拟 DOM 和 Diff

**简要总结：**

- 虚拟 DOM 是 JS 对象形式的 UI 描述
- Diff 用来比较新旧虚拟 DOM
- React 默认只做同层比较
- 不同类型元素会直接销毁重建
- `key` 用于列表节点复用判断

**面试口语：**

React 用虚拟 DOM 描述 UI。更新时会生成新的虚拟 DOM，然后和旧的做 Diff。为了降低复杂度，React 采用同层比较，不跨层级移动节点，列表中通过 key 判断节点身份。

### 5. 🔥 key 的作用

**简要总结：**

- 标识列表项身份
- 帮助 React 判断节点复用、移动、新增、删除
- 稳定 key 可以减少错误复用
- 不建议使用数组下标

**面试口语：**

`key` 是 React 在列表 Diff 中识别节点身份的依据。如果 key 稳定，React 就能正确复用节点；如果用下标作为 key，插入或删除列表项时可能导致组件状态错乱。

```jsx
{users.map((user) => (
  <UserItem key={user.id} user={user} />
))}
```

### 6. 🔥 Fiber

**简要总结：**

- Fiber 是 React 的新协调架构
- 一个 Fiber 节点对应一个组件或 DOM 节点的工作单元
- Fiber 让渲染工作可以被拆分、中断、恢复
- 为优先级调度和并发渲染打基础

**面试口语：**

Fiber 可以理解成 React 内部的一种任务单元和数据结构。旧版递归渲染一旦开始就很难中断，Fiber 把渲染拆成一个个小任务，让 React 可以根据优先级暂停、继续或丢弃某些渲染任务。

**底层原理 / 背后逻辑：**

Fiber 节点既是数据结构，也是工作单元。它保存组件类型、props、state、child、sibling、return、effect 标记等信息。旧版递归更新像一次深度递归调用，很难暂停；Fiber 把递归改造成可循环处理的链表结构，React 每处理一段工作就能检查是否还有时间、是否出现更高优先级任务，从而实现可中断渲染。真正修改 DOM 的 commit 阶段仍然必须一次完成。

📌 重点记忆：Fiber 解决的是“更新任务可中断、可调度”的问题。

### 7. 🔥 render 阶段和 commit 阶段

**简要总结：**

- render 阶段负责计算变化，生成 workInProgress Fiber 树
- render 阶段可以被中断
- commit 阶段负责真实 DOM 更新和副作用执行
- commit 阶段不能被中断

**面试口语：**

render 阶段只是计算，不会真正操作 DOM，所以可以被中断。commit 阶段会修改真实 DOM，如果中断可能导致 UI 不一致，所以必须一次性完成。

### 8. ⭐ Scheduler 和优先级调度

**简要总结：**

- Scheduler 负责安排任务执行时机
- 高优先级任务可以打断低优先级任务
- 用户输入通常优先级更高
- 时间切片让长任务拆成多个小片段执行

**面试口语：**

Scheduler 的作用是让 React 不必一次性把所有更新做完，而是根据任务优先级安排执行。比如用户输入优先级更高，列表渲染这种低优先级任务可以让路，避免页面卡顿。

**底层原理 / 背后逻辑：**

Scheduler 的核心是给更新分配优先级，并把长任务拆成小片段。用户输入、点击这类交互优先级高，普通数据刷新或过渡更新优先级低。React 在 render 阶段可以暂停低优先级工作，先处理高优先级任务；如果低优先级渲染结果还没 commit，也可以被丢弃重算。这样牺牲一部分计算重复，换取交互响应更稳定。

### 9. ⭐ Concurrent Rendering

**简要总结：**

- 并发渲染不是多线程
- 本质是 React 可以同时准备多个版本的 UI
- 渲染过程可以中断、恢复、丢弃
- 最终只有 commit 的结果会显示到页面

**面试口语：**

Concurrent Rendering 不是浏览器开了多个线程，而是 React 的一种可中断渲染能力。React 可以在后台准备新 UI，如果期间出现更高优先级更新，可以先处理高优先级任务。

⚠️ 注意：并发渲染不等于并行执行。

### 10. 🔥 useState 原理

**简要总结：**

- Hook 状态保存在 Fiber 节点上
- 多个 Hook 按调用顺序形成链表
- 每次渲染按相同顺序读取对应 Hook
- `setState` 会创建更新并调度组件重新渲染

**面试口语：**

`useState` 的状态不是保存在函数局部变量里，而是保存在组件对应的 Fiber 节点上。React 按 Hook 调用顺序把每个状态对应起来，所以 Hook 不能写在条件语句或循环里。

**底层原理 / 背后逻辑：**

函数组件每次渲染都会重新执行，局部变量会重新创建，所以 Hook 状态必须保存在组件对应的 Fiber 上。React 会按调用顺序把 Hook 串成链表，第一次渲染创建 Hook 节点，后续渲染按相同顺序取出对应节点。`setState` 会把更新放进这个 Hook 的 update queue，再调度当前 Fiber 重新渲染。

```jsx
const [name, setName] = useState('')
const [age, setAge] = useState(18)
```

### 11. 🔥 Hook 为什么不能写在条件语句中

**简要总结：**

- React 靠 Hook 调用顺序匹配状态
- 条件语句会导致某次渲染 Hook 数量或顺序变化
- 顺序错乱后，状态就会对应错误

**面试口语：**

React 并不是通过变量名识别 Hook，而是通过调用顺序识别。条件语句会让某些 Hook 有时执行、有时不执行，导致后面的 Hook 顺序错乱，所以 Hook 必须写在组件顶层。

```jsx
// 正确：Hook 在顶层调用
const user = useUser()

if (!user) {
  return null
}
```

### 12. 🔥 useEffect

**简要总结：**

- 用于处理副作用
- 默认在浏览器完成绘制后异步执行
- 依赖数组控制执行时机
- 返回清理函数用于取消订阅、清除定时器等

**面试口语：**

`useEffect` 用来处理渲染之外的副作用，比如请求数据、订阅事件、设置定时器。它通常在浏览器绘制后执行，所以不会阻塞页面渲染。

**底层原理 / 背后逻辑：**

React 渲染阶段只计算 UI，不应该执行副作用。`useEffect` 会在 render 阶段记录 effect 信息，在 commit 阶段 DOM 更新完成后，再异步执行 effect 回调。依赖数组会和上一次依赖做浅比较，变化才重新执行；重新执行前会先调用上一次返回的清理函数，所以订阅、定时器、事件监听要放在 cleanup 里释放。

```jsx
useEffect(() => {
  const timer = setInterval(() => {
    console.log('tick')
  }, 1000)

  return () => clearInterval(timer)
}, [])
```

### 13. 🔥 useEffect 和 useLayoutEffect

**简要总结：**

- `useEffect` 在浏览器绘制后异步执行
- `useLayoutEffect` 在 DOM 更新后、浏览器绘制前同步执行
- `useLayoutEffect` 可以读取布局并同步修改
- 滥用 `useLayoutEffect` 可能阻塞绘制

**面试口语：**

`useEffect` 更适合普通副作用，比如请求接口。`useLayoutEffect` 会在浏览器绘制前执行，适合需要读取 DOM 尺寸并同步调整布局的场景，但用多了会影响性能。

```jsx
useLayoutEffect(() => {
  const width = boxRef.current.offsetWidth
  setWidth(width)
}, [])
```

### 14. ⭐ useMemo 和 useCallback

**简要总结：**

- `useMemo` 缓存计算结果
- `useCallback` 缓存函数引用
- 都依赖依赖数组判断是否复用
- 不一定能提升性能

**面试口语：**

`useMemo` 是缓存一个值，`useCallback` 是缓存一个函数。它们常用于避免昂贵计算或配合 `React.memo` 减少子组件重复渲染，但不是所有地方都需要加。

```jsx
const total = useMemo(() => list.reduce((sum, item) => sum + item.price, 0), [list])

const onSelect = useCallback((id) => {
  setSelectedId(id)
}, [])
```

⚠️ 注意：过度使用 memo 类 API 会增加代码复杂度和比较成本。

### 15. ⭐ useRef

**简要总结：**

- 返回一个稳定的可变对象
- 修改 `.current` 不会触发重新渲染
- 可以保存 DOM 节点
- 可以保存跨渲染周期的普通变量

**面试口语：**

`useRef` 返回的对象在组件多次渲染之间保持稳定。修改 `ref.current` 不会触发重新渲染，所以它适合保存 DOM 引用、定时器 id 或不需要驱动视图的数据。

```jsx
const inputRef = useRef(null)

function focusInput() {
  inputRef.current?.focus()
}
```

### 16. ⭐ useContext

**简要总结：**

- 用来跨层级共享数据
- Provider 提供数据
- Consumer 或 `useContext` 消费数据
- Provider 的 value 变化会让相关消费组件重新渲染

**面试口语：**

Context 适合传递主题、语言、登录用户这类跨层级数据。但如果 value 经常变化，消费它的组件可能都会重新渲染，所以要注意拆分 context 或配合 memo 优化。

```jsx
const theme = useContext(ThemeContext)
```

### 17. 🔥 闭包陷阱 stale closure

**简要总结：**

- 函数组件每次渲染都会产生新的函数作用域
- 回调中可能拿到旧渲染时的 state
- 常见于定时器、异步回调、事件监听
- 可以用函数式更新、依赖数组、`useRef` 解决

**面试口语：**

闭包陷阱是因为函数组件每次渲染都有自己的 state 快照。异步回调如果引用了旧那次渲染的变量，就会拿到旧值。常见解决方式是用函数式更新或 ref 保存最新值。

```jsx
setCount((count) => count + 1)
```

### 18. 🔥 批量更新和 Automatic Batching

**简要总结：**

- React 会把多次 state 更新合并成一次渲染
- React 18 之前主要在 React 事件中批处理
- React 18 自动批处理扩展到 Promise、setTimeout、原生事件等场景
- 批处理可以减少渲染次数

**面试口语：**

批量更新就是多次 setState 不会每次都立刻触发渲染，而是合并后统一更新。React 18 的自动批处理范围更大，在异步回调里也能自动合并更新。

**底层原理 / 背后逻辑：**

`setState` 本质是创建 update 对象放入更新队列，而不是马上改当前变量。批量更新就是在同一个调度周期里收集多个 update，最后统一计算新 state 并渲染一次。React 18 使用 `createRoot` 后，Promise、setTimeout、原生事件等异步场景里的多次更新也会进入自动批处理，减少重复 render。

```jsx
setTimeout(() => {
  setCount((count) => count + 1)
  setVisible(true)
  // React 18 中通常会合并成一次渲染
})
```

### 19. ⭐ state 为什么看起来是异步的

**简要总结：**

- 调用 setState 后不会马上改当前渲染里的 state
- React 会把更新放入队列
- 当前函数中的 state 是这次渲染的快照
- 下一次渲染才能拿到新 state

**面试口语：**

React 的 state 更像一次渲染中的快照。调用更新函数后，React 会安排下一次渲染，而不是马上修改当前函数里的变量，所以立刻打印通常还是旧值。

```jsx
setCount(count + 1)
console.log(count) // 仍然是当前这次渲染里的旧值
```

### 20. 🔥 React 事件系统

**简要总结：**

- React 封装了合成事件 SyntheticEvent
- 统一不同浏览器事件差异
- 通过事件委托提升管理效率
- React 17 之前事件委托到 `document`
- React 17 之后事件委托到根容器

**面试口语：**

React 的事件不是简单直接绑定到每个 DOM 上，而是通过合成事件做了一层封装，统一浏览器差异，并使用事件委托管理。React 17 后事件绑定位置从 `document` 改到根容器。

**底层原理 / 背后逻辑：**

React 会在根容器上统一监听事件，事件触发后根据目标节点向上找到对应 Fiber，再按捕获和冒泡阶段执行组件上声明的事件处理函数。SyntheticEvent 的作用是统一不同浏览器的事件接口，并让事件系统能和 React 的更新优先级结合。比如点击、输入这类离散事件可以使用更高优先级调度更新。

```jsx
function Button() {
  return <button onClick={(event) => console.log(event.currentTarget)}>提交</button>
}
```

### 21. 🔥 组件重复渲染原因

**简要总结：**

- 自身 state 更新
- 父组件重新渲染
- props 引用变化
- context 变化
- 没有合理使用 memo 或拆分组件

**面试口语：**

React 中父组件更新时，默认子组件函数也可能重新执行。即使 props 内容看起来一样，只要对象或函数引用变了，配合浅比较时也会被认为发生变化。

### 22. 🔥 React.memo / PureComponent

**简要总结：**

- `React.memo` 用于函数组件
- `PureComponent` 用于类组件
- 都主要基于浅比较判断是否跳过渲染
- 浅比较只能比较第一层引用

**面试口语：**

`React.memo` 和 `PureComponent` 都是为了减少不必要渲染。它们会对 props 做浅比较，如果没有变化就跳过渲染。但浅比较只比较引用，所以对象、数组、函数要注意引用稳定。

```jsx
const UserCard = React.memo(function UserCard({ user }) {
  return <div>{user.name}</div>
})
```

### 23. ⭐ 减少 React 不必要渲染

**简要总结：**

- 合理拆分组件
- 使用 `React.memo`
- 使用 `useMemo` 缓存计算结果
- 使用 `useCallback` 缓存函数引用
- 避免把频繁变化的 state 放在过高层级
- 拆分 Context
- 长列表使用虚拟列表

**面试口语：**

减少 React 不必要渲染，核心是让变化影响的范围尽量小。可以拆分组件、降低状态位置、稳定 props 引用、使用 memo 类 API，以及把大列表改成虚拟列表。

### 24. ⭐ 受控组件和非受控组件

**简要总结：**

- 受控组件：表单值由 React state 控制
- 非受控组件：表单值由 DOM 自己维护
- 受控组件更方便校验和联动
- 非受控组件代码更少，适合简单表单或文件上传

**面试口语：**

受控组件就是 input 的 value 来自 state，输入变化通过 onChange 更新 state。非受控组件则更多依赖 DOM 自己保存值，React 通过 ref 获取。

```jsx
<input value={keyword} onChange={(event) => setKeyword(event.target.value)} />
```

### 25. ⭐ React Router

**简要总结：**

- 监听 URL 变化
- 根据路由配置匹配组件
- 渲染匹配到的页面组件
- hash 路由基于 `hashchange`
- history 路由基于 History API

**面试口语：**

React Router 的核心是监听路径变化，然后根据路由表匹配对应组件进行渲染。hash 模式不需要服务端配置，history 模式 URL 更自然，但刷新时需要服务端兜底。

```jsx
const router = createBrowserRouter([
  { path: '/users/:id', element: <UserDetail /> }
])
```

### 26. 🔥 Redux

**简要总结：**

- 单一 store 保存状态
- action 描述发生了什么
- reducer 根据旧 state 和 action 返回新 state
- dispatch 触发更新
- subscribe 订阅状态变化
- reducer 必须是纯函数

**面试口语：**

Redux 的核心是单向数据流：视图 dispatch action，reducer 根据 action 计算新 state，store 更新后通知视图。reducer 要保持纯函数，不能直接修改原 state，也不能做异步副作用。

**底层原理 / 背后逻辑：**

Redux 源码核心很小：`createStore` 保存当前 state 和 listeners，`dispatch` 调用 reducer 得到新 state，然后通知 listeners。它不关心 UI 框架，也不负责异步。异步能力来自中间件，React 更新来自 React-Redux 的订阅和 selector 比较。

```js
store.dispatch({ type: 'user/setName', payload: 'Tom' })
```

### 27. ⭐ Redux 中间件

**简要总结：**

- 中间件增强 `dispatch`
- 可以在 action 到 reducer 之间插入逻辑
- 常用于日志、异步请求、错误上报
- 常见中间件：redux-thunk、redux-saga

**面试口语：**

Redux 中间件本质是对 dispatch 的增强。它可以拦截 action，在 action 到达 reducer 之前做日志、异步请求或其他副作用处理。

```js
const middleware = (store) => (next) => (action) => {
  console.log(action.type)
  return next(action)
}
```

### 28. 💡 Zustand

**简要总结：**

- 轻量状态管理库
- 不强制样板代码
- 通过 store 和 selector 获取状态
- 组件只订阅自己需要的状态片段

**面试口语：**

Zustand 比 Redux 更轻量，创建 store 后组件可以按 selector 订阅状态。它的样板代码少，适合中小型项目或不想引入复杂状态管理流程的场景。

```ts
const count = useCounterStore((state) => state.count)
const increment = useCounterStore((state) => state.increment)
```

### 29. ⭐ React SSR 和 Hydration

**简要总结：**

- SSR 在服务端生成 HTML
- 浏览器先展示 HTML，提高首屏和 SEO
- 客户端加载 JS 后进行 hydration
- hydration 后页面才具有完整交互能力

**面试口语：**

React SSR 是服务端先把组件渲染成 HTML 返回给浏览器，用户能更快看到页面。客户端 JS 加载后会进行 hydration，把这些 HTML 接管成可交互的 React 应用。

### 30. 💡 React Server Components

**简要总结：**

- Server Component 在服务端渲染，不打包到客户端 JS
- 可以直接访问服务端资源
- Client Component 才能使用 state、effect、浏览器事件
- 常见于 Next.js App Router

**面试口语：**

Server Component 是在服务端执行的组件，它不进入客户端包，所以能减少客户端 JS 体积，也能直接访问数据库等服务端资源。需要交互、状态和浏览器 API 的部分仍然要写成 Client Component。

### 31. ⭐ Suspense / lazy

**简要总结：**

- `React.lazy` 用于组件懒加载
- `Suspense` 用于展示加载中的 fallback
- 常用于路由级代码分割
- 异步组件加载完成后再渲染真实组件

**面试口语：**

`lazy` 和 `Suspense` 常配合做代码分割。组件还没加载完成时，Suspense 先展示 fallback，加载完成后再显示真实组件。

```jsx
const UserPage = lazy(() => import('./UserPage'))

<Suspense fallback={<Loading />}>
  <UserPage />
</Suspense>
```

### 32. ⭐ Error Boundary

**简要总结：**

- 用于捕获子组件渲染阶段错误
- 只能用类组件实现
- 常用生命周期：`getDerivedStateFromError`、`componentDidCatch`
- 不能捕获事件回调、异步代码、服务端渲染错误

**面试口语：**

Error Boundary 是 React 的错误边界，可以捕获子组件渲染过程中的错误，避免整个应用白屏。但它不能捕获事件处理函数或异步代码里的错误。

### 33. 🔥 为什么不能直接修改 state

**简要总结：**

- 直接修改 state 不会通知 React 更新
- React 依赖引用变化判断数据是否变化
- immutable 数据更利于比较和回溯
- 直接修改可能导致 UI 和状态不一致

**面试口语：**

React 要通过 setState 或 set 函数来触发更新。直接修改 state 只是改了原对象，React 不一定知道发生了变化，也不利于浅比较优化，所以推荐使用不可变更新。

```jsx
setUser({
  ...user,
  name: 'Tom'
})
```

### 34. ⭐ React 18 核心变化

**简要总结：**

- `createRoot` 新根 API
- 自动批处理 Automatic Batching
- 并发渲染能力
- `startTransition`
- Suspense 能力增强
- 新 Hooks：`useId`、`useTransition`、`useDeferredValue`

**面试口语：**

React 18 最大的变化是引入并发渲染相关能力，并扩大了自动批处理范围。对业务开发来说，比较常见的是 `createRoot`、自动批处理、`useTransition` 和 Suspense 能力增强。

## Next.js 面试题

### 1. 🔥 Next.js 是什么

**简要总结：**

- Next.js 是基于 React 的全栈框架
- 提供文件路由、服务端渲染、静态生成、接口路由、构建优化等能力
- App Router 支持 React Server Components、布局嵌套、流式渲染
- 适合 SEO、首屏性能、全栈 React 应用和中大型前端项目

**面试口语：**

Next.js 可以理解成 React 的应用级框架。React 主要负责 UI 层，Next.js 在 React 之上补齐了路由、渲染模式、数据获取、缓存、服务端能力、图片字体优化和部署约定，让 React 项目可以更方便地做 SSR、SSG 和全栈开发。

**底层原理 / 背后逻辑：**

React 默认是客户端渲染库，浏览器先下载 JS，再执行 JS 生成页面。Next.js 的核心价值是把一部分渲染工作前移到服务端或构建阶段：能提前生成的页面提前生成，必须请求时计算的页面在服务端生成，需要交互的部分再交给客户端 hydration。这样可以改善首屏、SEO 和工程约束。

### 2. 🔥 App Router 和 Pages Router

**简要总结：**

- Pages Router 使用 `pages` 目录
- App Router 使用 `app` 目录
- App Router 支持布局嵌套、Server Components、loading、error、Route Handler
- 新项目一般优先 App Router
- 老项目仍可能使用 Pages Router

**面试口语：**

Pages Router 是 Next.js 早期路由方案，核心是 `pages` 文件夹下文件即路由。App Router 是新路由方案，基于 React Server Components，使用 `app` 目录，支持嵌套路由、共享 layout、loading、error、Server Actions 等能力。

```txt
app/
  layout.tsx
  page.tsx
  dashboard/
    layout.tsx
    page.tsx
    loading.tsx
    error.tsx
```

**底层原理 / 背后逻辑：**

App Router 不只是换了目录结构，它把路由切成 segment，每一层 segment 都可以有自己的 `layout`、`page`、`loading`、`error`。这样页面切换时，共享 layout 可以保留，只替换变化的 segment。再结合 Server Components，服务端可以返回更小的 RSC payload，客户端用它更新界面，而不是每次都下载完整页面 JS。

### 3. 🔥 Server Component 和 Client Component

**简要总结：**

- App Router 默认组件是 Server Component
- Server Component 在服务端执行，不进入客户端 JS 包
- Client Component 需要写 `'use client'`
- Client Component 才能使用 `useState`、`useEffect`、浏览器 API、事件
- Server Component 可以直接访问数据库、文件系统、服务端环境变量

**面试口语：**

Next.js App Router 默认是服务端组件。服务端组件适合数据查询和静态展示，不会打进浏览器 JS 包；如果组件需要交互、状态、effect 或浏览器 API，就要加 `'use client'` 变成客户端组件。

```tsx
// app/users/page.tsx，默认是 Server Component
export default async function Page() {
  const users = await getUsers()
  return <UserList users={users} />
}

// app/users/UserSearch.tsx
'use client'

export function UserSearch() {
  const [keyword, setKeyword] = useState('')
  return <input value={keyword} onChange={(e) => setKeyword(e.target.value)} />
}
```

**底层原理 / 背后逻辑：**

Server Component 的结果不是传统意义上的 HTML 或 JS，而是 React Server Component payload，用来描述组件树和客户端组件边界。服务端组件可以执行服务端逻辑，但不能绑定浏览器事件；客户端组件会被打包成 JS，浏览器 hydration 后才能交互。面试要记住：不是整个页面非黑即白，通常是“服务端组件负责数据和结构，客户端组件负责交互”。

### 4. 🔥 Next.js 渲染模式：SSR / SSG / ISR / CSR

**简要总结：**

- SSR：请求到来时服务端生成 HTML
- SSG：构建时生成静态 HTML
- ISR：静态页面按时间或事件重新生成
- CSR：客户端请求数据并渲染
- App Router 中更多通过缓存、动态函数和 fetch 配置决定静态或动态

**面试口语：**

Next.js 的渲染模式要看数据什么时候确定。如果内容构建时就确定，可以 SSG；如果每个用户或每次请求都不同，用 SSR；如果内容大部分时间不变但要定期更新，用 ISR；如果强依赖浏览器状态或实时交互，可以客户端渲染。

```tsx
// 静态缓存，适合变化不频繁的数据
await fetch('https://api.example.com/posts', {
  next: { revalidate: 3600 }
})

// 每次请求都取最新数据
await fetch('https://api.example.com/profile', {
  cache: 'no-store'
})
```

**底层原理 / 背后逻辑：**

SSG 把渲染成本放在构建阶段，用户请求时直接从 CDN 或静态资源服务返回，速度快但实时性弱。SSR 把渲染成本放在请求阶段，数据新但服务器压力更大。ISR 是折中方案：先返回缓存页面，过期后触发重新生成。App Router 下，是否静态更多由数据缓存和动态能力决定，比如读取 `cookies()`、`headers()` 或使用 `no-store` 通常会让路由变动态。

### 5. 🔥 数据获取和缓存机制

**简要总结：**

- Server Component 可以直接 `await fetch`
- Next.js 扩展了 `fetch`，支持缓存和重新验证
- `cache: 'force-cache'` 偏静态缓存
- `cache: 'no-store'` 每次请求重新获取
- `next.revalidate` 支持按时间重新验证
- `revalidatePath` / `revalidateTag` 支持按路径或标签失效缓存

**面试口语：**

Next.js 的数据获取重点不是“在哪里调接口”，而是“这份数据要不要缓存、什么时候失效”。在 Server Component 里可以直接请求数据，Next.js 会根据 `fetch` 的 cache 配置决定是否缓存和什么时候重新验证。

```tsx
export default async function Page() {
  const res = await fetch('https://api.example.com/products', {
    next: { tags: ['products'], revalidate: 60 }
  })
  const products = await res.json()

  return <ProductList products={products} />
}
```

```ts
'use server'

import { revalidateTag } from 'next/cache'

export async function updateProduct() {
  await saveProduct()
  revalidateTag('products')
}
```

**底层原理 / 背后逻辑：**

Next.js 的缓存可以理解成服务端的数据缓存和路由缓存组合。相同请求如果可缓存，就不需要每次都访问真实数据源。`revalidate` 是让缓存有过期时间，`tag` 是给一组缓存打标签，数据变更后可以精确失效。面试里要强调：服务端状态不要一股脑放 Redux，Next.js 更推荐利用服务端数据获取和缓存策略解决首屏数据问题。

### 6. 🔥 Server Actions

**简要总结：**

- Server Actions 可以让前端触发服务端函数
- 常用于表单提交、数据修改、服务端校验
- 文件或函数里使用 `'use server'`
- 可以配合 `revalidatePath`、`revalidateTag` 更新缓存
- 不适合当成普通数据查询接口滥用

**面试口语：**

Server Actions 主要用于 mutation，比如新增、删除、保存表单。它让组件可以调用服务端函数，服务端完成数据库操作后，再通过 revalidate 更新相关缓存。

```tsx
// app/actions.ts
'use server'

export async function createPost(formData: FormData) {
  const title = String(formData.get('title'))
  await db.post.create({ data: { title } })
  revalidatePath('/posts')
}
```

```tsx
// app/posts/page.tsx
import { createPost } from '../actions'

export default function Page() {
  return (
    <form action={createPost}>
      <input name="title" />
      <button type="submit">保存</button>
    </form>
  )
}
```

**底层原理 / 背后逻辑：**

Server Actions 的重点是把“修改数据”的逻辑留在服务端，客户端只提交参数。它不是传统 REST 接口的简单替代品，尤其不适合大量查询，因为 Server Actions 可能形成顺序执行和交互等待。面试可以说：查询优先 Server Component 或 Route Handler，修改数据可以考虑 Server Actions。

### 7. ⭐ Route Handler

**简要总结：**

- App Router 中用 `route.ts` 定义接口
- 支持 `GET`、`POST`、`PUT`、`PATCH`、`DELETE` 等方法
- 基于 Web `Request` / `Response` API
- 适合写 BFF、Webhook、第三方回调、轻量接口
- 同一路径层级不能同时有 `page.tsx` 和 `route.ts`

**面试口语：**

Route Handler 相当于 App Router 里的接口路由。它放在 `app` 目录下的 `route.ts` 文件里，可以处理 HTTP 请求，常用来做 BFF 聚合、登录回调、Webhook 或给客户端组件提供接口。

```ts
// app/api/users/route.ts
export async function GET() {
  const users = await db.user.findMany()
  return Response.json(users)
}

export async function POST(request: Request) {
  const body = await request.json()
  const user = await db.user.create({ data: body })
  return Response.json(user, { status: 201 })
}
```

### 8. ⭐ Middleware

**简要总结：**

- Middleware 在请求完成前执行
- 常用于重定向、鉴权前置判断、A/B 测试、改写请求头
- 文件通常是根目录或 `src` 下的 `middleware.ts`
- 只支持一个入口文件，可以拆模块后汇总
- 不适合慢数据请求、复杂 session 管理、重业务逻辑

**面试口语：**

Middleware 适合做轻量的请求前置处理，比如未登录跳转登录页、根据地区做 rewrite、统一加请求头。它不适合做慢接口请求或复杂业务，因为它处在请求链路前面，逻辑太重会拖慢所有匹配请求。

```ts
// middleware.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function middleware(request: NextRequest) {
  const token = request.cookies.get('token')

  if (!token && request.nextUrl.pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/login', request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ['/dashboard/:path*']
}
```

### 9. ⭐ Streaming 和 loading.tsx

**简要总结：**

- Streaming 可以让服务端分块发送 UI
- `loading.tsx` 会自动提供加载兜底
- Suspense 边界决定哪些内容可以先显示，哪些内容等待异步完成
- 适合慢接口、动态区域、提升首屏感知速度

**面试口语：**

Streaming 的价值是不要让整个页面被最慢的数据卡住。Next.js 可以先返回布局和骨架屏，慢的部分等数据回来后再流式补上。`loading.tsx` 本质上就是给当前路由段自动加 Suspense fallback。

```tsx
// app/dashboard/loading.tsx
export default function Loading() {
  return <div>加载中...</div>
}
```

```tsx
import { Suspense } from 'react'

export default function Page() {
  return (
    <Suspense fallback={<ChartSkeleton />}>
      <SlowChart />
    </Suspense>
  )
}
```

**底层原理 / 背后逻辑：**

传统 SSR 往往要等整棵组件树的数据都准备好再返回 HTML。Streaming 把页面切成多个 Suspense 边界，先把已经就绪的部分发给浏览器，未就绪部分后续再补。这样不能让接口本身变快，但能让用户更早看到可用页面。

### 10. ⭐ next/link、路由预取和导航

**简要总结：**

- `next/link` 用于客户端导航
- 视口内链接通常会自动预取
- App Router 导航时复用共享 layout
- 动态路由可以结合 loading 和 streaming 提升体验

**面试口语：**

Next.js 的页面跳转不是简单刷新页面。`Link` 会做客户端导航和预取，用户真正点击时，目标路由需要的资源可能已经提前加载。App Router 还能复用不变的 layout，只更新变化的路由段，所以导航体验更接近 SPA。

```tsx
import Link from 'next/link'

export function Nav() {
  return <Link href="/dashboard">工作台</Link>
}
```

### 11. ⭐ next/image、next/font、next/script

**简要总结：**

- `next/image` 优化图片尺寸、格式、懒加载
- `next/font` 优化字体加载，减少布局偏移
- `next/script` 控制第三方脚本加载策略
- 都是围绕性能和 Web Vitals 做内置优化

**面试口语：**

Next.js 内置了很多性能组件。`Image` 解决图片尺寸、懒加载和格式优化；`font` 减少字体加载导致的 CLS；`Script` 可以控制第三方脚本什么时候加载，避免阻塞首屏。

```tsx
import Image from 'next/image'

export function Avatar() {
  return <Image src="/avatar.png" width={80} height={80} alt="头像" />
}
```

```tsx
import Script from 'next/script'

export function Analytics() {
  return <Script src="/analytics.js" strategy="afterInteractive" />
}
```

### 12. ⭐ Metadata 和 SEO

**简要总结：**

- App Router 支持 `metadata` 静态配置
- 动态 SEO 可用 `generateMetadata`
- 服务端渲染可以让搜索引擎更容易拿到首屏内容
- SEO 不只靠 meta，还包括语义化、性能、结构化数据

**面试口语：**

Next.js 适合 SEO 的原因是它可以在服务端或构建阶段生成 HTML，搜索引擎不必等客户端 JS 执行完才能看到内容。App Router 里可以用 `metadata` 或 `generateMetadata` 管理标题、描述和 Open Graph 信息。

```tsx
export const metadata = {
  title: '商品列表',
  description: '查看最新商品'
}

export async function generateMetadata({ params }) {
  const product = await getProduct(params.id)

  return {
    title: product.name,
    description: product.summary
  }
}
```

### 13. 🔥 Next.js 性能优化

**简要总结：**

- 静态优先，动态按需
- 合理使用缓存和 revalidate
- 避免把大组件都写成 Client Component
- 用 Streaming 避免慢数据阻塞整页
- 图片、字体、脚本使用 Next.js 内置优化能力
- 按路由自动代码分割

**面试口语：**

Next.js 性能优化核心是减少客户端 JS、减少服务端重复计算、减少首屏阻塞。能在服务端做的数据获取不要放到客户端，能缓存的数据不要每次请求都查，能流式返回的慢区域不要阻塞整个页面。

**底层原理 / 背后逻辑：**

Next.js 的性能优化可以按三条线讲：第一是渲染线，静态生成和缓存减少请求时计算；第二是传输线，Server Component 减少客户端 JS，图片字体脚本优化减少资源成本；第三是体验线，Streaming 和 Suspense 让页面先显示可用部分。面试回答时不要只说“用了 Image”，要说明它解决的是 LCP、CLS 或 JS 体积问题。

### 14. ⚠️ Next.js 常见坑

**简要总结：**

- 误把所有组件都写成 Client Component，导致 JS 包变大
- 在 Server Component 中使用 `window`、`document`、`useState`
- 缓存策略没想清楚，导致数据不更新或请求过多
- Middleware 写重逻辑，拖慢请求链路
- SSR 中服务端和客户端渲染结果不一致，导致 hydration mismatch

**面试口语：**

Next.js 最大的坑通常来自“服务端和客户端边界没分清”。需要交互的组件才加 `'use client'`，服务端组件不要访问浏览器 API；数据获取要先判断静态、动态还是可重新验证；Middleware 只做轻量逻辑。

## Vue 和 React 对比

### 1. 🔥 核心思想对比

**Vue：**

- 模板语法
- 响应式系统自动追踪依赖
- 单文件组件组织代码
- 上手成本相对低

**React：**

- JSX
- 状态变化触发组件重新渲染
- 函数组件 + Hooks
- 更强调 JavaScript 表达能力

**面试口语：**

Vue 更依赖响应式系统自动追踪依赖，开发体验偏模板和配置；React 更强调用 JavaScript 描述 UI，状态变化后重新执行组件函数。两者都是组件化和声明式 UI，只是更新模型和写法不同。

### 2. ⭐ 更新机制对比

**简要总结：**

- Vue 能通过依赖收集知道哪些组件依赖了哪些数据
- React 默认是状态变化后从组件开始重新渲染子树
- Vue 更新粒度通常更细
- React 更依赖 memo、组件拆分和状态位置控制优化

**面试口语：**

Vue 有响应式依赖收集，数据变化时能更精确地知道哪些组件需要更新。React 的模型更简单直接，state 变化后重新执行组件函数，再通过 Diff 和 memo 等机制减少真实 DOM 更新和不必要渲染。

### 3. ⭐ 选型思路

**简要总结：**

- 中后台、团队需要统一规范：Vue 很顺手
- 强 JavaScript 表达、复杂交互、生态组合：React 很灵活
- 大团队项目更看重规范、工程化、团队熟悉度
- 真实选型不要只看框架，要看生态和团队经验

**面试口语：**

我不会简单说哪个框架更好，而是看项目场景和团队情况。Vue 上手快、约定清晰，中后台开发效率高；React 灵活度高，生态很大，复杂交互和跨端生态选择更多。
