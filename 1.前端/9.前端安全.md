# 前端安全

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 安全基础

### 1. 🔥 前端安全主要关注什么

**简要总结：**

- XSS：攻击者把恶意脚本注入页面
- CSRF：利用用户登录态发起非本人意愿请求
- 点击劫持：页面被 iframe 嵌套诱导点击
- 敏感信息泄露：token、密钥、源码、错误信息泄露
- 依赖安全：第三方包漏洞或供应链攻击

**面试口语：**

前端安全重点是保护用户身份、页面执行环境和数据边界。常见攻击包括 XSS、CSRF、点击劫持、依赖漏洞和敏感信息泄露。安全不是只靠前端，通常需要前端、后端、网关和浏览器安全策略一起配合。

**底层原理 / 背后逻辑：**

浏览器安全的核心是“隔离”和“限制能力”。同源策略限制跨源读取，CSP 限制脚本来源，Cookie 属性限制凭证访问和跨站携带，前端转义和过滤限制不可信内容进入 DOM 执行环境。面试要能讲清楚攻击如何发生，以及防护为什么有效。

### 2. 🔥 XSS

**简要总结：**

- XSS 是跨站脚本攻击
- 攻击者让恶意 JS 在用户浏览器里执行
- 常见类型：存储型、反射型、DOM 型
- 防护核心：不信任用户输入，输出时转义，限制脚本执行

**面试口语：**

XSS 的本质是攻击者把数据变成了代码。比如评论内容本来应该当文本展示，但如果直接用 `innerHTML` 插入页面，里面的 `<script>` 或事件属性就可能执行。

```js
// 危险：把不可信内容当 HTML 执行
container.innerHTML = userInput

// 更安全：把不可信内容当纯文本
container.textContent = userInput
```

**底层原理 / 背后逻辑：**

浏览器解析 HTML 时，会把标签、属性、事件处理器当成可执行结构。XSS 就是利用这个解析过程，把用户输入从“普通字符串”变成“页面代码”。防护时要在输出到不同上下文时做不同处理：HTML 文本要转义 `<`、`>`，属性要处理引号，URL 要限制协议，富文本要白名单过滤。

📌 重点记忆：XSS 不是“输入有问题”，而是“不可信输入进入了可执行上下文”。

### 3. 🔥 XSS 防护

**简要总结：**

- 默认使用框架模板插值，不手写 `innerHTML`
- 必须渲染 HTML 时做白名单过滤
- 使用 CSP 限制脚本来源
- Cookie 设置 `HttpOnly` 降低 token 被 JS 读取的风险
- 对 URL、富文本、Markdown 等高风险输入特别处理

**面试口语：**

防 XSS 首先是输出转义，能用框架插值就不要自己拼 HTML。必须展示富文本时，用白名单过滤，只允许安全标签和属性。再配合 CSP 限制脚本来源，即使有注入点，也尽量不让恶意脚本执行。

```html
<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'self'; script-src 'self'"
/>
```

```js
function escapeHTML(value) {
  return value
    .replaceAll('&', '&amp;')
    .replaceAll('<', '&lt;')
    .replaceAll('>', '&gt;')
    .replaceAll('"', '&quot;')
    .replaceAll("'", '&#39;')
}
```

**底层原理 / 背后逻辑：**

转义的作用是让特殊字符失去 HTML 语义，比如 `<script>` 变成普通文本。CSP 的作用是从浏览器层面限制脚本、样式、图片等资源的加载来源。`HttpOnly` 不能防止 XSS 发生，但可以让恶意 JS 读不到 Cookie，降低登录凭证被偷的风险。

### 4. 🔥 CSRF

**简要总结：**

- CSRF 是跨站请求伪造
- 攻击者借用用户登录态发请求
- 常发生在 Cookie 自动携带登录态的系统中
- 防护：SameSite、CSRF Token、校验 Origin / Referer

**面试口语：**

CSRF 的本质是浏览器会自动带 Cookie。用户登录了 A 网站，再访问恶意 B 网站，B 网站可以诱导浏览器向 A 发请求。如果 A 只看 Cookie，就可能把这个请求当成用户本人操作。

```html
<!-- 恶意页面诱导浏览器请求目标站点 -->
<img src="https://bank.example.com/transfer?to=attacker&amount=1000" />
```

**底层原理 / 背后逻辑：**

CSRF 利用的是“请求能发出去”和“Cookie 自动携带”。同源策略主要限制 JS 读取跨源响应，不阻止表单、图片这类跨站请求发送。防护要让攻击者无法伪造完整请求：`SameSite` 限制跨站 Cookie，CSRF Token 要求请求带一个攻击者拿不到的随机值，Origin/Referer 校验请求来源。

```http
Set-Cookie: sid=abc; HttpOnly; Secure; SameSite=Lax
```

📌 重点记忆：XSS 是执行恶意脚本，CSRF 是借用用户身份发请求。

### 5. ⭐ Token 存哪里更安全

**简要总结：**

- `localStorage` 容易被 XSS 读取
- Cookie 可配合 `HttpOnly`，JS 读不到
- Cookie 需要额外考虑 CSRF
- 没有绝对安全方案，要结合业务风险选择

**面试口语：**

如果 token 存 localStorage，使用方便，但一旦 XSS，攻击者可以直接读取。HttpOnly Cookie 能降低被 JS 偷走的风险，但要处理 CSRF。真实项目里会结合 SameSite、CSRF Token、短 token、刷新 token 和服务端风控。

**底层原理 / 背后逻辑：**

localStorage 是 JS 可读写的持久化存储，所以怕 XSS。Cookie 是浏览器请求凭证机制，设置 HttpOnly 后 JS 不能读取，但浏览器仍会按规则自动携带，所以怕 CSRF。安全设计要先判断主要威胁模型，而不是背一个固定答案。

### 6. ⭐ 点击劫持

**简要总结：**

- 攻击者把目标网站放进透明 iframe
- 用户以为点击的是攻击页面，实际点到目标网站
- 防护：`X-Frame-Options`、CSP `frame-ancestors`

**面试口语：**

点击劫持就是攻击者把你的网站嵌到 iframe 里，再用透明层诱导用户点击。防护一般由服务端返回响应头，禁止页面被不可信站点嵌套。

```http
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'self'
```

### 7. ⭐ CORS 安全

**简要总结：**

- CORS 是浏览器跨域读取响应的放行机制
- 不是服务端鉴权机制
- 携带凭证时 `Access-Control-Allow-Origin` 不能是 `*`
- 不能只靠 CORS 保护接口

**面试口语：**

CORS 解决的是浏览器允不允许前端读取跨域响应，不等于接口安全。接口是否能访问，还是要靠登录态、权限校验、签名、风控等服务端逻辑。

```http
Access-Control-Allow-Origin: https://admin.example.com
Access-Control-Allow-Credentials: true
```

**底层原理 / 背后逻辑：**

跨域请求很多时候已经到达服务端，CORS 只是浏览器收到响应后决定要不要把内容交给 JS。攻击者用 curl 或服务端脚本请求接口时不受浏览器 CORS 限制，所以服务端必须做真正的鉴权和权限判断。

### 8. 🔥 前端依赖安全

**简要总结：**

- 第三方 npm 包可能有漏洞
- 供应链攻击可能通过依赖包注入恶意代码
- 锁文件能固定版本，但不能证明版本安全
- CI 中应接入依赖扫描和审计

**面试口语：**

前端项目依赖很多，安全风险不只在业务代码，也在第三方包。项目里一般会固定锁文件、定期升级依赖、使用 npm audit 或安全扫描工具，并避免随便引入无人维护的小包。

```bash
npm audit
pnpm audit
```

**底层原理 / 背后逻辑：**

构建工具会把第三方依赖打进最终产物。如果依赖包在安装脚本、构建时代码或运行时代码里包含恶意逻辑，就可能泄露环境变量、篡改页面或窃取用户数据。锁文件解决“装到哪个版本”，安全扫描解决“这个版本是否有已知风险”。

### 9. ⭐ 敏感信息泄露

**简要总结：**

- 前端环境变量会进入浏览器产物
- 不能把密钥、数据库密码、私有 token 放前端
- Source Map 生产环境要控制访问
- 错误信息不要暴露内部实现细节

**面试口语：**

前端代码最终会发到用户浏览器，所以任何写进前端包里的密钥都不能算秘密。环境变量只是构建时注入，不是加密。真正的密钥应该留在服务端。

```js
// 可以：公开接口地址
const apiBaseURL = import.meta.env.VITE_API_BASE_URL

// 不可以：私有密钥
const secret = import.meta.env.VITE_PRIVATE_SECRET
```

### 10. ⭐ 安全面试回答模板

**回答思路：**

- 先说明攻击原理
- 再说明攻击发生的前提
- 然后说明防护手段
- 最后说明防护边界

**面试口语：**

比如讲 XSS，我会先说它是把不可信输入变成可执行脚本；发生前提是输入没有正确转义或过滤；防护包括输出转义、富文本白名单、CSP、HttpOnly；同时说明 HttpOnly 不能阻止 XSS，只能降低 Cookie 被盗风险。
