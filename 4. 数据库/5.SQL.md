## 查询基础

### 1. 🔥 SQL 查询执行顺序

**简要总结：**

- 逻辑顺序：FROM、JOIN、WHERE、GROUP BY、HAVING、SELECT、ORDER BY、LIMIT
- 实际执行会被优化器改写
- SQL 描述结果，不完全描述执行过程
- 性能要看执行计划

**面试口语：**

SQL 写法上 SELECT 在前，但逻辑上通常先确定数据来源，再过滤，再分组聚合，最后排序分页。真实执行时优化器会根据索引和统计信息调整执行方式。

**底层原理 / 背后逻辑：**

数据库优化器会把 SQL 转成执行计划。它关心哪些表先读、用什么索引、JOIN 怎么做、扫描多少行、是否需要排序和临时表。所以面试里不能只会写 SQL，还要能解释 SQL 为什么慢。

### 2. 🔥 WHERE 和 HAVING 区别

**简要总结：**

- WHERE 在分组前过滤行
- HAVING 在分组后过滤聚合结果
- 能用 WHERE 就不要放 HAVING
- WHERE 更容易利用索引减少扫描量

**面试口语：**

WHERE 是先过滤原始数据，HAVING 是分组之后过滤聚合结果。比如统计订单数大于 10 的用户，要先 WHERE 过滤有效订单，再 GROUP BY 用户，再 HAVING count 大于 10。

**底层原理 / 背后逻辑：**

WHERE 越早过滤，后面参与 JOIN、GROUP BY、ORDER BY 的数据越少。HAVING 已经到了聚合之后，前面该扫的数据通常已经扫了，所以滥用 HAVING 会让数据库做更多无效工作。

## JOIN 与聚合

### 1. 🔥 JOIN 类型

**简要总结：**

- INNER JOIN：只保留两边匹配的数据
- LEFT JOIN：保留左表全部数据，右表没有则为 NULL
- RIGHT JOIN：保留右表全部数据
- 多表 JOIN 要注意数据量放大

**面试口语：**

INNER JOIN 适合只要匹配成功的数据，LEFT JOIN 适合主表数据必须保留，右表信息可有可无的场景，比如查询用户和他的最后一次登录记录。

**底层原理 / 背后逻辑：**

JOIN 的本质是两组数据按条件匹配。小表驱动大表、连接字段有索引，通常会更快。连接条件不合理或一对多关系没处理好，会让结果集倍数放大，后面的排序和聚合也会变慢。

### 2. ⭐ GROUP BY 和窗口函数

**简要总结：**

- GROUP BY 会把多行聚合成一行
- 窗口函数保留原始行，同时计算分组统计
- 常见窗口函数：row_number、rank、sum over
- 适合排名、分组取 Top N、累计统计

**面试口语：**

GROUP BY 会改变结果粒度，窗口函数不会压缩原始行。比如要查每个用户最近一笔订单，可以用 row_number 按用户分组排序，再取排名第一。

**底层原理 / 背后逻辑：**

聚合需要维护每个分组的中间状态，窗口函数通常还需要按分区排序。数据量大时，分组和排序都可能消耗大量内存，甚至落盘，所以相关字段的索引和过滤条件很重要。

## 分页与写入

### 1. 🔥 深分页问题

**简要总结：**

- `LIMIT 100000, 20` 会跳过大量数据
- offset 越大，扫描成本越高
- 可用游标分页优化
- 必须有稳定排序字段

**面试口语：**

深分页慢是因为数据库不是直接跳到第 100000 行，而是通常要先找到并丢弃前面的数据。优化时可以用 `where id > last_id order by id limit 20` 这种游标分页。

**底层原理 / 背后逻辑：**

分页必须先确定顺序，再取目标范围。offset 很大时，前面的数据虽然不返回，但仍可能参与扫描和排序。游标分页利用索引从上次位置继续向后读，避免重复扫描大量历史数据。

### 2. ⭐ UPSERT

**简要总结：**

- MySQL：`insert ... on duplicate key update`
- PostgreSQL：`insert ... on conflict ... do update`
- 依赖唯一键判断冲突
- 常用于幂等写入

**面试口语：**

UPSERT 适合“有就更新，没有就插入”的场景，比如第三方回调按业务单号写入结果。关键是表上要有唯一约束，否则数据库不知道什么叫冲突。

**底层原理 / 背后逻辑：**

UPSERT 的本质是把并发下的先查再写交给数据库原子处理。应用层先 SELECT 再 INSERT，在并发下可能两个请求都查不到，然后重复插入。唯一索引加 UPSERT 能把冲突判断下沉到数据库。
