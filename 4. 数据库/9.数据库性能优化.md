# 数据库性能优化

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 排查思路

### 1. 🔥 数据库慢怎么排查

**简要总结：**

- 先确认是单条 SQL 慢还是整体负载高
- 看慢 SQL 日志
- 用 EXPLAIN 看执行计划
- 看索引、扫描行数、排序、临时表
- 再看锁等待、连接池、磁盘 IO、CPU

**面试口语：**

我不会一上来就说分库分表。会先定位慢在哪里：是 SQL 没走索引，还是扫描行数太多，还是锁等待，还是连接池不够，还是数据库整体资源打满。

**底层原理 / 背后逻辑：**

数据库性能问题最终通常落到 CPU、内存、磁盘 IO、锁等待和网络连接。慢 SQL 会放大资源消耗，长事务会造成锁等待，连接池不合理会让请求排队。优化要先定位瓶颈，再决定手段。

### 2. 🔥 EXPLAIN 看什么

**简要总结：**

- 查询访问类型
- 使用了哪个索引
- 预估扫描行数
- 是否 Using filesort
- 是否 Using temporary
- 是否回表或覆盖索引

**面试口语：**

EXPLAIN 主要看有没有走合适索引、扫描行数是不是太大、有没有文件排序和临时表。如果扫描行数很大，即使结果只返回几条，也说明中间过程很重。

**底层原理 / 背后逻辑：**

执行计划是优化器根据统计信息做出的成本估算。它不一定百分百等于真实执行成本，但能暴露查询路径。性能优化要关注“数据库为了得到结果做了多少无效工作”。

## 常见优化

### 1. 🔥 SQL 优化

**简要总结：**

- 避免 `SELECT *`
- 过滤条件尽量命中索引
- 避免索引列函数计算
- 大分页改游标分页
- 大批量写入分批处理
- 避免在业务高峰做大表 DDL

**面试口语：**

SQL 优化的核心是减少扫描、减少排序、减少回表、减少锁时间。能用索引定位就不要全表扫，能少返回字段就不要查全部字段。

**底层原理 / 背后逻辑：**

数据库每多扫描一行、每多排序一批数据、每多回表一次，都会消耗 CPU、内存和 IO。SQL 优化不是语法游戏，而是减少数据库为了回答问题所做的中间工作。

### 2. ⭐ 架构优化

**简要总结：**

- 缓存热点数据
- 读写分离
- 冷热数据拆分
- 历史数据归档
- 分库分表
- 引入搜索引擎或数仓

**面试口语：**

当单条 SQL 和索引已经优化过，数据库整体压力仍然很高时，才考虑架构优化。比如热点读放 Redis，报表查询走数仓，历史数据归档，读多场景做读写分离。

**底层原理 / 背后逻辑：**

架构优化本质是把不同类型的负载拆开。核心交易库负责短事务和强一致，缓存负责热点读，搜索引擎负责复杂检索，数仓负责统计分析。每个系统做自己擅长的事，整体性能才稳定。

## 线上经验

### 1. 🔥 慢查询影响线上服务

**简要总结：**

- 慢查询占用连接
- 大量扫描挤占 Buffer Pool
- 排序和临时表消耗内存或磁盘
- 长事务导致锁等待
- 可能引发接口超时和雪崩

**面试口语：**

一个慢 SQL 不只是自己慢，它可能占住连接、拖慢磁盘 IO、污染缓存页，还可能持有锁，导致其他正常请求也变慢。

**底层原理 / 背后逻辑：**

数据库是共享资源。慢查询会抢占公共的 CPU、内存、IO、连接和锁。面试里说性能优化时，要从单条 SQL 扩展到整个系统资源竞争，这样更像真实线上排查思路。
