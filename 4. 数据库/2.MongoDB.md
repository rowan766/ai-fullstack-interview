## 文档数据库基础

### 1. 🔥 MongoDB 适合什么场景

**简要总结：**

- 半结构化数据
- 字段变化频繁的数据
- 文档整体读写的数据
- 日志、配置、用户画像、内容管理、埋点数据
- 不适合强依赖复杂 JOIN 的核心交易场景

**面试口语：**

MongoDB 适合数据结构不完全固定、经常按一个整体读取的场景。比如用户扩展信息、配置、内容详情，字段可能经常变化，用文档模型会比频繁改关系表更灵活。

**底层原理 / 背后逻辑：**

MongoDB 的核心是文档聚合思想：把一次业务经常一起读取的数据放在同一个文档里，减少多表关联。但这种灵活性是有代价的，字段冗余、数据一致性、复杂统计和跨文档事务都会更难处理。

### 2. 🔥 文档模型和关系模型区别

**简要总结：**

- 关系模型：按实体拆表，靠主外键表达关系
- 文档模型：按访问场景聚合数据
- 关系模型更强调规范化和一致性
- 文档模型更强调读写局部性和灵活结构

**面试口语：**

关系型数据库通常先分析实体关系，比如用户表、订单表、商品表。MongoDB 更关注这个接口一次需要什么数据，如果总是整体读取，就可以放在一个文档里。

**底层原理 / 背后逻辑：**

关系模型把冗余降到低，更新一个实体通常只改一处；文档模型为了读取方便，可能把数据冗余到多个文档。读快了，写一致性就变复杂了。面试回答要说出这个取舍，而不是只说 MongoDB 灵活。

## 设计与索引

### 1. 🔥 MongoDB 表结构怎么设计

**简要总结：**

- 优先根据查询路径设计文档结构
- 经常一起读取的数据可以内嵌
- 独立生命周期的数据适合引用
- 文档不能无限膨胀
- 需要提前考虑索引和数据增长

**面试口语：**

MongoDB 设计时我会先看接口怎么查、怎么改。如果子数据和主数据生命周期一致，并且经常一起返回，可以内嵌；如果子数据会独立变化或数量无限增长，就更适合单独集合引用。

**底层原理 / 背后逻辑：**

内嵌可以减少查询次数，但文档过大会影响读写性能，也可能造成热点文档频繁更新。引用更接近关系型数据库拆表，灵活但需要额外查询或应用层组装。MongoDB 的设计核心不是“不要关联”，而是控制关联成本。

### 2. ⭐ MongoDB 索引

**简要总结：**

- 常用索引：单字段索引、复合索引、唯一索引、TTL 索引、文本索引
- 查询条件和排序字段要匹配索引
- 数组字段会产生多键索引
- 索引也会增加写入成本和存储空间

**面试口语：**

MongoDB 也需要索引。没有索引时，大集合查询同样会变成全量扫描。复合索引也要关注字段顺序，要根据过滤条件、排序条件和选择性来设计。

**底层原理 / 背后逻辑：**

MongoDB 索引本质也是额外维护一套可快速查找的数据结构。查询快是因为能通过索引定位候选文档，写变慢是因为写文档时还要同步更新索引。数组字段的多键索引会为数组元素建立索引项，因此要注意索引膨胀。

## 一致性与事务

### 1. ⭐ MongoDB 事务和一致性

**简要总结：**

- 单文档操作天然原子
- 多文档事务是支持的，但成本更高
- 副本集提供高可用
- 写关注和读关注会影响一致性和性能

**面试口语：**

MongoDB 单个文档内的修改是原子的，所以很多场景会把需要原子修改的数据放在一个文档里。多文档事务虽然支持，但不应该滥用，否则就失去了文档数据库的性能优势。

**底层原理 / 背后逻辑：**

MongoDB 的优势来自文档局部性。如果一个业务动作总要跨多个集合、多个文档强事务处理，那就说明这个场景可能更适合关系型数据库。面试要能说出：选 MongoDB 不是为了逃避设计，而是为了匹配数据访问模式。
