# 主从 / 高可用

## 主从复制

### 1. 🔥 主从复制解决什么问题

**简要总结：**

- 读扩展
- 数据备份
- 故障切换基础
- 报表查询隔离
- 不能天然解决所有一致性问题

**面试口语：**

主从复制主要是把主库的数据同步到从库。主库负责写，从库可以承担读请求、备份或报表查询。它提升了可用性和读能力，但会带来主从延迟。

**底层原理 / 背后逻辑：**

复制的本质是日志重放。主库把变更写到日志里，从库拉取日志并按顺序执行。MySQL 常见是 binlog 复制，PostgreSQL 是 WAL 流复制。只要是异步复制，就可能存在延迟。

### 2. 🔥 主从延迟

**简要总结：**

- 主库写入太快
- 从库重放慢
- 网络延迟
- 大事务
- 从库机器性能不足

**面试口语：**

主从延迟意味着刚写入主库的数据，从库可能暂时查不到。所以像下单后立即查订单、支付状态确认这类强一致读，应该读主库，不能无脑读从库。

**底层原理 / 背后逻辑：**

从库同步要经历日志传输和日志重放。主库提交成功只代表主库完成，不代表所有从库都完成。读写分离提升读能力的代价，就是应用要识别哪些读能接受延迟。

## 高可用

### 1. 🔥 高可用切换

**简要总结：**

- 监控主库是否故障
- 选择合适从库提升为新主
- 应用连接切换到新主
- 要处理数据丢失和脑裂风险
- 切换后要修复旧主

**面试口语：**

高可用不是简单多加一台机器。主库挂了以后，要判断哪个从库数据最新，把它提升为新主，并让应用切过去，同时避免两个主同时写造成脑裂。

**底层原理 / 背后逻辑：**

故障切换的难点在于“谁是最新数据源”。异步复制下，某些从库可能还没追上主库。如果直接提升落后的从库，就可能丢数据。自动切换必须结合心跳、复制位点、仲裁和应用连接管理。

### 2. ⭐ 读写分离

**简要总结：**

- 写请求走主库
- 可接受延迟的读请求走从库
- 强一致读走主库
- 需要连接路由或中间件支持

**面试口语：**

读写分离不是把所有 SELECT 都丢到从库。刚写完马上读、支付结果、权限变更这类强一致数据，最好读主库，普通列表和报表查询可以读从库。

**底层原理 / 背后逻辑：**

读写分离把读压力拆到多个节点，但复制是有时间差的。应用层要根据业务一致性要求路由请求，否则用户可能刚保存成功，刷新页面却看不到数据。

## Redis 高可用

### 1. ⭐ Sentinel 和 Cluster

**简要总结：**

- Sentinel 负责监控和故障转移
- Cluster 负责分片和扩展
- 主从复制提供副本
- 集群模式要关注 key 分布和跨 slot 限制

**面试口语：**

Redis Sentinel 主要解决主节点故障自动切换，Cluster 主要解决单机内存和吞吐上限，把数据分散到多个节点。

**底层原理 / 背后逻辑：**

Sentinel 是高可用控制面，负责发现故障、投票、选新主。Cluster 是数据分片方案，用 slot 把 key 分散到不同节点。一个偏可用性，一个偏扩展性。
