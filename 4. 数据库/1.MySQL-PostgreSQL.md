## 关系型数据库基础

### 1. 🔥 关系型数据库适合什么场景

**简要总结：**

- 强结构化业务数据
- 需要事务一致性的核心数据
- 需要复杂 SQL 查询和统计
- 需要唯一约束、外键、索引等数据约束
- 常见场景：用户、订单、支付、权限、任务、审计日志

**面试口语：**

关系型数据库适合保存结构清晰、关系明确、对一致性要求高的数据。比如订单创建、库存扣减、支付流水这些数据，不能只追求写得快，还要保证状态正确、可追溯、可恢复。

**底层原理 / 背后逻辑：**

关系型数据库不是简单把数据放进表里，它的价值在于“结构约束 + 查询优化 + 事务日志”。表结构定义数据边界，约束保证基础正确性，优化器选择执行路径，事务日志保证异常时可以回滚或恢复。面试回答时要体现：核心业务数据要先保证正确，再考虑性能。

### 2. 🔥 MySQL 和 PostgreSQL 的区别

**简要总结：**

- MySQL：互联网项目常见，生态成熟，部署和运维经验多
- PostgreSQL：SQL 标准支持更完整，复杂查询能力强，扩展能力强
- PostgreSQL 对 JSON、数组、窗口函数、CTE、GIS 等支持更强
- MySQL 在中小型 Web 项目、后台系统、业务系统中非常常见

**面试口语：**

MySQL 更常见，生态成熟，很多互联网业务系统默认会选它。PostgreSQL 更像一个能力更完整的关系型数据库，在复杂 SQL、数据分析、JSON、GIS、自定义扩展这些场景更有优势。

**底层原理 / 背后逻辑：**

两者底层都围绕磁盘页、缓存、索引、事务日志工作，但设计取向不同。MySQL 特别是 InnoDB 更偏高并发 OLTP 场景，PostgreSQL 更强调标准 SQL、扩展能力和复杂查询表达力。面试时不要说谁绝对更好，要结合业务复杂度、团队经验、生态和运维成本回答。

### 3. ⭐ OLTP 和 OLAP

**简要总结：**

- OLTP：在线事务处理，关注高并发读写和事务正确性
- OLAP：在线分析处理，关注大数据量统计分析
- 业务库通常是 OLTP
- 报表、数仓、BI 更偏 OLAP

**面试口语：**

OLTP 面向日常业务操作，比如下单、支付、修改用户资料；OLAP 面向分析统计，比如按月销售额、用户留存、转化漏斗。业务库不能随便跑很重的统计 SQL，否则会影响线上请求。

**底层原理 / 背后逻辑：**

OLTP 查询通常是小范围、高频、低延迟，依赖索引快速定位少量行。OLAP 通常扫描大量数据做聚合，消耗 CPU、内存和 IO。把两类负载混在一个库里，重查询可能拖慢事务写入，所以实际系统常做读库、报表库或数仓同步。

## 存储与日志

### 1. 🔥 数据库为什么按页读写

**简要总结：**

- 磁盘 IO 的基本成本很高
- 数据库通常按 page 组织数据
- 一次读写一页比一行一行访问更高效
- Buffer Pool 会缓存热点数据页

**面试口语：**

数据库不会真的每次只从磁盘读一行数据，而是按页读取。页被加载到内存后，多次查询可以直接命中缓存，减少磁盘 IO。

**底层原理 / 背后逻辑：**

磁盘随机 IO 成本远高于内存访问。数据库把数据组织成固定大小的数据页，查询时把页加载进 Buffer Pool，修改时先改内存页，再通过日志保证持久化。这样可以把大量随机磁盘操作变成更可控的页缓存和顺序日志写入。

### 2. 🔥 redo log / undo log / binlog / WAL

**简要总结：**

- redo log：保证已提交事务崩溃后能恢复
- undo log：支持事务回滚和 MVCC 历史版本
- binlog：MySQL 逻辑变更日志，常用于复制和恢复
- WAL：PostgreSQL 的预写日志，用于恢复和复制

**面试口语：**

事务提交不是简单把数据立刻写进磁盘文件，而是先写日志。redo log 保证提交后的修改能恢复，undo log 保证失败时能回滚，binlog 或 WAL 可以用于主从复制和时间点恢复。

**底层原理 / 背后逻辑：**

日志比随机修改数据页更适合顺序写。数据库先把“怎么改”写进日志，再慢慢刷脏页。崩溃后根据日志判断哪些事务已提交、哪些没提交，已提交的重做，未提交的回滚。这就是预写日志思想：先保证日志可靠，再让数据页异步落盘。
