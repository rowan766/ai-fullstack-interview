## Redis 基础

### 1. 🔥 Redis 常见用途

**简要总结：**

- 缓存热点数据
- 分布式锁
- 计数器、排行榜、限流
- Session 和验证码
- 简单队列、延迟任务辅助

**面试口语：**

Redis 通常不是替代 MySQL 的主数据库，而是加速层或协调层。核心数据还是落到关系型数据库，Redis 用来解决高频读、短期状态、计数和并发控制问题。

**底层原理 / 背后逻辑：**

Redis 快的关键是内存访问、紧凑数据结构、高效网络模型，以及命令执行主路径单线程，减少了锁竞争。它快，也意味着容量和持久性要特别关注，所以不能把所有数据无脑放 Redis。

### 2. 🔥 Redis 为什么快

**简要总结：**

- 数据主要在内存中
- 单线程命令执行避免大量锁竞争
- IO 多路复用处理网络连接
- 数据结构针对常见场景优化
- 简单命令时间复杂度低

**面试口语：**

Redis 快不是只有“内存”一个原因。它还用单线程执行命令避免多线程锁竞争，用 IO 多路复用处理大量连接，并且内置字符串、哈希、集合、有序集合等高效数据结构。

**底层原理 / 背后逻辑：**

内存访问比磁盘快很多，但如果网络和线程模型设计不好，仍然扛不住高并发。Redis 的事件循环会监听多个 socket，哪个连接就绪就处理哪个连接的命令。命令执行串行化后，很多并发安全问题被简化了。

## 数据结构

### 1. 🔥 五大基础类型

**简要总结：**

- String：缓存值、计数器、分布式锁
- Hash：对象字段缓存
- List：队列、最新列表
- Set：去重、交集、共同关注
- ZSet：排行榜、延迟队列

**面试口语：**

Redis 不只是 key-value，它的价值在于提供了贴近业务的数据结构。比如排行榜用 ZSet，去重用 Set，用户信息可以用 Hash，计数器用 String 的自增。

**底层原理 / 背后逻辑：**

不同数据结构对应不同操作复杂度。选错结构会让本来简单的问题变复杂，比如排行榜如果用普通 List，每次排序都很重；ZSet 内部维护分值有序性，可以高效按分数范围查询。

## 缓存问题

### 1. 🔥 缓存穿透、击穿、雪崩

**简要总结：**

- 缓存穿透：查询不存在的数据，缓存和数据库都没有
- 缓存击穿：热点 key 过期，大量请求打到数据库
- 缓存雪崩：大量 key 同时过期或 Redis 故障
- 解决：空值缓存、布隆过滤器、互斥锁、逻辑过期、随机过期时间、多级缓存

**面试口语：**

缓存穿透是查不存在，击穿是热点 key 突然失效，雪崩是大量 key 同时失效。解决时要先判断是哪一种，再选择空值缓存、互斥重建、随机过期时间或多级缓存。

**底层原理 / 背后逻辑：**

缓存的本质是用内存挡住数据库压力。一旦缓存没有挡住，数据库会突然承受原本不该承受的流量。穿透、击穿、雪崩都是缓存保护层失效，只是失效范围不同：单个不存在 key、单个热点 key、大量 key。

### 2. 🔥 缓存一致性

**简要总结：**

- 常见策略：先更新数据库，再删除缓存
- 不建议先更新缓存再更新数据库
- 删除缓存可能失败，需要重试或消息队列补偿
- 对强一致场景，不能只依赖缓存

**面试口语：**

缓存一致性通常不能做到绝对强一致，更多是最终一致。常见做法是更新数据库成功后删除缓存，下次查询再重新加载。关键业务要能接受短暂不一致，不能接受就直接读主库。

**底层原理 / 背后逻辑：**

数据库和缓存是两个系统，跨系统更新天然没有单机事务保证。先改库再删缓存，是因为数据库是权威数据源，缓存只是副本。删除失败时要有重试、binlog 订阅或异步补偿，避免旧缓存长期存在。

## 持久化与高可用

### 1. 🔥 RDB 和 AOF

**简要总结：**

- RDB：定期生成内存快照
- AOF：记录写命令日志
- RDB 恢复快，但可能丢最近数据
- AOF 数据更完整，但文件可能更大

**面试口语：**

RDB 像拍快照，恢复速度快，但两次快照之间的数据可能丢失。AOF 像记录操作日志，数据更完整，但文件更大，恢复时要重放命令。

**底层原理 / 背后逻辑：**

Redis 是内存数据库，宕机后内存会丢，所以需要持久化。RDB 用某个时间点的完整快照换恢复速度，AOF 用连续日志换更小的数据丢失窗口。实际生产常常两者结合。

### 2. ⭐ Sentinel 和 Cluster

**简要总结：**

- Sentinel：监控主从并自动故障转移
- Cluster：数据分片和横向扩展
- 主从复制解决读扩展和备份
- 集群会带来跨 slot 操作限制

**面试口语：**

Sentinel 主要解决高可用，主节点挂了可以自动选新主。Cluster 主要解决容量和吞吐扩展，把 key 分散到多个节点上。

**底层原理 / 背后逻辑：**

高可用和扩展是两件事。Sentinel 关注节点故障切换，Cluster 关注数据分片。分片后单 key 操作很快，但多个 key 如果不在同一个 slot，事务和批量操作会受限制。
