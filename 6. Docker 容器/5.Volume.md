## 数据持久化

### 1. 🔥 为什么需要 Volume

**简要总结：**

- 容器可写层随容器删除而丢失
- 数据库、上传文件、日志需要持久化
- Volume 生命周期独立于容器
- 可以在容器重建后保留数据

**面试口语：**

容器本身适合无状态运行，重要数据不能只放容器可写层。比如数据库数据、用户上传文件，要放到 Volume 或宿主机挂载目录里。

**底层原理 / 背后逻辑：**

容器删除时，可写层会被删除。Volume 是 Docker 管理的独立存储位置，挂载到容器目录后，容器读写这个目录其实是在读写外部持久存储。这样容器可以重建，数据仍然保留。

### 2. 🔥 bind mount 和 volume

**简要总结：**

- bind mount：宿主机指定路径挂到容器
- volume：Docker 管理存储位置
- 开发环境常用 bind mount
- 生产数据更常用 volume 或专门存储

**面试口语：**

bind mount 是把宿主机某个明确目录挂进去，适合开发时同步代码。volume 是 Docker 管理的数据卷，适合让容器数据独立持久化。

**底层原理 / 背后逻辑：**

挂载会覆盖容器镜像中对应路径的内容。比如镜像里 `/app` 有文件，但运行时把宿主机空目录挂到 `/app`，容器看到的就是空目录。这是很多“镜像里有文件但运行时找不到”的原因。

## 常见场景

### 1. ⭐ 数据库容器数据

**简要总结：**

- 数据库数据目录必须挂载
- MySQL 常见 `/var/lib/mysql`
- PostgreSQL 常见 `/var/lib/postgresql/data`
- Redis 持久化也要挂载数据目录

**面试口语：**

数据库容器一定要挂载数据卷，否则容器删除或重建后数据会丢。数据库镜像升级时，也要先备份再操作，不能只依赖容器还在。

**底层原理 / 背后逻辑：**

数据库的数据文件写在容器文件系统里，如果没有外部挂载，本质上仍在容器可写层。容器重建是常见操作，所以数据库数据必须和容器生命周期解耦。

### 2. ⭐ 权限问题

**简要总结：**

- 容器内用户可能没有宿主机目录权限
- UID / GID 不匹配会导致写入失败
- 日志和上传目录常见
- 排查要看容器内进程用户和挂载目录权限

**面试口语：**

挂载目录写不了时，我会看容器内服务用哪个用户运行，再看宿主机目录 owner 和权限。很多时候不是程序 bug，而是 UID、GID 或目录权限不匹配。

**底层原理 / 背后逻辑：**

Linux 权限看的是用户 id，不是用户名字符串。容器内外用户名可能不同，但 UID 相同就被认为是同一个身份。挂载目录权限问题要从 UID / GID 角度看。
