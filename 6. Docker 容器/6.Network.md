## Docker 网络基础

### 1. 🔥 Docker 网络模式

**简要总结：**

- bridge：默认桥接网络
- host：直接使用宿主机网络
- none：无网络
- container：共享另一个容器网络 namespace
- Compose 默认会创建项目级网络

**面试口语：**

Docker 默认使用 bridge 网络，容器有自己的 IP，通过端口映射对外访问。host 模式直接使用宿主机网络，性能简单但隔离性更弱。

**底层原理 / 背后逻辑：**

Docker 通过 network namespace 给容器独立网络视图，再通过虚拟网桥、iptables NAT 和端口映射实现容器与宿主机、外部网络通信。容器网络问题本质上仍然是 Linux 网络问题。

### 2. 🔥 端口映射

**简要总结：**

- `-p 宿主机端口:容器端口`
- 容器内服务要监听正确端口
- 宿主机端口冲突会启动失败
- 只暴露需要访问的端口

**面试口语：**

容器里服务监听的是容器端口，外部访问要通过宿主机端口映射。比如 `-p 8080:80`，外部访问宿主机 8080，Docker 转发到容器 80。

**底层原理 / 背后逻辑：**

容器和宿主机有不同网络命名空间。端口映射是 Docker 在宿主机上配置转发规则，把外部流量导入容器。映射了端口不代表服务一定可用，还要看容器内进程是否监听。

## 容器互通

### 1. 🔥 容器之间怎么访问

**简要总结：**

- 同一 Docker 网络内可以互通
- Compose 中可以用服务名访问
- 不建议用容器 IP 写死配置
- 跨网络默认不能直接访问

**面试口语：**

Docker Compose 里，后端访问数据库通常直接用服务名，比如 `mysql:3306`，而不是写容器 IP。因为容器 IP 可能变化，服务名会通过 Docker DNS 解析。

**底层原理 / 背后逻辑：**

Docker 为自定义网络提供内置 DNS。容器加入同一个网络后，服务名可以解析到对应容器 IP。容器重建 IP 变了，但服务名不变，所以配置更稳定。

### 2. ⭐ localhost 问题

**简要总结：**

- 容器内的 localhost 指容器自己
- 不是宿主机
- 也不是其他容器
- 访问其他容器用服务名
- 访问宿主机要用特殊地址或网关

**面试口语：**

容器里写 `localhost`，访问的是容器自己，不是宿主机。后端容器要访问数据库容器，应该写数据库服务名；要访问宿主机服务，需要用宿主机网关地址。

**底层原理 / 背后逻辑：**

每个容器有自己的网络 namespace，loopback 地址也是隔离的。`127.0.0.1` 永远指当前网络命名空间自身，所以容器内 localhost 和宿主机 localhost 不是一回事。
