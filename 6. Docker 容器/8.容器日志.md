# 容器日志

> 图标说明：⭐ 重点｜🔥 高频｜⚠️ 注意｜💡 提示｜📌 重点记忆

## 日志基础

### 1. 🔥 docker logs 看什么

**简要总结：**

- 查看容器标准输出和标准错误
- 常用于排查启动失败
- `docker logs -f` 实时跟踪
- `--tail` 查看最近日志
- `--since` 按时间过滤

**面试口语：**

容器启动失败或反复重启时，我第一步通常看 `docker logs`。容器化应用最好把日志输出到 stdout 和 stderr，让 Docker 或日志系统统一采集。

**底层原理 / 背后逻辑：**

容器日志默认来自主进程的标准输出和标准错误。Docker 日志驱动负责把这些输出保存到宿主机或转发到日志系统。应用把日志写进容器内部文件，反而不利于统一采集。

### 2. 🔥 容器日志过大

**简要总结：**

- 默认 json-file 日志可能持续增长
- 日志过大会打满磁盘
- 需要设置 max-size 和 max-file
- 生产要接入集中式日志

**面试口语：**

Docker 容器日志如果不限制大小，长期运行可能打满宿主机磁盘。生产环境要配置日志轮转，或者接入 ELK、Loki 这类集中式日志系统。

**底层原理 / 背后逻辑：**

Docker 默认会把容器 stdout/stderr 写到宿主机日志文件。服务高频打印日志时，日志文件会快速增长。磁盘满后，不只是这个容器受影响，宿主机上其他服务也可能异常。

## 日志设计

### 1. ⭐ 容器里要不要写日志文件

**简要总结：**

- 推荐输出到 stdout / stderr
- 不推荐只写容器内部文件
- 必要文件日志要挂载到宿主机或 volume
- 日志要包含 trace_id

**面试口语：**

容器化应用更推荐把日志打到标准输出，由平台统一收集。如果必须写文件，也要挂载出来，并配置切割策略。

**底层原理 / 背后逻辑：**

容器可能随时被销毁和重建，内部文件不可靠。stdout/stderr 是容器平台天然能接管的日志出口，更适合云原生部署和多实例日志聚合。

### 2. ⭐ 多容器日志排查

**简要总结：**

- 先定位哪个服务出错
- 再按 trace_id 串联日志
- 网关、后端、任务、模型服务都要看
- Compose 可用 `docker compose logs 服务名`

**面试口语：**

多容器应用排查不能只看一个容器。一次请求可能经过 Nginx、后端、Redis、数据库和任务容器，要按 trace_id 和时间线把日志串起来。

**底层原理 / 背后逻辑：**

容器把服务拆开运行，隔离性变强，但日志也分散了。集中式日志和 trace_id 的价值，就是把分散在不同容器里的事件重新拼成一条请求链路。

## 面试优先级

### 第一优先级

- 🔥 docker logs
- 🔥 stdout / stderr
- 🔥 日志过大和磁盘
- 🔥 日志轮转

### 第二优先级

- ⭐ docker compose logs
- ⭐ trace_id
- ⭐ 集中式日志

### 第三优先级

- 💡 logging driver
- 💡 sidecar 日志采集
