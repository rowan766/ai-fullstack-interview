## 容器运行

### 1. 🔥 容器是什么

**简要总结：**

- 容器是镜像运行后的实例
- 容器本质是被隔离和限制的进程
- 容器有自己的文件系统视图、网络视图、进程视图
- 容器生命周期跟主进程相关

**面试口语：**

容器不是一台小虚拟机，它本质上是宿主机上的进程，只是通过 Docker 做了文件系统、网络、进程等隔离，让它看起来像在独立环境里运行。

**底层原理 / 背后逻辑：**

Linux namespace 提供隔离视图，比如 PID namespace 让容器内看到自己的进程树，network namespace 让容器有自己的网卡和路由，mount namespace 让容器看到独立文件系统。cgroups 再限制它能用多少 CPU 和内存。

### 2. 🔥 容器为什么退出

**简要总结：**

- 容器主进程结束，容器就退出
- 后台启动服务可能导致主进程立即结束
- 启动命令错误会退出
- 配置或依赖缺失会退出
- 用 `docker logs` 看原因

**面试口语：**

容器的生命周期跟主进程绑定。如果主进程退出，容器就退出。所以容器里服务要以前台方式运行，不能启动后直接放后台然后让主进程结束。

**底层原理 / 背后逻辑：**

Docker 管理的是容器的 PID 1 主进程。这个进程存在，容器存在；这个进程退出，容器也结束。生产排查容器反复重启时，第一步就是看主进程为什么退出。

## 进入和排查

### 1. 🔥 docker exec 和 docker attach

**简要总结：**

- `docker exec`：在运行中容器里启动新命令
- `docker attach`：连接到容器主进程
- 排查通常用 exec
- attach 可能影响当前主进程交互

**面试口语：**

排查容器内部环境我一般用 `docker exec -it 容器名 sh`，它是在容器里新开一个 shell。`attach` 是连到主进程输入输出，使用时要小心。

**底层原理 / 背后逻辑：**

exec 会在已有容器 namespace 中创建一个新的进程，所以能看到容器内部文件、网络和环境。attach 只是接入主进程的标准输入输出，不适合大多数排查场景。

### 2. ⭐ 容器内修改为什么不可靠

**简要总结：**

- 容器内修改只在当前容器可写层
- 删除容器后修改丢失
- 重建容器不会保留手动改动
- 正确做法是改 Dockerfile、配置或挂载卷

**面试口语：**

容器里临时改文件只能用于排查，不应该当正式修复。正式修复要改镜像、配置或挂载的数据卷，否则容器一重建就没了。

**底层原理 / 背后逻辑：**

容器可写层属于当前容器，不属于镜像。镜像不变，重建出来的容器还是旧环境。容器化部署强调不可变基础设施，修改应该通过重新构建和发布实现。
