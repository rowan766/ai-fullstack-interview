## Compose 基础

### 1. 🔥 Docker Compose 是什么

**简要总结：**

- 用一个 YAML 文件管理多容器应用
- 定义服务、镜像、构建、端口、环境变量、卷、网络
- 适合本地开发、测试环境、小型部署
- 常用于后端 + 数据库 + Redis + Nginx

**面试口语：**

Docker Compose 适合管理一组相关容器。比如一个后端项目需要 API 服务、MySQL、Redis、Nginx，就可以用 compose 文件统一启动和管理。

**底层原理 / 背后逻辑：**

Compose 本质上还是调用 Docker API 创建镜像、容器、网络和卷。它解决的是多容器配置和启动顺序的组织问题，让环境可以用声明式文件复现。

### 2. 🔥 compose.yml 常见字段

**简要总结：**

- `services`：定义服务
- `image`：使用已有镜像
- `build`：从 Dockerfile 构建
- `ports`：端口映射
- `environment`：环境变量
- `volumes`：挂载卷
- `depends_on`：依赖关系

**面试口语：**

Compose 里最核心的是 services。每个 service 对应一类容器，可以配置镜像、构建方式、端口、环境变量、挂载目录和依赖关系。

**底层原理 / 背后逻辑：**

Compose 会为项目创建默认网络，同一个 compose 项目里的服务可以通过服务名互相访问。它把原来很多条 `docker run` 命令变成一份可维护的配置文件。

## 依赖和健康检查

### 1. 🔥 depends_on 不等于服务可用

**简要总结：**

- `depends_on` 只保证启动顺序
- 不保证数据库已经准备好
- 应用需要重试连接
- 可以配合 healthcheck

**面试口语：**

`depends_on` 只能说明先启动数据库容器，再启动后端容器，但不代表数据库已经能接受连接。后端启动时还要有连接重试，或者配合 healthcheck。

**底层原理 / 背后逻辑：**

容器启动和服务就绪是两件事。MySQL 容器进程起来后，初始化数据、恢复日志、监听端口都需要时间。应用如果立刻连接，可能会失败。

### 2. ⭐ 环境变量和配置

**简要总结：**

- 环境变量适合注入配置
- 不要把敏感信息提交到仓库
- `.env` 可供 Compose 读取
- 生产环境要结合密钥管理

**面试口语：**

Compose 可以用环境变量注入数据库地址、账号、端口等配置。本地可以用 `.env`，生产环境敏感信息最好走密钥管理，不要直接提交到 Git。

**底层原理 / 背后逻辑：**

容器镜像应该尽量保持环境无关。不同环境的差异通过环境变量、挂载配置或平台配置注入，这样同一个镜像可以跑在开发、测试和生产环境。
